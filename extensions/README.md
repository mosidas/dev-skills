# 拡張サンプル集(Layer 3)

個別具体的なパターン(受託開発の納品物など)でのみ要求される拡張スキル・拡張ワークフローのサンプル。**この場所のファイルは実行時に読まれない**。展開スクリプト(`../install.py`)で利用側プロジェクトへ導入して使う。本体(Layer 0〜2)はこれらの拡張の存在を前提にしない(なくても動く)。

## 1. グループと収録物

拡張バンドルは、まとまりごとにグループ化して `extensions/<グループ名>/` に置く。各グループはバンドル群と README(グループの目的・収録物・グループ固有の導入手順)を持つ。

```
extensions/
├── README.md                  # 本書(Layer 3 全体の規約・導入手順の正本)
└── <グループ名>/
    ├── README.md              # グループの目的・収録物・グループ固有の導入手順
    ├── ext-<name>/            # 拡張スキル
    └── flow-<name>/           # 拡張ワークフロー
```

- バンドルはいずれかのグループに置く(`extensions/` 直下に置かない)。
- 1 つのバンドルを複数のグループで使ってよい(導入はバンドル単位のため、利用側は必要なグループの README に従って組み合わせる)。バンドル名はグループをまたいで一意にすることが望ましい(同名がある場合、install.py は `<グループ名>/<バンドル名>` の指定を要求する)。

現在、収録済みのバンドルグループはない。本書は拡張を自作・導入するときの規約(グループ構成・導入手順・作成規約)を定める枠組みとして維持する。

## 2. 利用側プロジェクトへの導入(install.py)

配布ルートの `install.py`(Python 3 標準ライブラリのみ)で導入する。導入・削除は利用側の明示操作である(DESIGN §3 規律 9)。

```console
$ python3 <dev のパス>/install.py core --target <利用側プロジェクト>          # コア(skills・agents)をコピー
$ python3 <dev のパス>/install.py ext <name> --target <利用側プロジェクト>       # 拡張バンドルを導入(バンドル名は全グループから解決)
$ python3 <dev のパス>/install.py status --target <利用側プロジェクト>         # 導入状態を表示
$ python3 <dev のパス>/install.py remove <name> --target <利用側プロジェクト>  # 拡張を削除
```

導入はすべて**ハードコピー**(シンボリックリンクを使わない。devcontainer 等でホスト側パスが解決できない環境でも動き、利用側が導入物を自リポジトリに Git 管理できる。D-006)。

- **バンドル名の解決**: `ext <バンドル名>` は全グループ(`extensions/*/`)から検索する。複数グループに同名バンドルがある場合はエラーになるため、`ext <グループ名>/<バンドル名>` で指定する。導入先(`.claude/skills/<バンドル名>/`)と lock の記録名にグループ名は含まない。
- **core**: `dev-*` / `flow-*` の `.claude/skills/*` と `.claude/agents/*.md` をコピーする(`meta-*` は dev-skills 自身の保守用のため配布しない)。記録は `.claude/dev-core.lock.json`。再実行(更新)で、前回コピーして今回の配布元に無いスキル・エージェント(廃止分)を削除する。
- **拡張**: `.claude/skills/<name>/` にバンドルのスキル本体(`agents/`・`ports/`・`settings.snippet.json` を除く。`hooks/` は含む)をコピーする。コピーのため相対参照 `../dev-core/` は導入先の実体へ解決する(シンボリックリンクのようにディレクトリごとで壊れる問題がない)。
- **hooks を持つ拡張**: `settings.snippet.json` を利用側 `.claude/settings.json` へ冪等マージし、管理集合を `.claude/dev-extensions.lock.json` に記録する。`remove` はこの記録に基づき hooks を取り消す(利用側の既存設定には触れない)。
- **同梱 port**: バンドルの `ports/` を `docs/dev/ports/<name>/` へコピーする(既存ファイルは上書きしない)。コピー後は利用側の資産であり、`remove` でも削除しない。
- 汎用の port サンプルはリンク・自動コピーせず、`<dev のパス>/ports/` から必要なものを**コピー**してプロジェクトに合わせて編集する(port はプロジェクト側の資産)。
- グループ固有の導入手順・差し替え port の要件は各グループの README に従う。

## 3. 拡張を自作するときの規約

### 3.1. バンドル構成(1 拡張 = 1 自己完結フォルダ)

拡張は skill・agents・hooks・port を 1 つのフォルダに梱包し、`install.py` が展開する。バンドルは所属するグループのディレクトリ配下に置く(1. のグループ構成)。

```
extensions/<グループ名>/<name>/
├── SKILL.md              # 必須。拡張スキル・拡張ワークフローの本体
├── references/ templates/ # 任意。スキルの補助ファイル
├── scripts/              # 任意。拡張固有の決定論的スクリプト(Python 3 標準ライブラリのみ)
├── workflow.json 等      # 任意。拡張ワークフロー(flow-*)の状態機械定義(バンドル直下。dev-core の state.py が読む)
├── agents/               # 任意。拡張固有エージェント(<name>-*.md)
├── hooks/                # 任意。hook スクリプト
├── settings.snippet.json # hooks/ を持つとき必須。配線内容(hooks と permissions.deny のみ)
└── ports/                # 任意。同梱 port(導入時に docs/dev/ports/<name>/ へコピー。利用側が案件ごとに編集する差し替え port の雛形に限る = ports.md §4)
```

- `settings.snippet.json` のコマンドパスは `$CLAUDE_PROJECT_DIR/.claude/skills/<name>/hooks/...` で書く(導入先で解決される)。
- 同梱エージェントの命名は `<name>-*` とし、Layer 0 の役割エージェント(dev-\*)と衝突させない・上書きしない。

### 3.2. 依存と内容の規律

- 命名: 拡張スキルは `ext-*`、拡張ワークフローは `flow-*`。
- 依存: Layer 0〜1(dev-core・部品)に依存してよい。**Layer 2 の composition(flow-sdd 等)は参照しない**(必要な工程は部品を直接束ねる)。本体を変更してはならない(変更に閉じ、拡張に開く)。
- 顧客・組織固有の内容は拡張・port 側に置き、汎用化できる部分は本体への提案として分離する。
- hooks・settings.json・MCP は本体(Layer 0〜2)では使用しない(DESIGN §3 規律 9)。イベント駆動の自動実行(検査の機械的強制・テレメトリ等)が必要な場合は「hooks 配線」として 3.1 の形で梱包する。導入は `install.py`(利用側の明示操作)が行う。
- 拡張スキルは実行時に port(利用側資産)を生成・編集してよい(例: 原則 port の策定支援)。既存ファイルを上書きする場合はユーザーに確認する。
