# D-000: dev スキル群 設計思想(初版)

> meta-doc 導入前の手書き `DESIGN.md`(初版)の内容を、判断層の基底(D-000)として保存したもの。以後 `DESIGN.md` の構造層は meta-doc が `.claude` から再生成する。相対リンクは本ファイルの位置(`.meta/decisions/`)に合わせて階層を 1 つ深くしてある。

本書は、汎用開発スキル群 `dev-skills` リポジトリのアーキテクチャ設計を定める。

先行する SDD(仕様駆動開発)のスキル群・ツール群の知見を参考にする(GitHub Spec Kit、cc-sdd、[addyosmani/agent-skills](https://github.com/addyosmani/agent-skills))。ただし、それらに共通する次の 3 点は採らない。第一に、顧客ヒアリングの質問セットや納品物形式など特定プロジェクト向けのカスタマイズを本体に混在させること(他のプロジェクトへ持ち出せなくなる)。第二に、状態機械の phase を SDD 前提でスクリプトに焼き込むこと(SDD 以外のワークフローを組めなくなる)。第三に、ドキュメントを SSoT とすること(コードとの整合を保つ維持コスト、すなわち上流変更時のカスケード再生成とドリフトの再整合を恒常的に要求する。ドキュメント SSoT を採る体系が再整合の工程を必要とすること自体が、放置するとドリフトすることの証拠である)。

そこで本スキル群の構成は 1 から起こす。SSoT はソースコードに置き、仕様ドキュメントは実装までの中間生成物と位置づける。スキル群は汎用の部品と差し替え可能な拡張点で構成し、SDD はこの部品群から組み立てる composition の一つと位置づける。

本書の規約は、要請レベルを RFC2119 に対応する日本語の語句(しなければならない = MUST、する必要がある = SHOULD、してもよい = MAY)で表す。

本書が定めるのは構造(レイヤー・依存の規律・部品の構成)と設計判断の理由である。実行時の手順・スキーマ・カタログ(port の宣言と選択、状態機械の定義データと操作、レビュー観点、恒久情報の配置等)の正本は dev-core のリファレンス群であり、本書の記述と差異がある場合はリファレンス側を正とする。

## 1. 設計原則

### 1.1. オニオン型レイヤリング

スキル群を 4 つの同心レイヤーに分け、依存は外側から内側への一方向に限定する(オニオンアーキテクチャの依存規則をスキル群の構成に適用する。出典: [Jeffrey Palermo, The Onion Architecture](https://jeffreypalermo.com/2008/07/the-onion-architecture-part-1/))。内側のレイヤーは外側のレイヤーの存在を知らない。これにより、外側(ワークフロー・顧客固有拡張)をいくら追加・変更しても内側(部品・基盤)に影響しない。

### 1.2. コードが SSoT

恒久的な真実(SSoT)はソースコードのリポジトリにのみ置く。プロジェクト内の文書は「恒久情報 / 中間生成物(実装完了で凍結)/ 注入知識(1.5)」の 3 分類に限り、これ以外の恒久文書を作ってはならない。分類の定義と規律の正本は [principles.md](../../.claude/skills/dev-core/references/principles.md) §1、恒久情報の配置規約の正本は [durable-info.md](../../.claude/skills/dev-core/references/durable-info.md)。

この転換の帰結として、ドキュメント SSoT の維持コスト(上流変更のカスケード再生成、コード↔文書の再整合)は構造ごと消える。凍結された中間生成物には整合を保つ義務がない。

大規模な自然言語ドキュメント(アプリ全体仕様書等)が恒久的に要求されるのは、受託開発の納品物など個別具体的なパターンに限られる。その要求は拡張(Layer 3)のスキル・ワークフローが満たし、生成された文書は納品成果物であって SSoT ではない(コードとの整合の正は常にコード)。この場合も Layer 1 の部品は変更しない(2.4)。

### 1.3. 機構と方針の分離

汎用性の中核は、機構(mechanism)と方針(policy)の分離である。基盤は「状態機械を回すエンジン」「成果物を検査する枠組み」という機構だけを提供し、「どんな状態があり、どう遷移するか」という方針は composition がデータとして与える。状態機械の実装が phase の enum を機構へ焼き込むと SDD 専用になるため、この分離が汎用化の直接の解決策になる。

### 1.4. 部品の自立性

部品スキル(Layer 1)は、ワークフローの外で単独で呼び出しても機能しなければならない。そのために、各部品は入出力の既定値(読むファイル・書くファイルの既定パス)を自身で持ち、composition はそれを上書きして使う。

### 1.5. port による拡張

部品本体に固有の内容を書かず、規約パスのファイルとして差し込む。部品は「所定パスにファイルがあればそれに従う、なければ部品内のデフォルトに従う」という規約を持つ。port は 2 種類ある。

- 差し替え port: 組織・顧客固有の内容でデフォルトを置き換える。例: ヒアリング質問セット、言語規約、納品物形式
- 知識 port: 作業内容に応じて部品(主に dev-implement)へ条件付きで注入する専門知識。例: プログラミング言語別の知識、機能ドメイン別の知識(認証等)、視覚設計(GUI を持つときのみ)、コーディング原則・テスト方針、レビュー観点の追加(8.2)

視覚設計(frontend-design)やコーディング原則(principles)のように、独立したスキルや生成文書として持たれがちな要素は、この知識 port として定義する。「行為は部品、知識は port」と整理する。

### 1.6. 共通原則

SDD に依存しない共通原則(根拠主義・コンテキスト効率・承認ゲート・決定論的補完・オーケストレーション安全則)を基盤(Layer 0)の原則として定める。各原則の定義の正本は [principles.md](../../.claude/skills/dev-core/references/principles.md)(オーケストレーション安全則の詳細は [orchestration-patterns.md](../../.claude/skills/dev-core/references/orchestration-patterns.md)「中核原則」)。

## 2. レイヤー構造

### 2.1. Layer 0: foundation(基盤)

何にも依存しない最内層。以下を含む。

- 共通原則(1.6 の内容)と成果物契約の記法(トレーサビリティ記法、曖昧語禁止・定量化ルール、恒久情報の配置規約)を定めるリファレンス群
- 決定論的スクリプト: 汎用状態機械エンジン、静的チェッカの枠組み(いずれも Python 3 標準ライブラリのみ)
- 役割エージェントの定義(8. を参照)

### 2.2. Layer 1: parts(部品)

単機能のスキル群。1 スキル 1 機能とし、foundation のみに依存する。部品は役割で 3 区分する。

- コア部品(implement・release): 永続成果物であるコードを扱う。implement はコードを作り、release は出荷可否を判定する
- サブ部品(requirements・design・decompose): 作業単位(issue・feature 等)を整理して implement へ渡すための中間生成物を作る。出力は実装完了で凍結される
- オプション部品(check): 必要時のみ使う read-only の検査

生成後のレビューは独立部品にせず、各部品に内蔵するレビューゲート(独立文脈の reviewer)として実装する。

部品同士は相互参照してはならない。連携は成果物ファイルの契約(どのファイルを読み、どのファイルを書くか)だけで行う。

### 2.3. Layer 2: composition(ワークフロー)

部品を状態機械で束ねたワークフロー。SDD(flow-sdd)はここの一つである。composition は以下を持つ。

- 状態機械の定義データ(状態・遷移・承認ゲート)
- 部品の呼び出し順と、部品の入出力既定値の上書き
- そのワークフロー固有の要素(SDD なら作業単位への振り分け)

composition が依存してよいのは部品(Layer 1)と foundation(Layer 0)のみで、**composition 同士は参照しない**。また、承認の自動化(自己承認・自走)は Layer 2 の composition の要件から除外する(必要な場合は Layer 3 の拡張ワークフローとして実現する)。

### 2.4. Layer 3: extension(拡張)

組織・顧客・ドメイン固有の要求を満たす最外層。本スキル群の配布物には含めず(サンプルは含めてよい)、利用側が追加する。形態は 4 つある。

- port ファイル: 部品のデフォルトの差し替え・知識の注入(1.5)
- 拡張スキル: 個別パターンでのみ要求される行為(例: アプリ全体仕様書など納品用の大規模自然言語ドキュメントの生成)
- 拡張ワークフロー: 拡張スキルと Layer 1 部品を束ねた composition(例: 納品物込みの受託開発フロー)
- hooks 配線: イベント駆動の自動実行(検査の機械的強制・テレメトリ等)を要する要求を満たす、hook スクリプト + settings スニペットの組。コアの決定論的スクリプト(チェッカ等)を hooks から呼び出す形をとってよい。導入は展開スクリプトが利用側 `.claude/settings.json` へ冪等マージして行う(実行は利用側の明示操作。リンクだけでは導入が完結しない唯一の形態)

拡張は「1 拡張 = 1 自己完結フォルダ」で梱包する(スキル本体・同梱エージェント・hook スクリプト・settings スニペット・同梱 port)。導入・削除は配布ルートの展開スクリプト(`install.py`)が行い、バンドル構成と導入手順の正本は extensions/README.md とする。拡張固有のエージェントは `<拡張名>-*` で命名し、Layer 0 の役割エージェントを変更・上書きしない(8.3)。

本体(Layer 0〜2)は変更に閉じ、拡張に開く。個別具体的な要求は拡張の追加で満たし、Layer 1 の部品を変更してはならない。拡張スキル・拡張ワークフローは Layer 0〜1(foundation・部品)に依存してよいが、**Layer 2 の composition(flow)は参照しない**(必要な工程は部品を直接束ねる。flow 間の結合は、拡張の要求が本体の flow へ逆流する経路になるため)。内側のレイヤーは extension の存在を前提にしてはならない(なければデフォルトで動く)。命名は、拡張ワークフローは `flow-*`(composition と同じ機構に乗るため)、拡張スキルは `ext-*` を推奨する。

## 3. 依存の規律

以下を非交渉の規律とする。

1. 依存は外側から内側への一方向とする。内側のスキル・スクリプト・リファレンスが外側を参照してはならない
2. 部品同士は相互参照してはならない。連携は成果物ファイルの契約に限る
3. 部品は composition の状態を進めてはならない。部品は「成果物を書いたら完了」であり、状態遷移(phase 更新・承認)は composition の責務とする
4. 顧客・組織固有の固有名詞・質問文・書式は、Layer 0〜2 に書いてはならない。port(Layer 3)へ外出しする
5. 凍結された中間生成物を変更してはならない。実装後に判明した差異はコード(と恒久情報)へ反映する
6. 個別具体的なパターンでのみ要求される成果物・文書(納品物等)は、拡張スキル・拡張ワークフローの追加で満たす。Layer 0〜2 の変更で満たしてはならない
7. 実行時に読まれるファイル(`.claude/` 配下のエージェント・スキル・リファレンス・スクリプト)は、`.meta/` および配布物の外(他のスキル群等)を参照してはならない。`.meta/` は設計文書であり、配布物に含まれなくてもスキル群は動作する
8. composition(拡張ワークフローを含む)は、他の composition を参照してはならない。ワークフローが必要とする工程は部品(Layer 1)と foundation(Layer 0)を直接束ねて実現する(flow 間の結合は、外側の要求が内側の flow へ逆流する経路になるため)
9. コア(Layer 0〜2)が使用してよい実行機構は、スキル(SKILL.md・references・templates・scripts)とエージェント定義(`.claude/agents/*.md`)に限る。hooks・settings.json・MCP を使用してはならない。判断原理は「ファイル配置(シンボリックリンク)だけで導入・削除が完結する機構のみを使う」である。プロジェクト単位のシングルトン設定(settings.json)はリンク配布と両立せず、常駐的副作用(hooks・MCP)はスキルの起動と無関係に働くため部品の自立性(1.4)とレイヤー隔離を破る。これらを要する要求は Layer 3 の hooks 配線(2.4)として満たす

## 4. ディレクトリ構成と命名

```
dev-skills/
├── CLAUDE.md                    # 言語規約など最小限のプロジェクト指示
├── install.py                   # 導入スクリプト(コアのリンク・拡張バンドルの展開)
├── .meta/                       # 本書・README 等の設計文書
└── .claude/
    ├── agents/                  # 役割エージェント(Layer 0)
    └── skills/
        ├── dev-core/            # Layer 0: 共有リファレンス + スクリプト
        ├── dev-<部品名>/        # Layer 1: 各部品(SKILL.md + templates/)
        └── flow-<ワークフロー名>/ # Layer 2: composition(SKILL.md + 状態機械定義)
```

命名はレイヤー別 prefix とする。foundation と部品は `dev-*`、composition は `flow-*`。スキル名はプロジェクト内でフラットな名前空間のため、prefix で組み込みスキル(/code-review 等)との衝突を避け、呼び出し時にレイヤーを識別できるようにする。

## 5. 部品一覧

| 区分       | 部品             | 機能                                                                                                               | 出力の性質                 |
| ---------- | ---------------- | ------------------------------------------------------------------------------------------------------------------ | -------------------------- |
| コア       | dev-implement    | TDD 実装(implementer/reviewer/debugger 協調)。知識 port を作業内容に応じて注入                                     | 永続(コード)               |
| コア       | dev-release      | 出荷可否判定(GO/NO-GO)とリリース計画(フラグ・段階ロールアウト・ロールバック・監視)                                 | 永続(コード同居文書)+ 一時 |
| サブ       | dev-spec         | 壁打ち(対話)による仕様化: 公開インターフェース・データ構造の契約と EARS 受け入れ基準を spec.md 1 本に確定する(flow-sdd の上流部品)         | 中間生成物                 |
| サブ       | dev-decompose    | 参照で自己完結するタスクへの分解(タスク固有情報 + 仕様文書への ID・節参照。仕様の転記はしない。File Structure Plan も担う) | 中間生成物                 |
| オプション | dev-check        | read-only の整合性検査。対象はコード内一貫性・知識 port への準拠・テストと実装の対応                               | 一時(レポート)             |

上流工程は、当初 dev-requirements(EARS 要件)+ dev-design(責務境界・設計)+ dev-decompose の 3 部品として設計したが、dev-spec(壁打ちで契約と受け入れ基準を確定)+ dev-decompose の 2 部品に再編した(実運用で、必要な上流工程は「対話で公開インターフェース・データ構造を定める」と「実装タスクへの分解」の 2 つであり、要件文書と設計文書の分割が同内容の書き分けになっていたため)。dev-requirements / dev-design のスキルは削除し、上流成果物は spec.md 1 本に一本化した(requirements.md + design.md のレガシー 2 文書構成とその後方互換読み取りは撤去した)。

## 6. 部品の入出力契約

### 6.1. workdir 方式

部品の入出力は「workdir(成果物ディレクトリ)+ 固定ファイル名」の 2 段で定める。

- 部品は workdir 内の固定ファイル名で読み書きする。例: dev-spec は `<workdir>/spec.md` を書き、dev-decompose はそれを読んで `<workdir>/tasks.md` を書く
- workdir は呼び出し時の引数とし、既定値は利用側プロジェクトの `docs/dev/` とする。composition はこれを上書きする(flow-sdd なら作業単位ごとのディレクトリ)
- 部品は上流成果物を「ファイル名の契約」としてのみ知る。誰が書いたか(他の部品か人間か)に依存してはならない

### 6.2. 契約の宣言

各部品の SKILL.md は冒頭に契約セクションを持ち、以下を宣言する。

- 入力: workdir 内のファイル名と、必須か任意か
- 出力: workdir 内のファイル名
- port: 参照する規約パス(1.5)

成果物の中身のフォーマットは部品の `templates/` が定義する。部品間で参照し合う ID 記法(トレーサビリティ)は dev-core の記法規約に従う。

port の配置(共通ルート `docs/dev/ports/`・自由階層)・frontmatter による宣言(`name` / `inject` / `condition`)・走査と選択の優先順は、**ポートマッピング**として [ports.md](../../.claude/skills/dev-core/references/ports.md) を正本とする。設計判断として本書に残すのは次の 2 点である。第一に、識別は配置パスではなく frontmatter の `name` で行い、ルート以下の階層を人間の整理用として意味から切り離す(利用側の整理の自由と機械照合の両立)。第二に、注入先は port 側が宣言する。これにより port の追加・削除・移動が 1 ファイルで完結し、スキル側の変更を要しない(開放閉鎖が port にも及ぶ)。選択結果は Implementation Notes 等に記録する(再現性の担保)。

拡張を隠しディレクトリではなく `docs/` 配下に置くのは、Docs-as-Code(拡張も Git 管理・PR レビュー対象にする)を継承するためである。

### 6.3. 単独利用時の入力欠落

単独利用で入力契約のファイルが存在しない場合、部品は停止せず、ユーザーの依頼文と AskUserQuestion で必要最小限の入力を確認して進む。ただし推測で埋めない原則(1.6 の承認ゲート・根拠主義)は維持し、確認できない事項を勝手に確定してはならない。

### 6.4. 中間生成物のライフサイクル

サブ部品の出力(spec.md・tasks.md 等)は、実装完了までは上流の変更に応じて更新してよい。実装完了(状態機械の完了状態への到達)をもって凍結とし、以後は参照専用とする。実装後に判明した仕様との差異は、中間生成物ではなくコードと恒久情報(テスト・ADR 等)へ反映する。凍結の機械的な表現と検査の正本は [static-check.md](../../.claude/skills/dev-core/references/static-check.md)。

## 7. 状態管理

### 7.1. エンジンと定義データの分離

foundation に汎用状態機械エンジン(スクリプト)を置き、各 composition が定義データで状態・遷移・承認ゲートを与える。

- エンジンの責務: 状態ファイルの生成・更新・検証、遷移の妥当性検査(定義にない遷移の拒否)、承認フラグの管理
- 定義データの責務: 状態の集合、遷移規則、各遷移に必要な承認ゲート、状態に応じて存在すべき成果物
- 定義データの形式は JSON とする。Python 3 標準ライブラリのみという制約(追加インストール不要の担保)の下では YAML パーサを使えないため

新しいワークフローは、定義データと composition スキルを追加するだけで組める。エンジンの変更を要してはならない。

### 7.2. 定義データとインスタンス状態

定義データは composition が持ち(例: `flow-sdd/workflow.json`)、エンジンは workdir 内に `state.json` を生成・更新する。定義データのスキーマ(states / initial / final / transitions / gate / artifacts)、エンジンの操作(init / set-state / approve / show / status / scan)、凍結(完了状態への到達時に成果物の sha256 を記録し、以後の変更を静的チェッカが検出する)の正本は [static-check.md](../../.claude/skills/dev-core/references/static-check.md)。

手書きでの state.json 編集はしない(エンジンの検証を通さない状態変更を許すと、遷移の妥当性検査と凍結の検出が無効になるため)。

gate の機械的強制が対象とするのは、`set-state` による承認の素通りという誤操作の防止である。人間承認そのものの担保(承認操作を人間の明示承認なしに実行しないこと)は、composition スキルの停止規律(1.6 の承認ゲート)が担う。

## 8. エージェント

### 8.1. 役割の構成

役割エージェントは Layer 0 の実行資源として `.claude/agents/` に一元定義し、部品は名前で参照する。5 役割とする。

| エージェント    | 役割                                                        | モデル |
| --------------- | ----------------------------------------------------------- | ------ |
| dev-implementer | タスク定義に基づく TDD 実装                                 | 高能力 |
| dev-debugger    | 失敗の根本原因の切り分けと最小修正                          | 高能力 |
| dev-reviewer    | 敵対的判定器(read-only)。コード検証と文書ゲートの両方を担う | 高能力 |
| dev-explorer    | read-only 調査。ダイジェストのみ返す                        | 軽量   |
| dev-author      | 文書生成の隔離実行                                          | 高能力 |

モデル配分は品質優先とする。事前の検証で、生成を中位モデルに落とすとコストは低くなるが実行時間と品質が悪化したため、コスト優先のティア分離を採らない(調査のみ軽量モデル)。各エージェントの具体的なモデルは agents 定義(`.claude/agents/*.md`)の frontmatter `model:` を正本とする。生成物の自己採点の甘さは、モデルティアではなく「生成と別の独立文脈 + 敵対的既定(不合格から出発し、立証できた項目のみ合格)」で避ける。

### 8.2. 多観点レビュー(判定器 1 + 観点カタログ)

レビューの多観点化(セキュリティ・コード構造・パフォーマンス・要件整合等)は、ペルソナ別のエージェント定義ではなく「汎用判定器 1 体(dev-reviewer)+ 観点カタログ(データ)」で実現する。観点の一覧・各観点の専門手順・返却契約・起動形態(観点別の並列 fan-out と軽量な文書ゲート)・port による追加差し替えの正本は [review-perspectives.md](../../.claude/skills/dev-core/references/review-perspectives.md)。

この方式を採る理由は 2 つある。第一に、観点の追加・差し替えがエージェント定義の追加ではなくデータの追加で済む(開放閉鎖)。第二に、各観点を独立したクリーンな文脈で当て、結果を保守的にマージする(1 観点でも Critical なら不合格)ことで、単一文脈の一括レビューより見落としを減らせる。

- 各部品の内蔵レビューゲート(2.2)は dev-reviewer を独立文脈で起動して実現する
- オーケストレーション安全則(1.6)はエージェント定義とリファレンスの双方で担保する

この方式は、プロンプト注入型の fan-out を一般化し、agent-skills のペルソナが持つ専門手順の深さをカタログ側へ取り込んだものである(出典: [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills))。

### 8.3. 拡張固有エージェント

拡張(Layer 3)は、バンドルに固有のエージェント定義を同梱してよい(2.4)。命名は `<拡張名>-*` とし、Layer 0 の 5 役割の変更・上書きをしてはならない。

## 9. 実装計画

オニオンの内側から外側へ、マイルストーン単位で作る。コア部品(dev-implement)をサブ部品より先に作るのは、コードが SSoT である本設計の中心部品であり、知識 port の注入機構という新規性の高い要素を最初に検証すべきためである。flow-sdd は最小構成(requirements→design→decompose→implement)から始め、オニオン設計の成立(部品が composition から組めること、エンジンが定義データだけで動くこと)を検証してから拡張する。

| マイルストーン | 内容                                                                                         | 検証すること                       |
| -------------- | -------------------------------------------------------------------------------------------- | ---------------------------------- |
| M1             | dev-core(記法規約・恒久情報の配置規約・状態機械エンジン・チェッカ枠組み)+ agents             | エンジンが定義データだけで動くこと |
| M2             | dev-implement(知識 port の注入機構を含む)                                                    | コア部品の単独利用と知識 port 注入 |
| M3             | サブ部品 3 つ(dev-requirements・dev-design・dev-decompose)                                   | ファイル契約連携と中間生成物の凍結 |
| M4             | flow-sdd 最小構成(composition スキル + workflow.json)                                        | オニオン全体の成立                 |
| M5             | dev-release・dev-check・port サンプル整備・flow-sdd 拡張(ルーティング・オーケストレーション) | 主要能力を一通り備えること         |
