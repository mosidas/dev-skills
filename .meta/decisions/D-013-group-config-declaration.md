# D-013: グループ固有の規約を宣言ファイルへ外出しする(2026-07-31)

## 背景

`meta-*` は「スキル群自体を構成するドキュメントの品質を担保する」道具である。しかし検査項目・抽出項目のいくつかは dev グループの構造(オニオン型のレイヤー・状態機械の命名規約・部品名のプレフィックス)を前提にしていた。D-012 で `writing`・`authoring` のグループを追加した結果、レイヤー構造も状態機械も持たないグループが同じ検査を受けることになった。

検査項目・抽出項目を棚卸しし、全グループ共通か、グループごとに前提が異なるか、リポジトリ全体の構成に依存するかで分類した。

| 項目 | スクリプト | 分類 | 判断の理由 |
| ---- | ---------- | ---- | ---------- |
| 参照実在 | meta_check | 共通 | 相対パス参照はどのスキルにもある |
| frontmatter(name と配置の一致・description) | meta_check | 共通 | Agent Skills 標準の要求で、グループによらない |
| 依存規律(`meta-*` を参照しない) | meta_check | 共通 | 配布するスキル全部に課す(D-012 で対象を拡大済み) |
| 未記入マーカー | meta_check | 共通 | 文書の記法の問題でグループによらない |
| description のトリガ | trigger_check | 共通 | description は全スキルが持つ |
| 領域ごとの行数集計 | meta_loc | 共通 | 配置から決まり、規約に依存しない |
| 分類(family) | meta_extract | 共通 | グループ名がそのまま分類になる(D-011) |
| 部品名実在 | meta_check | **グループ固有** | 名前らしさの判定を `dev-`・`flow-`・`meta-`・`ext-` のプレフィックスに固定していた。プレフィックスを持たないスキル名は照合されない |
| 状態整合(SKILL.md の状態名トークン) | meta_check | **グループ固有** | 状態名らしさを `-generated`・`-approved`・`-ing`・`-initialized` の語尾で判定していた。これは flow-sdd の命名規約 |
| レイヤー判定 | meta_extract | **グループ固有** | `dev-core`/`meta-core` を 0、`flow-` を 2、`ext-` を 3 とする割り当ては dev グループのレイヤー構造 |
| DESIGN テンプレートの節構成 | meta-doc | **グループ固有** | レイヤー構造・処理シーケンスの節が、レイヤーと状態機械を持つグループを前提にしていた |
| inject 実在 | meta_check | リポジトリ構成 | `ports/` の有無で決まり、グループ差ではない。ディレクトリが無ければ検査しない |
| 走査対象ディレクトリ(`.meta`・`ports`・`extensions`・`tests`) | meta_check・meta_loc | リポジトリ構成 | dev-skills のディレクトリ構成であり、グループ差ではない |

「inject 実在」と「走査対象ディレクトリ」のうち `ports`・`extensions` は、この 2 つが dev グループの機構であることから「グループ固有」へ再分類した(→ D-014 で更新)。

## 決定

- **グループ固有の前提は、グループ直下の `group.json` が宣言する**。宣言する項目は `part_prefixes`(部品名らしさの判定)・`state_suffixes`(状態名らしさの判定)・`layers`(レイヤーの割り当て。名前の glob で指定)とする。`meta-*` のスクリプト・テンプレートに特定のグループの前提を直接書かない。
- **宣言を持たないグループが既定で成立する**。宣言が無ければ、その判定を行わない(部品名を照合しない・状態名を判定しない)か、既定値を使う(レイヤーは部品 = 1)。新しいグループを足すときに宣言を書かなくても、誤検出も検査漏れも起きない状態を既定とする。
- **宣言は `skills/`・`agents/` の外に置く**。`install.py core` はグループ配下の `skills/`・`agents/` だけをコピーするため、宣言は配布されない。利用側は宣言を持たず、`meta-*` も配布しない(D-006)。
- **読めない宣言を既定へ黙って落とさない**。`meta-check` に「グループ規約」の検査項目を足し、壊れた宣言・型の違う宣言を error で報告する。報告した場合、その宣言に依存する検査(状態整合の語尾判定・部品名の実在)は実行しない。誤った前提のまま指摘を出すと、利用者は指摘の当否を判断できない。
- **部品名らしさの判定は、全グループの宣言の和で作る**。本文中のトークンがどのグループのものかは走査時に判別できないため、宣言されたプレフィックスをすべて集めて 1 つのパターンにする。
- **`writing`・`authoring` は `part_prefixes` を宣言しない**。単一スキルのグループでタイポ検出から得られる利得が、`japanese-` や `skill-` という一般的な語をパターンに加える誤検出のリスクに見合わない。宣言すれば検査対象になる仕組みだけを用意し、宣言は空にする。

## 却下した選択肢

- **port による知識注入**: `ports.md` §1 は port の共通ルートを利用側プロジェクトの `docs/dev/ports/` と定め、§4 は「port に置くのは、利用側がプロジェクト・案件ごとに編集・差し替えする拡張点のみ。配布物として固定の方法論・手順はスキル側が持つ」と規律する。グループの検査規約は dev-skills 内部の固定データであり、利用側の拡張点ではない。加えて port は LLM がスキル実行時に読む Markdown の知識で、決定論スクリプトが読む機械可読データではない。規約を Markdown 本文から機械抽出する形になり、規約の追加のたびに解析側も変わる。
  - 再検討条件: 利用側が自分のスキル群の検査規約を差し替える必要が生じた場合(`meta-*` を配布する判断とセットになる)。
- **meta の extension バンドル**: `extensions/` は `install.py ext` で利用側へ配布する Layer 3 の仕組みで、`extensions/README.md` は「本体(Layer 0〜2)はこれらの拡張の存在を前提にしない(なくても動く)」と規律する。配布しない `meta-*` の規約を配布機構の場所に置く非対称が生じ、さらに `meta-*` の検査が拡張の存在を前提にすると本体が拡張を知らない規律にも反する。
  - 再検討条件: グループ固有の検査が、宣言データでは表せない手続き(独自のスクリプトを走らせる等)を必要とするようになった場合。
- **規約を 1 つのファイル(リポジトリルートの `groups.json` 等)にまとめる**: グループの追加・削除のたびに離れた場所の索引を更新することになり、D-011 で「ディレクトリの形を唯一の正本にする」と決めた方針と食い違う。
- **宣言を必須にする**: 規約を書かないと検査が動かない状態は、グループを足す手間を増やすだけで安全側にならない。既定で成立させ、必要な群だけが宣言する形にした。

## 帰結

- `dev/group.json`(`part_prefixes`・`state_suffixes`・`layers`)と `.claude/group.json`(`part_prefixes`・`layers`)を追加した。`writing`・`authoring` は宣言を持たない。
- `meta_lib.py` に `group_config()`・`part_prefixes()`・`state_suffixes()`・`layer_of()`・`GroupConfigError` を追加した。定数 `GROUP_CONFIG`・`DEFAULT_LAYER` を置いた。
- `meta_check.py`: 固定の `PART_TOKEN_RE`・`STATE_LIKE_SUFFIX` を削除し、規約から組み立てる形にした。`check_group_configs()` を追加し、宣言が読めない場合は規約に依存する検査を実行しない。
- `meta_extract.py`: `classify()` のレイヤー判定を `meta_lib.layer_of()` に委ねた。全スキルの分類とレイヤーの割り当ては変更前と一致する。
- `design-template.md`: レイヤー構造の節を「複数のレイヤーを持つ分類はネストした subgraph、1 段しかない分類は 1 つのノード」に、処理シーケンスの節を「状態機械を持つスキルごと。無ければ節ごと省略」に改めた。
- `principles.md` に §6「グループ固有の規約は宣言で与える」を追加し、規律に「グループ固有の前提を `meta-*` のスクリプト・テンプレートに直接書かない」を加えた。
- `README.md`・`.meta/DESIGN.md`・`meta-check/SKILL.md` を宣言方式に合わせた。
- `tests/test_meta_lib.py` に規約の読み込み(既定・集約・glob 照合・エラー送出)のテストを、`tests/test_meta_check.py` に規約の検査と宣言を持たないグループの扱いのテストを、`tests/test_meta_extract.py` に規約からのレイヤー判定のテストを追加した。全 238 件が通る。
- 検証: 変更前の `meta_check.py --json` を基準に取り、変更後の実行で新規の指摘が 0 件であることを確認した。`meta_extract.py` の出力は、`meta-check` の description を更新したことによる role の文言の違いを除き、変更前と一致する(分類・レイヤー・状態機械・inject グラフ・エージェントはすべて同じ)。

## 再検討条件

宣言する項目が増えて `group.json` が肥大し、グループごとの差より宣言の管理コストが大きくなった場合。または、グループ固有の検査が宣言データでは表せない手続きを必要とし、スクリプトの差し替えが要るようになった場合(却下した extension 案を再検討する)。
