# D-006: 導入をハードコピーにし、meta-* を消費側へ配布しない(2026-07-15)

## 背景

`install.py` はコア(`.claude/skills/*`・`agents/*`)をシンボリックリンクで導入していた。しかし recognizer の実運用で 2 つの問題が判明した。

- **devcontainer でリンクが壊れる**: recognizer は devcontainer 内で開発し、ホスト側の配布ルートへのシンボリックリンクはコンテナ内で解決できない。実際には手動のハードコピーで運用され、`install.py` の想定と乖離していた。
- **meta-* が消費側へ配布される**: `install.py core` は `.claude/skills/*` を一括で導入するため、`meta-*`(dev-skills 自身の品質を保守する道具)も消費プロジェクトへ入る。消費側では意味を持たない(D-005 の「スキル群自体の品質」= メタレベルの道具で、dev-skills リポジトリでのみ使う)。

## 決定

- **導入はすべてハードコピーにする**。シンボリックリンクを使わない。devcontainer 等でホスト側パスが解決できない環境でも動き、利用側が導入物を自リポジトリに Git 管理できる。
- **`install.py core` は `meta-*` を配布対象から除外する**(`dev-*` / `flow-*` のみをコピー)。`meta-*` は dev-skills リポジトリを直接開いて使う。
- コピー方式では更新・削除の追跡に記録が要るため、**core にも lock(`.claude/dev-core.lock.json`)を導入**する。更新(再実行)は上書きコピーし、前回コピーして今回の配布元に無いスキル・エージェント(廃止分)を削除する。
- 拡張(ext)もリンクからコピーへ変える。コピーのため相対参照 `../dev-core/` が導入先の実体へ解決し、シンボリックリンク特有の「バンドルをディレクトリごとリンクすると壊れる」制約が消える。バンドルのスキル本体を丸ごとコピーする(`agents/`・`ports/`・`settings.snippet.json` は別経路)。

## 却下した選択肢

- **シンボリックリンクを維持し、devcontainer だけ別対応する**: 環境ごとの分岐が増え、リンク切れの検出・修復が利用側の負担になる。コピーに統一する方が単純で、Git 管理とも整合する。
- **リンクとコピーを `--copy` 等で選べるようにする**: 2 経路の保守コストに見合う利点がない。コピー一本にする。
- **meta-* も従来どおり配布する(scope 据え置き)**: 消費側で使わない道具を配る合理性がない。除外する。

## 帰結

- `install.py` を全面的にコピー方式へ書き換えた(core・ext・remove・status・ヘルパ)。core は `meta-*` を除外し、廃止スキルの掃除を行う。
- `README.md`・`extensions/README.md`・`principles.md` §5・`DESIGN.md` 概要をコピー方式・meta-* 非配布に追随させた。
- 検証: 合成 target への `core` コピー(実体・`meta-*` 除外・`.pyc` 非混入)、更新時の廃止スキル削除、`status`、`ext` のエラー経路を確認した。
- recognizer は本方針の先取り(手動コピー・meta-* 除外)で既に現行版へ移行済み(PR #8)。以後 `install.py core` で更新できる。

## 再検討条件

シンボリックリンクの自動追随(配布元更新の即時反映)が強く必要になり、かつ全消費環境でリンクが解決できると判明した場合。
