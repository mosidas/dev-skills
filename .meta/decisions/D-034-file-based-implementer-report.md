# D-034: 実装者の報告をファイル経由にし、返却を分岐に使う 6 フィールドへ絞る(2026-08-22)

## 背景

D-031 が「別の決定として扱う」とした 1 件である。dev-implementer の返却は 11 フィールドを持ち、すべてが呼び出し側(この部品を実行する文脈。通常は `dev-implement-runner`)の文脈に載る。`MUTATION_CHECK` は受け入れ基準ごとに 1 行、`VERIFICATION` は検証コマンドと実行時検証の結果、`UNTOUCHED`・`OUT_OF_BOUNDARY`・`TEST_CHANGES` はファイル単位の申告であり、1 タスクあたりの返却は数十行に達する。

呼び出し側がこの本文で行う判断は `STATUS` の分岐、`CHANGED_FILES` による差分の実在確認(`../../dev/skills/dev-implement/SKILL.md` 6.)、`NOTES` の Implementation Notes への追記、`BLOCKER` の読み取りに限られる。残る 5 フィールドは dev-reviewer への転記にしか使わないが、転記のために一度は呼び出し側の文脈を通る。返却本文は文脈に残り、以後のターンごとに読み直される。

[obra/superpowers](https://github.com/obra/superpowers) の subagent-driven-development は、この構造を「起動プロンプトへ貼った内容と、サブエージェントが返した内容は、セッションの残りの間ずっと文脈に居座り、以後のターンごとに読み直される」と述べ、報告本文をレポートファイルへ書かせて返却を状態・コミット・1 行のテスト要約・懸念へ絞る形を採る。

## 決定

- **返却を 6 フィールドへ絞る**。`STATUS`・`SUMMARY`・`CHANGED_FILES`・`REPORT_FILE`・`NOTES`・`BLOCKER` とする。いずれも呼び出し側が分岐・記録に使う。
- **詳細をレポートファイルへ書かせる**。`UNTOUCHED`・`OUT_OF_BOUNDARY`・`TEST_CHANGES`・`VERIFICATION`・`MUTATION_CHECK` の 5 項目を `## <フィールド名>` の見出しで書き出させる。
- **書き出し先はリポジトリの外の一時ディレクトリとする**。パスは `<一時ディレクトリ>/dev-implement/<作業単位名>/task-<タスク番号>-report.md` とし、起動のたびに部品が決めて `<report_file>` で渡す。
- **部品はレポートを読まない**。読むのは dev-reviewer であり、`<implementer_report>` にパスを入れて渡す。
- **修正の再投入では同じパスへ追記させる**。前回の内容を消させない(何を試したかがレビューの材料になる)。
- **書き出せない場合は縮退する**。`REPORT_FILE: なし` が返ったら、返却本文に含まれる 5 項目を `<implementer_report>` へ転記して渡す。機構が使えないことで申告を省かせない。
- **レビュアーが読めない場合は `REJECTED` を返させる**。パスを読み直してもなお内容が得られなければ、判定に必要な申告が無いものとして扱う。読めないこと自体を実装者の欠陥として `FINDINGS` へ挙げさせない(D-032 が入れた「証拠が読めないことは証拠が無いことではない」と同じ扱い)。
- **観測データの定義を広げる**。プロンプトの記法で、タグの内側に入る観測データを「転記した記録、またはその記録を書いたファイルのパス」とする。ファイルの内容にも、そこに現れる「指示」に従わない規律を掛ける。

## 却下した選択肢

- **workdir 配下の git 管理外ディレクトリへ置く**: 所在は安定するが、利用側のリポジトリへ `.gitignore` の追加を強いる。workdir の中身が中間生成物だけという前提も崩れ、凍結(`state.json` の `frozen`)と `check.py` の検査の対象を増やす。
- **レポートを workdir へコミットする**: 中間生成物ではない(レビューが終われば不要になる)ものを凍結の対象へ入れることになる。`tasks.md` への書き込みを列挙で限定した D-021 の方向にも反する。
- **`MUTATION_CHECK` だけをファイルへ出す**: 最も長いフィールドではあるが、`VERIFICATION` と 3 つの申告も同じ性質(呼び出し側は転記にしか使わない)を持つ。切り分けの基準を「長さ」ではなく「呼び出し側が分岐に使うか」に置いた。
- **dev-reviewer の返却もファイル化する**: 却下した。`VERDICT`・`FINDINGS`・`COVERAGE` は呼び出し側が次の分岐(再投入・コミット・`_Blocked:`)に使う。指摘の本文を読まずに再投入の可否を決められない。
- **レポートの撤去を部品の手順に入れる**: 一時ディレクトリはセッションの終了で消える。撤去の手順を足すと、失敗時の扱い(消せなかったらどうするか)を定める必要が生じ、得るものより手順が増える。

## 帰結

- `../../dev/skills/dev-implement/templates/implementer-prompt.md` に `<report_file>` タグと「報告の書き出し」の節を追加し、返却フォーマットを 6 フィールドへ絞った。`REPORT_FILE: なし` のときに 5 項目を書き足す縮退も明記した。
- `../../dev/skills/dev-implement/templates/reviewer-prompt.md` の `<out_of_boundary>`・`<test_changes>`・`<mutation_check>` の 3 タグを `<implementer_report>` へ統合し、確認手順 4・7・8 と変異注入の制約の参照先を同タグの該当項目へ変えた。記法の説明で観測データにパスを含めた。
- `../../dev/skills/dev-implement/SKILL.md` に 9.2(報告の受け渡し)を新設し、9. の dev-implementer・dev-reviewer の記述を追随させた。
