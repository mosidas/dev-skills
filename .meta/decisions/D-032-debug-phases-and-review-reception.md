# D-032: デバッグの手順を 4 段に定め、レビュー指摘の受け取りと TDD の規律を明文化する(2026-08-22)

## 背景

home/035 の調査(obra/superpowers)で採用と判断した要素のうち、品質側の 4 件を反映する。D-031 が消費量と実時間の削減を扱ったのに対し、本決定は検出力と規律の側を扱う。再調査の記録は `1_issues/dev-skills/020-apply-superpowers-findings/2026-08-21.md`(workspace 側の記録)にある。

現況の欠落は次のとおりである。

- `../../dev/agents/dev-debugger.md` と `../../dev/skills/dev-implement/templates/debugger-prompt.md` は「根本原因を特定して最小修正する」「有界(最大 2 ラウンド)」を定めるが、根本原因へ至る手順を持たない。進め方は 5 項目の箇条書きで、仮説を複数立てることを許し、層をまたぐ対象での証拠の集め方を持たない。
- 有界リトライ(`../../dev/skills/dev-implement/SKILL.md` 10.)は上限に達したタスクを `_Blocked:` でマークして次へ進む。上限への到達が「個別の修正では届かない」ことを示す信号である点は扱っていない。依存する後続タスクの有無も見ない。
- スキル群はレビューを出す側の規律(`../../dev/skills/dev-core/references/review-perspectives.md`)を持つが、受け取る側の規律を持たない。指摘の一部だけを理解したまま着手する、指摘を検証せず実装する、使われていない機能へ実装を足す、といった失敗に対する定めが無い。
- `../../dev/skills/dev-implement/SKILL.md` 7. の TDD は RED → GREEN → REFACTOR を手順として書くが、省略の言い分に対する反駁を持たない。同じ様式(言い分と反駁の表)は `../../dev/skills/dev-core/references/runtime-verification.md` §7 に既にあり、TDD へ適用されていないだけである。
- 実装者の `STATUS: READY_FOR_REVIEW` を、差分の実在を確かめずにレビューへ渡している。

## 決定

- **デバッグの進め方を 4 段に定める**。第 1 段(根本原因の調査)・第 2 段(パターンの照合)・第 3 段(仮説の単一化と最小検証)・第 4 段(打開策の提示)とし、前の段を終えてから次へ進む。第 1 段に、層をまたぐ対象では各層の境界で入出力を記録して壊れる層を特定してから調べること、誤った値を発生源まで遡ることを含める。第 3 段は仮説を 1 つに絞り、一度に動かす変数を 1 つに限る。
- **修正の試行が 3 回を超えた時点で構造を疑う**。「修正のたびに別の場所へ症状が出る」「修正に作り直しが要る」「共有状態・結合が次々に見つかる」のいずれかが当たるなら、外れた仮説ではなく構造の誤りとして扱い、4 回目の修正を提案せず `ESCALATION` に構造上の論点を挙げる。判定に使う試行回数は統括が持つため、起動プロンプトの `<situation>` へ渡す。
- **有界リトライの上限到達を構造の問題の兆候として扱う**。`_Blocked:` に根本原因と、繰り返しの失敗が示したパターン、dev-debugger の `ESCALATION` を書く。上限に達したタスクへ `_Depends:` で依存する後続タスクがある場合は、次タスクへ進まず停止して報告する。
- **レビュー指摘の受け取りの規律を dev-core の reference として新設する**(`review-response.md`)。着手の前提(不明な指摘が 1 件でもあれば全項目の着手を止める、指摘を主張として扱い対象コードで成立するかを確かめる、確かめられないものは明示する)、押し返す条件(既存の振る舞いを壊す・使用箇所が 0 件の機能への実装要求・バージョンで成立しない・承認済みの決定と矛盾する)、処理の順序、応答の形(賛辞と謝辞で応じない)を定める。実装者に掛かる部分は `implementer-prompt.md` の `<review_findings>` の節が安全エコーとして持つ。
- **TDD の反駁表を 7. に置く**。6 行の言い分と反駁を、`runtime-verification.md` §7 と同じ様式で書く。実装者のプロンプトには、守らせたい 2 点(失敗を実行で観測すること、テストより先に書いた実装コードを削除してから書き直すこと)だけを入れる。
- **実装者の返却を受けた直後に差分の実在を確認する**。`git status --porcelain` と `git diff --stat` で変更が実在し、申告の `CHANGED_FILES` と一致することを確かめてからレビューへ渡す。空または不一致ならレビューを起動せず `NEEDS_CONTEXT` として扱い直す。

## 却下した選択肢

- **レビュー指摘の受け取りを新規の部品(スキル)にする**: 配布の単位が増える一方、この規律だけを目的に起動する場面が無い。指摘を受け取るのは既存の役割(再投入される実装者・最終検証 NO-GO を受ける統括・CI 失敗を直す統括)であり、条件付き参照の reference で足りる。
- **`runtime-verification.md` の適用範囲を完了主張の全般へ広げる**: 同ファイルは実行時検証の正本であり、範囲を広げると名称と内容が乖離する。superpowers の verification-before-completion のうち dev-skills に欠けていたのは「サブエージェントの成功報告を根拠にせず版管理の差分で確認する」の 1 点であり、これは実装ループの手順として 6. に置くのが適切である。残りの項目(テスト・ビルド・リントの結果を実行してから主張する)は同ファイルと `dev-implement` の既存の規定が既に覆う。
- **TDD の反駁表を implementer-prompt へ入れる**: 実装者は毎タスク起動されるため、6 行の表を全タスクで再送することになる。規律の本体は SKILL.md に置き、プロンプトには実装者の手が止まる 2 点だけを書いた。
- **debugger-prompt に試行回数の判定を持たせる**: 回数を数えられるのは統括であり、クリーンな文脈で起動される dev-debugger は自分が何回目かを知らない。`<situation>` に渡す形にした。
- **4 段の順序を返却フィールドで強制する**(段ごとの結果を必須フィールドにする): 返却が長くなり、統括の文脈に段の作業内容が載る。D-031 の方向(統括の文脈に判断以外を載せない)に反する。手順として書き、`EVIDENCE` に観測事実を求める現行の形を維持した。

## 帰結

- `../../dev/skills/dev-implement/templates/debugger-prompt.md` の「進め方」を 4 段構成へ書き換え、`<situation>` に修正の試行回数を追加した。
- `../../dev/skills/dev-implement/SKILL.md` 10. に上限到達の扱い(構造の問題の兆候・依存タスクがある場合の停止)を追加した。
- `../../dev/skills/dev-core/references/review-response.md` を新設し、`dev-implement` の条件付き参照へ追加した。
- `../../dev/skills/dev-implement/templates/implementer-prompt.md` に `<review_findings>` タグと 3 点の要約を追加し、進め方 1(RED)へ失敗の観測と先行実装の削除を追加した。
- `../../dev/skills/dev-implement/SKILL.md` 7. に TDD の反駁表を追加し、6.(イテレーション規律)のサイクルへ差分の実在確認を挿入した。9. の dev-implementer の記述に再投入時の `<review_findings>` の受け渡しを追加した。

## 再検討条件

netdiver の次の作業単位で、dev-debugger の返却が第 1 段の観測を欠いたまま打開策へ飛ぶ事例が観測された場合(手順の記述では効かないため、段ごとの結果を返却フィールドへ移す)。レビュー指摘の受け取りで `NEEDS_CONTEXT` が過剰に返り、往復が増えた場合(不明の判定基準が厳しすぎるため、着手を止める範囲を「関係しうる項目」に狭める)。または差分の実在確認が 1 度も不一致を検出しない状態が複数 unit 続いた場合(検査の価値が無いため外す)。
