# D-023: 4 観点の棚卸しで維持と決めた構成要素(2026-08-10)

## 背景

[Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps) は「ハーネスの各構成要素は、モデルが単独ではできないことについての仮定を符号化している」と述べ、モデルが強くなるたびに構成要素を再評価して削ることを求める。

この観点で構造(用途グループの分割・レイヤーの段数・`meta-*` の 4 スキル構成・`flow-sdd` の状態数)と、既存の判断のうち今回の評価対象と重なるものを棚卸しした(`../notes/2026-08-10-engineering-lenses.md` 5.・6.)。削ると決めたのは `dev-author` 1 件(D-022)で、他は維持と判断した。

維持は変更が無いため帰結を持たないが、根拠を残さないと次の棚卸しで同じ検討を繰り返す。D-008 と同じ扱いで、判断の記録だけを残す。

## 決定

次を維持する。各行の根拠と再検討条件を対にする。

採録の基準は「今回の棚卸しで削減の候補として個別に検討した要素」とする。構造の要素(用途グループ・レイヤー・`meta-*` の構成・状態機械)と、既存の判断のうち今回の 4 観点と重なるもの(D-008・配布範囲・スクリプト・進捗ファイル)が該当する。調査ノートで「維持する」と結論した項目のうち、記述の性質に関するもの(P-5 成功基準と自由度・P-6 description の規約・C-1 の採用済み 3 手段・L-1 の反復単位と終了条件と評価者の分離)は、削減の候補として検討していないため本表に採らない。

| 構成要素 | 維持の根拠 | 再検討条件 |
| -------- | ---------- | ---------- |
| 用途グループの分割(dev / writing / authoring) | 利用側が必要な群だけを導入するという配布の要求(D-012)に対応する。モデルの能力とは独立で、能力の向上で消えない | グループが 1 つに減った場合、または `install.py core` のグループ指定が使われた記録が無いまま利用側が 3 件以上に増えた場合 |
| オニオン型レイヤー 0〜3 | 依存規律違反の観測実績は無く、符号化した仮定の真偽は本評価では判定できない。ただしレイヤーは検査以外にも、`install.py` の配布境界と `../../dev/extensions/README.md` 3.2 の拡張の依存規律を記述する語彙として使われており、削ると両方の記述先が無くなる | 拡張の仕組みを廃止し、配布境界を別の語彙で記述する場合 |
| `meta-*` の 4 スキル構成 | `meta-check`・`meta-review` は read-only、`meta-doc` は `../DESIGN.md` を全上書きする。副作用の有無が異なる操作を 1 つの description に束ねると、read-only を意図した依頼で上書きが走る | `meta-doc` の生成を read-only の出力(差分の提示)に変え、副作用の非対称が消えた場合 |
| `flow-sdd` の 7 状態 | 削ると再開時の分岐が「状態」1 つではなく「状態と `approvals` の組」になり、D-020 の再開手順の固定化と逆行する | 承認を状態から分離した別の再開手順を採る場合 |
| 差し戻し遷移(飛び越しを定義しない) | 1 段ずつ戻る形は、戻り先で何を作り直すかを状態が示す | 1 つの作業単位で、中間状態を経由するだけの差し戻しが 2 回以上発生した場合 |
| モデル自動起動を使う(D-008) | 再検討条件(意図しない commit / push・本番操作の発生、description の近接衝突の実測)を満たす観測が無い。`trigger_check.py` の近接衝突検出は 0 件 | D-008 の再検討条件に同じ |
| `permissions.allow`・サンドボックス設定を配布しない | 利用側のリスク許容度と CI 構成で決まる判断を、配布側が上書きしない。`permissions.deny` は配布側の規律を足すだけなので既存どおり許す | 複数の利用側プロジェクトで同一の allow 設定が書かれていることを確認した場合(雛形の提示を検討する。配線は行わない) |
| 決定論スクリプトの現状(改修しない) | [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) の要点(操作の統合・名前空間・レスポンス量の制限・次の行動が分かるエラー)に対応が付いている | 既定出力(`--json` なし)が 1 回の実行で 100 行を超え、要約の追加が要ると判断された場合 |
| 進捗ファイルを追加しない | 進捗の正本が `state.json`・`tasks.md`・git と重複し、正本が割れる(D-017) | D-017 の再検討条件に同じ |

## 却下した選択肢

- **`spec-approved`・`tasks-approved` を削り、承認は `approvals` フラグだけで表す**: 状態数は 7 から 5 に減るが、再開時に「次に何をするか」を決めるのに状態と `approvals` の 2 つを読む必要が生じる。D-020 で Step 0 を固定手順にする方針と逆行する。
- **`meta-check` と `meta-review` を 1 スキルに束ねる**: どちらも read-only で副作用の非対称は無いが、決定論的検査と意味レビューは実行コストが 2 桁違い(スクリプト実行とサブエージェント起動)、機械検査だけを回したい場面で意味レビューまで走る。
- **`writing`・`authoring` を `dev` グループへ統合する**: 両者は dev の機構(port・拡張バンドル・状態機械)を使わず、統合するとグループ単位の導入(D-012)ができなくなる。
- **レイヤー 3 の枠組みを廃止する**: D-018 で hook 拡張を置いたため、実体を持つ。

## 帰結

構成を変更していない。判断の記録だけを残す(D-008 と同じ扱い)。
