# D-026: 自走する工程をサブエージェントへ委譲し、対話を伴う工程は統括に残す(2026-08-13)

## 背景

netdiver の unit #2 を flow-sdd で実装した実運用で、実装フェーズを `--resume` で継続すると会話全体が毎回送り直され、文脈が 1M の窓の 55〜69% を占めた(`1_issues/netdiver/007-mvp-core-loop/2026-08-12.md`。workspace 側の記録)。工程の作業内容(タスクごとの実装レポート・検証の出力・調査の本文)が統括セッションに積み上がることが原因である。

工程をサブエージェントへ委譲すれば作業内容は委譲先の文脈に閉じ、統括には構造化結果だけが返る。ただし [Create custom subagents](https://code.claude.com/docs/en/sub-agents) は、`AskUserQuestion` を「`tools` に列挙してもすべてのサブエージェントから除去される」ツールの 1 つとして挙げる。委譲先はユーザーに質問できない。

各工程がユーザーとの対話に依存する度合いを調べた。

| 工程 | 対話の位置づけ |
| ---- | -------------- |
| roadmap の生成 | 経路判定の提示と承認。目的が確定しないときの質問 |
| 仕様(dev-spec) | Step 2 が質問駆動(1〜3 問ずつ)、Step 3 が契約の壁打ちの往復。**対話が工程の本体** |
| タスク分解(dev-decompose) | 内蔵ゲートの `QUESTIONS` のみ(例外時) |
| 実装(dev-implement) | ワークフロー内では `tasks.md` が既にあるため発生しない |

同ドキュメントは、サブエージェントの入れ子を「既定でメイン会話の 3 層下まで」と定める。統括 → 工程ランナー → 役割エージェント(dev-implementer 等)はこの範囲に収まる。

## 決定

- **自走する工程だけを委譲する**。タスク分解フェーズと実装フェーズをサブエージェントへ委譲し、仕様フェーズと経路判定・承認は統括セッションが実行する。roadmap の生成は分解の分析だけを委譲し、提示と承認は統括に残す。
- **起動プロンプトは workdir・作業単位名・実行する SKILL.md のパスに限る**。工程の手順・生成規則・判定基準はファイルにあり、プロンプトへ転記しない。仕様・タスクの内容も転記せず、委譲先が workdir から読む。
- **委譲先は質問の代わりに停止して返す**。部品の SKILL.md が質問を指示する箇所で、委譲先は構造化結果の `OPEN_QUESTIONS` に論点を挙げて停止する。統括がユーザーに諮り、回答を添えて再委譲する。
- **状態遷移は委譲先へ渡さない**。`init` / `set-state` / `approve` は統括セッションだけが実行する。D-000 §3.3(部品は composition の状態を進めてはならない)と `flow-sdd/SKILL.md` 6. をそのまま維持する。承認ゲートは人間の応答を要し、委譲先はユーザーと対話できないため、ゲートは統括に置くしかない。
- **セッション管理はサブエージェントの起動そのものとする**。`--resume` 等のハーネスのセッション機構には依存しない。コアが使ってよい実行機構をスキルとエージェント定義に限る D-000 §3.9 に収まり、flow-sdd を Layer 2 に置いたまま実装できる。
- **unit 分解を部品として切り出す**。`dev-roadmap`(Layer 1)を新設し、`roadmap.md` の生成を担わせる。**経路判定は composition に残す**。経路判定はワークフローの駆動の仕方を決める判断であり、unit 分解は成果物の生成であるためである(`flow-sdd/SKILL.md` 冒頭が定める composition の担当範囲を変えない)。
- **配布するエージェントにモデルを固定してよい。ただし family alias に限る**。同ドキュメントによれば、frontmatter の `model` が利用側の `availableModels` で許可されない場合、Claude Code はエラーにせず代替する(family alias なら許可される最新版へ、それ以外は継承モデルへ)。加えて利用側は `CLAUDE_CODE_SUBAGENT_MODEL` で全サブエージェントのモデルを一括で上書きできる。固定しても利用側の環境で動作が止まらず、利用側に上書きの手段がある。完全なモデル ID(`claude-opus-5` 等)は版を固定するため使わない。
- **役割エージェントに `effort` を指定する**。frontmatter の `effort`(`low` / `medium` / `high` / `xhigh` / `max`)がセッションの effort を上書きする。工程の性質に応じて割り当てる。

| エージェント | model | effort | 理由 |
| ------------ | ----- | ------ | ---- |
| dev-explorer | haiku | low | read-only の抽出と要約 |
| dev-implement-runner | opus | medium | ループの制御。実装の判断は入れ子の dev-implementer が担う |
| dev-implementer | opus | high | 1 タスクの TDD 実装 |
| dev-reviewer | opus | high | 合格基準への適合の判定 |
| dev-decompose-runner | opus | high | File Structure Plan と分解の設計 |
| dev-debugger | opus | xhigh | 根本原因の切り分け |
| dev-roadmap-planner | opus | xhigh | 最上流の分解。後続の全工程の区切りを決める(→ D-028 で更新) |

## 却下した選択肢

- **全工程を委譲し、質問を中継するプロトコルを新設する**: 委譲先が質問を構造化して返し、統括がユーザーに問い、回答を添えて再委譲する形。dev-spec の壁打ちは往復ごとに再委譲になり、サブエージェントは毎回新しい文脈で起動するため往復の履歴を毎回渡す必要がある。文脈削減という目的が壁打ちでは達成されず、保守すべきプロトコルだけが残る。
- **工程ランナーを 1 つの汎用エージェントにまとめる**: `effort` は frontmatter でしか指定できず(起動ごとの上書きはモデルにしかない)、工程ごとに effort を変えられない。
- **委譲先に状態遷移を任せる**: D-000 §3.3 の改訂を伴う。承認ゲートは委譲先から通過できないため、遷移だけを渡すと承認と遷移が別の場所に分かれ、状態機械の一貫性を追いにくくなる。
- **経路判定も `dev-roadmap` へ移す**: 経路判定は「どの工程を、どの状態機械で駆動するか」を決める判断であり、composition の担当範囲(`flow-sdd/SKILL.md` 冒頭)そのものである。部品へ移すと部品が composition の駆動を決めることになり、D-000 §3.3 と同じ逆流を招く。
- **エージェントのモデルを `inherit` にして固定しない**: 役割ごとの費用と能力の割り当て(調査は haiku、判定は opus)が失われる。固定しても利用側で動作が止まらないことを確認したため、固定の不利益は無い。
- **`skills` frontmatter で部品の SKILL.md をプリロードする**: 起動プロンプトを短くできるが、プリロードは工程の手順を起動時に固定するため、SKILL.md の条件付き参照(条件に当たるときだけ読む設計)と噛み合わない。委譲先にパスを渡してファイルから読ませる形を選んだ。

## D-007 との関係

D-007 は多段オーケストレーションの禁止対象を「委譲先をエージェントが決めること」に限定し、段数そのものを禁止していない。本決定の委譲は次の理由でこの禁止に当たらない。

- 委譲の構造は実行前にファイルで読める。統括が起動する相手は `flow-sdd/SKILL.md` 5.0 の表が、工程ランナーが起動する相手は各部品の SKILL.md が定める。エージェントが委譲先を選ばない。
- 合流点は統括が一元管理する。工程ランナーは構造化結果を返して終わり、次の分岐は統括が決める。
- 承認ゲートを跨がない。委譲は 1 つのゲートの内側に閉じる区間(Step 2 の生成まで、Step 3 の実装まで)に限り、ゲートの通過は統括が行う。

D-007 が定める「スクリプト実行機構に依存する実装は拡張(Layer 3)に置く」にも当たらない。委譲の手段はエージェント定義であり、D-000 §3.9 がコアに許す実行機構の範囲内である。

## 帰結

- `../../dev/skills/dev-roadmap/`(SKILL.md・templates/roadmap-template.md)を新設した。
- `../../dev/agents/` に 3 定義を追加した。`dev-roadmap-planner`・`dev-decompose-runner`・`dev-implement-runner`。いずれも「起動プロンプトが指定する SKILL.md を読んで実行する」形とし、手順を持たない。
- 既存の 4 定義(dev-explorer・dev-implementer・dev-reviewer・dev-debugger)に `effort` を追加した。`model` は変更していない。
- `../../dev/skills/flow-sdd/SKILL.md`: frontmatter の description に dev-roadmap を加え、2.(経路判定と unit 分解の担当の区別)・5.0(工程の委譲)・Step R・Step 2・Step 3・6.(規律)を更新した。
- `../../.claude/skills/meta-core/trigger-cases.json` に dev-roadmap の検査ケース 4 件(肯定 2・否定 2)を追加した。否定例は dev-decompose・dev-spec の依頼文を流用し、3 者の取り違えを検出する形にした。
- `dev-roadmap` の description は当初 dev-spec と類似度 0.306(閾値 0.3)で近接警告が出たため、「仕様」の語を減らし「切り分け・順序・依存・範囲」の語彙へ寄せて解消した。

## 再検討条件

委譲した工程で、統括セッションが構造化結果だけでは次の分岐を決められない事例が観測された場合(返却項目の追加、または委譲範囲の見直しを検討する)。またはサブエージェントがユーザーと対話できるようになった場合(仕様フェーズの委譲を再検討する)。または利用側の環境で入れ子の上限が 2 層以下に設定され、工程ランナーが役割エージェントを起動できない事例が生じた場合。
