# 再開の問い

作業を始める前か再開する前に本人の最近の作業の文脈を組み直す手順を定める。返すのは今の状態と次の一手の短いまとめである。

文脈は 2 つの記録にある。1 つは会話の記録とタスクの記録である。何をして何が決まったかがここにある。もう 1 つは共有の記録である。同じコードの周りで起きたことがここにある。例は利用者が報告し続ける症状・出してから戻した修正・本番で出続けるエラーである。不具合の続く機能の経緯は大半が共有の記録にある。会話の記録だけから組み直さない。

## 1. 振り分け

- 1 つのタスクを中断した箇所から続けるときは develop 11. に従う。本書は使わない。
- 本人が状態(パス・ブランチ・変更)を既に示したときはそれを使う。記録を調べない。
- 本人の作業の要約を文書にする依頼は本書の対象外である。write-doc が扱う。
- 本書が扱うのは作業の前に複数の会話とタスクをまたいで文脈を読み込むことである。

## 2. 範囲の固定

調べる前に範囲を固定する。本人に 1 行で書き返す。範囲の誤りは調べる前なら直せる。

- 期間: 「最近」は具体的な範囲にする。既定は直近 7 日である。
- 話題: 本人が名前を出していればその話題に絞る。
- 作業場所: 既定は今の作業ディレクトリのプロジェクトである。別のプロジェクトの記録は頼まれたときだけ読む。守るものは別の案件の非公開の文脈である。
- 「全部」と言われたら全件を調べる。件数を縮めるときは書き返す行にその件数を書く。

## 3. 入力

入力は 4 つである。

| 入力 | 取り方 | 使う CLI |
| :-- | :-- | :-- |
| backlog | `backlog search "<話題>" --type task --plain` で探す。`backlog task list --status "In Progress" --plain` で進行中を拾う。`backlog task <id> --plain` で状態と Implementation Notes を読む | すべて |
| gh | `gh pr list --state all --author "@me" --search "<話題>" --json number,title,state,headRefName,mergedAt,url` | すべて |
| git | `git log --since="<期間>" --oneline --all`・`git branch --list`・`git status`・`git stash list` | すべて |
| 会話の記録 | `~/.claude/projects/<slug>/*.jsonl` | Claude Code のみ |

- 会話の記録の `<slug>` は retro 3. の memory の段落と同じ規則で求める。
- 直下の `*.jsonl` が 1 つの会話であり 1 行が 1 件のメッセージである。サブエージェントの記録は `<セッション id>/subagents/` にあり本体の会話と分かれている。
- 会話の記録は統括が読む。サブエージェントは作業ディレクトリの外のファイルを読めないものとして扱う(SKILL.md 3.)。
- Codex CLI・Antigravity CLI では会話の記録の置き場が違う。backlog・gh・git だけを入力にする。

## 4. 会話の記録

Claude Code だけで行う。統括が読む。記録は大きい。1 件の会話の記録は 1 万行を超えることがあり全体を読むと調べ終わる前に統括のコンテキストが埋まる。そのため次の順で絞ってから読む。

- 会話の記録は更新日時の順(`ls -t`)で並べる。ファイル名(UUID)の順は日時と関係しない。
- 話題の語で grep してから一致した会話の該当箇所だけを読む。
- 今の会話を除く。評価とテストの会話も除く。
- 統括が直接読む。該当が多いときは新しい順に絞る。絞った件数は 2. の書き返す行に書く。一致した箇所の前後だけを読む。守るものは統括のコンテキストである。

会話ごとに次を控える。各項目にセッション id(ファイル名)を書く。一致しない会話は「該当なし」と 1 行で書く。

- 話題:
- 本人の目的:
- 決まったこと:
- 未完のスレッド:
- つまずきと訂正:
- 成果物: <PR・タスク・ブランチ>

## 5. 共有の記録

話題が機能・ファイル・サブシステム・領域・不具合を名指すときは調べる。これは既定であり統括の裁量ではない。「自分の X の作業」という言い方でも省かない。省いてよいのは対象の無い活動の振り返り(今週何をしたか)だけである。

- `why.md` 3. の情報源の割り当てと 4. の調査役のブリーフの雛形を使う。雛形の問いの節は「なぜこの形か」でなく次の問いにする。今の状態はどうか。何を試して定着しなかったか。利用者がまだ報告している症状は何か。雛形の「コードの足場」は再開の問いでは空になることがある。分かる項目だけ埋める。
- `why.md` 3. の合成役 1 体の箇条は使わない。調査役を 1 体起動して所見は統括がまとめる。
- 調査役は 4. の会話の記録を読む前に起動する。統括が記録を読む間に並行して進む。
- 何も返さなかった結果も所見である。
- ほかの 6 分類は `why.md` 3. のとおり欠落として出力の「問題」の節に書く。

## 6. 現状の照合

所見に出た PR・ブランチ・タスクを実物で確かめる。記録より実物を正とする。記録は書かれた時点の状態であり今の状態ではない。

```sh
gh pr view <番号> --json state,mergedAt,headRefName,url
git branch --list '<ブランチ>'
git log --oneline main..<ブランチ>
backlog task <id> --plain
```

答えがエージェントの実際の操作(実行したツール・読んだファイル・出たエラー)で決まるときは会話の記録の該当箇所を全文で読む。要約された記録は操作を省いていることがある。

## 7. 出力の形

要約・スレッド・問題・次の一手の順で書く。詳細は下に回すか削る。次の形を写して埋める。

```markdown
**要約**

- <この作業が何で全体としてどこまで進んだか。5 点以内>

**スレッド**

- <状態タグ> <スレッドの名前と状態を 1 行で>(<出典>)

**問題**

- <繰り返す問題。利用者が報告し続ける症状と出してから戻した修正を含める。5 点以内>

**次の一手**

<最も役に立つ次の行動を 1 つ具体的に書く>
```

- スレッドの各行に respond 3.5 の状態タグを 1 つ付ける。タグの無い行を残さない。
- 隣の機能とタスクはこの作業を止めているときだけ入れる。
- 1 画面に収まらないときはスレッドを削る前に詳しい内容を削る。
- 出典は会話の所見ならセッション id を書く。共有の記録の所見ならその位置(PR 番号・課題の id・URL)を書く。
- 公開する場所(PR・issue)に写すときは個人情報と非公開の文脈を除く。
