# 設計の原則

コードの形(データ構造・型・モジュールの境界)を確定するときの原則と設計の赤信号を定める。planner が方針と設計を書くときと reviewer が簡潔さを点検するときに読む。

## 1. 適用範囲

- 状態を持つロジック・分岐の多いコード・型と関数のシグネチャ・モジュールの境界・並行する処理の共有を設計するときに適用する。
- ponytail のはしごと規則を先に適用する。本書は作ると判断した構造の形を確定する。作るかどうかの判断は変えない。
- 言語に固有の型の書き方は扱わない。

## 2. 原則

### 2.1. ドメインを構造で表す

状態を持つロジックを書くときに適用する。分岐の多いコードと同じ形の仮定(項目の有無・値の組み合わせ)を複数のファイルで繰り返すコードにも適用する。

- ドメインの規則は散らばった条件分岐でなくデータ構造で表す。ドメインに合う構造は不正な状態を表現できなくする。分岐も減る。構造は書く時点で選択する。後から構造を直す変更はリファクタに見えて後回しにされる。
- 構造の例は次のとおりである。
  - 散らばったブール値・段階・ライフサイクルの判定の代わりに状態機械
  - 緩い引数や繰り返す形の仮定の代わりに型付きのモデル
  - 複数のファイルに広がる分岐の代わりに表・登録簿・直和型
  - 場当たりの状態の変更の代わりに reducer かコマンドとイベントのモデル
  - アクセスの経路に合わせたキュー・キャッシュ・索引・木・正規化した集合
- モジュールは 1 つのドメインの知識ごとに分ける。処理の順(読み込み・検証・変換・保存)では分けない。実行の順は持ち主を表さないためである。
- 合う構造が見つからないときはコードが許してはならない状態とデータの読まれ方を書き出す。その 2 つを過不足なく表す構造を探す。
- 構造を押し付けない。今の形が明確で局所的で大きくなる見込みが無ければそのままのコードを保つ。分岐・重複した規則・不正な状態・ライフサイクルの誤りのどれも減らさずに間接の層を加える構造は作らない。

判定の問いは「この構造で分岐・重複した規則・不正な状態のどれかが減るか」である。減らないなら作らない。

兆候は 3 つある。

- 新しい機能が既存の if/else の連鎖を 1 本伸ばす。
- 別のブール値と同期させる必要のあるブール値が増える。
- 段階の名前のモジュール(読み込み・検証・保存)が同じドメインの規則をそれぞれ持つ。

### 2.2. 型で守る

型と関数のシグネチャを設計するときに適用する。静的型付きの言語で書くときも同じである。ありえない状態・取り違えたプリミティブ・扱っていない場合を実行時の処理でなく型検査が拒否する形にする。特別な場合を処理する分岐を増やさない。その場合が型の上で生じない形を優先する。

- 意味の違うプリミティブには別の型を与える。ユーザー ID と注文 ID は中身が同じ文字列でも取り違えられないようにする。値は作るときに 1 回だけ検証する。その後は型を信頼する。同じプリミティブの型で意味の違う 2 つの引数を受け取る関数ではそれぞれに別の型を与える。
- 外部のデータはパースするまで型の無いものとして扱う。RPC の応答・JSON・プロセス間のメッセージ・CLI の引数・設定ファイル・環境変数・DB の行が当たる。境界ごとにパースの関数を 1 つ持つ。その関数が型付きのモデルに変換する。検証の場所は ponytail の規則(検証と防御を信頼境界に集める)に従う。
- 形を定義するファイル(proto・OpenAPI と GraphQL のスキーマ・DB のマイグレーション・デザイントークンのファイル)があるときは型をそこから導出する。同じ形の型を別に手で書かない。手で書いた型は定義の変更に追従しないためである。

判定の問いは「この誤りは実行時まで残るか」である。残るなら型検査が拒否する形を探す。

兆候は 3 つある。

- 同じ値の妥当性の確認が複数の関数で繰り返される。
- 型の強制(キャスト・`any`・実際には常に値が入るオプショナルの項目)で型検査を通している。
- 定義のファイルと同じ形を手で書いた型がある。

### 2.3. 境界の内側の構造

検証・エラー処理・フレームワークへの接続を書くときに適用する。

- 境界での検証と内側での再検証の禁止は ponytail の規則に従う。本節は境界の内側のコードの形を扱う。
- 業務のロジックはフレームワークに依存しない純粋関数にする。フレームワークに接続する外殻は入力を受け取って純粋関数を呼んで結果を返すだけの薄い層にする。ロジックをフレームワークなしでテストできるためである。生のバイト列から型付きの状態へのパースと構造化した状態からの文字列の組み立てが純粋関数の例である。
- 境界の公開面にはドメインの概念を出す。通信・保存・フレームワークの型(ワイヤの型・DB のスキーマ・フレームワークのオブジェクト)を公開面から再エクスポートしない。汎用の仕組みは内側に持つ。特定の用途に限る方針は境界の側に持つ。

判定の問いは「外殻が呼ぶだけの純粋関数にできるか」と「この型は境界の内側の表現か」である。前者が成り立つなら純粋関数に抜き出す。後者が成り立つなら公開面に出さない。

兆候は 3 つある。

- 業務の規則がリクエストのハンドラやフレームワークのコールバックの中にある。
- フレームワークを起動しないと業務の規則をテストできない。
- 呼び出し側が通信や保存の型を import している。

### 2.4. 直列化の前に共有をなくす

並行するアクター(プロセス・スレッド・ジョブ・ワーカー)が同じファイル・ブランチ・キー・状態に書きうるときに適用する。

- 先に共有をなくす。アクターが 1 つの対象を共有する必要があるかを問う。それぞれが独立した事実を書くだけなら共有は不要である。アクターごとに専有の書き込み対象(ファイル・キー・ブランチ・状態のディレクトリ)を与える。結果は読む側か報告の段階で合わせる。2 つのワーカーが 1 つの `state.json` にそれぞれの項目を書くのは共有の変更のままである。`indexer-state.json` と `metrics-state.json` に分ければ共有は無い。
- 1 つの書き込み対象が本当の不変条件であるときだけ構造で直列化する。手段はロックファイル・逐次の段階・単一の書き手・アトミックな比較と交換である。指示や慣習は並行の制御にならない。
- 「ロックが必要だ」という判断は設計を見直す兆候として扱う。既定の答えにしない。意図したグローバルロックは ponytail の `shortcut:` のコメントで記録する。

判定の問いは「別のアクターがこの値を同時に変えたら何が起こるか」である。答えが「何も起こらない」でなければ分ける。

兆候は 3 つある。

- 複数のアクターが同じファイルを読み書きする。
- 同じブランチやキーに複数の書き手がいる。
- 同時に実行したときだけ再現する不具合がある。

## 3. 設計の赤信号

関数境界を越える設計の案は確定する前に次の 8 項目に照らして当たる項目があれば案を直すか退ける。次にそのコードを変える読み手は開いたファイルだけを見て最も近い例を写して型検査を通る最短の経路を取るエージェントだと仮定する。1 つのファイルから見て正しい変更がリポジトリ全体でも正しくなる案を選択する。条件を満たす案が複数あるときは公開面が小さくその裏で多くを引き受ける案を選択する。

### 3.1. 浅いモジュール

公開面が大きいのに裏で引き受ける処理が少ない。

- 深さは公開面の大きさに対する裏の機能と方針の量で測る。深いモジュールは理解を複数の層に分散させる深い呼び出しの連鎖とは別のものである。
- 兆候は 1 つの操作のために呼び出し側が複数のメソッドを組み合わせること・公開のオプションが内部の段階や実装の選択を露出すること・インターフェースを覚えても実装を読む必要が残ることである。

### 3.2. 情報の漏れ

複数のモジュールが同じ内部の判断(表現・方針・プロトコルの細部)に依存していてその判断を変えるときに複数の箇所を同時に編集する必要がある。

- 通信の型の再エクスポートもこれに当たる。
- 外部のデータはインターフェースの裏でドメインの型にパースする。保存のスキーマ・フレームワークのオブジェクト・プロトコルの細部は非公開にする(2.3)。

### 3.3. 実行順の分割

モジュールを持つ知識でなく実行の順で分けている。

- 読み込み・検証・変換・保存の段階に分けると 1 つの表現と不変条件が複数の境界で繰り返される。
- コードは知識と持ち主でまとめる(2.1)。違う時点で動くメソッドでも同じ判断を守るなら 1 つのモジュールに入れる。

### 3.4. 素通しのメソッド

引数をそのまま別のメソッドへ渡すだけである。

- 渡す先は同じ形のメソッドである。層を増やすだけで複雑さを隠さない。
- 取り除く。または操作を完結できるモジュールに責任を移す。
- 転送の層を残すのは方針・変換・別の抽象を加えるときだけである。既存の素通しの層を畳むかは ponytail の規則(変更の範囲の素通しの層)に従う。

### 3.5. 状態の持ち主が複数

複数のモジュールが同じ状態を書くかそれぞれ写しを持つ。

- 1 つの書き手を編集するエージェントには他の書き手が見えないので書き手ごとの規則が食い違っていく。
- 状態ごとに持ち主を 1 つにする。他のモジュールは状態を読むか持ち主に変更を依頼する。

### 3.6. 同じ仕事に 2 つのやり方

同じ仕事を 2 通り以上の方法でできる。

- エージェントは最初に見つけた方法を写すのでどの方法にも呼び出し元が増え続ける。
- 方法を 1 つにする。他の方法の呼び出し元を移して同じ変更で削除する(ponytail の規則の内部 API の置き換え)。

### 3.7. 外から import できる内部

モジュールの外から内部を import できる。

- エージェントは型検査を通る最短の経路を取るので内部を直接 import してしまい内部がインターフェースの一部になる。
- 外からの import がビルドで失敗するように内部を到達できなくする。

### 3.8. 手で同期する一覧

同じ項目の一覧が 2 か所以上にあって項目を加えるたびにすべての一覧を編集する必要がある。

- 1 つの一覧だけを見たエージェントはその一覧だけを更新する。
- 一覧を 1 つにして他の一覧を導出する。導出できないときは一覧が食い違ったらビルドが失敗するようにする。
