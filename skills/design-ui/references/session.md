# UI モックの作成

本ファイルは、Web の新しい画面とフォームを実装する前に、UI モックを本人と往復して作る工程を定める。UI モックは、出力先のディレクトリにある brief.md・mock.html・frames.html と、往復ごとの PNG からなる。ダーク表示を持つ製品では、frames-dark.html も加わる。PRD があれば PRD と組で build に渡し、無ければ単独で develop に渡す。

対象は Web の新しい画面とフォームである。次のものは対象外とする。

- ネイティブアプリの画面。HTML で OS の部品を再現できないためである。
- 既存の画面の変更。実装そのものが見本になるためである。ただし、ユーザーが明示して求めたときは作る。

## 1. 工程

| 工程 | 担当 | 成果 |
| :-- | :-- | :-- |
| 聞く | 統括(ユーザーとの対話) | 保存先、書き始めた brief.md、洗い出した状態 |
| 往復する | 統括(ユーザーとの対話) | 往復ごとの mock.html・PNG・文言の表と、brief の往復の記録 |
| 確かめて終える | 統括(ユーザーとの対話) | 本人が合意した brief と、次の一手の提示 |

## 2. 聞く

- 聞き始める前に保存先を聞き、雛形 `brief.md` を保存先へコピーする。既定の保存先は、backlog を初期化したリポジトリのルートからの `docs/ui-mock/<slug>/` である。ユーザーは別の場所を指定できる。
- 答えは聞くたびに brief.md へ書く。進み具合を会話でなく brief に持つため、中断しても brief から再開できる。この考えは specify 2. と同じである。
- 1 問ずつ聞く。PRD・対象リポジトリ・既存のデザインシステムで答えが出る問いは、先に調べる。
- 準備として、`../SKILL.md` 3. の 1〜3 を行う。題材を決め、トークン案を書き、`anti-ai.md` と照合する。既存のトークンがあれば、それを使う。
- 品質(簡易 / プロダクト)を brief の品質の行に書く。PRD があれば対応する要求の品質を写し、無ければ本人に聞く。決め方は `../../develop/references/requirements.md` 3. に従う。
- 状態を洗い出して brief の「状態ごとの表示」に書く。対象は、`checklist.md` 2. の画面と操作の状態のうち該当するものである。待機・読み込み中または送信中・成功・失敗(直せる/直せない)・空・タイムアウト・オフラインがこれに当たる。
- brief の品質がプロダクトのときは、recover 2.1 の失敗も状態に入れる。入力の不備、外部への呼び出しの失敗とタイムアウト、内部の例外、上限の超過がこれに当たる。
- PRD があれば、その要求の受け入れ条件にある「失敗時:」の箇条を状態に写す。

## 3. 往復する

### 3.1. 1 往復で出すもの

- 1 往復で統括が出すものは次の 4 つである。
  - 案 1 つ。mock.html、PNG、文言の表からなる。文言の表の列は `| 状態 | 見出し | 本文 | 操作 |` で、planner の「利用者に見せる文言」と同じである。文言は `text.md` に従い、8. のとおり敬体で書く。
  - 前回からの差分。「指摘 → 変えた箇所」の形で書き、1 往復目は「初回」とする。
  - 質問 1 つ。
  - 往復の番号(`n/3`)。
- 案を 1 つにするのは、本人の注意を比較に割かせず、指摘を 1 案に集めるためである。
- 前例の無い操作と感触で決まる判断では統括が本人に見せる前に根本の違う 2〜3 案を作業ツリーの外で試作して比べる(`../../develop/references/kinds.md` 5.)。本人には選定した 1 案を出す。比べた案と捨てた理由は往復の記録(前回からの差分)に書く。
- 質問を 1 つにするのは、specify 2. と同じく、答えによって次に聞くべきことが変わるためである。
- 質問には、未決の点のうち不確かさが最も大きいものを選択する。未決の点が無くなったら「この案で確定してよいか」を聞く。
- 往復のたびに、brief の「往復の記録」に 1 行を追加し、状態の行を `往復中 n/3` にする。

### 3.2. 見せ方

- 本人に見せる前に、統括が PNG を 1 回だけ点検する(`../SKILL.md` 3. の 5)。見るのは、崩れ、横のはみ出し、`text.md` 8. に反する文言、ダミー以外の値である。欠陥を見つけたら、まとめて直し、撮り直してから示す。
- Claude Code では、統括が Read で PNG を開いて点検する。画像を表示できない CLI では、PNG のパスだけを示す。
- 撮れなかったときは、PNG の代わりに mock.html のパスを示し、本人がブラウザーで開く。
- 次の形で示す。

```text
往復 <n>/3
画像: <ライトの PNG の絶対パス>
画像(ダーク): <ダークの PNG の絶対パス>(ダーク表示が無い製品では、この行を書かない)
差分: <指摘> → <変えた箇所>(1 往復目は「初回」)
文言:
| 状態 | 見出し | 本文 | 操作 |
| :-- | :-- | :-- | :-- |
| <状態> | <見出し> | <本文> | <操作> |
質問: <質問 1 つ>
```

### 3.3. モックの作り方

- mock.html は単一の HTML にし、CSS はインラインで書く。トークンは `:root` の CSS 変数で定義する。ダーク表示を持つ製品では、`@media (prefers-color-scheme: dark)` で変数を切り替える。
- JavaScript を使わない。状態は 1 ページに縦に並べ、それぞれに状態名の注記を付ける。状態名は brief の「状態ごとの表示」と同じ語にする。
- 外部の資源(CDN・Web フォント・画像の URL)を読み込まない。書体は brief に名前を書き、モックでは端末の書体で代える。
- 値はダミーにする(例: 「例 太郎」、`example.com`、`0000`)。`example.com` は RFC 2606 が例示用に予約したドメインである。個人情報、秘密、本番の識別子を書かない。出力先はリポジトリにコミットされるためである。
- 決定は brief に書く。mock.html は brief を図にしたものであり、両者が食い違えば brief に従う。

### 3.4. 撮影

出力先の frames.html に、mock.html を表示する iframe を幅 1280 と幅 390 の 2 枚並べる。高さは全状態が入る値にする。ダーク表示を持つ製品では、`<style>` の先頭に `:root{color-scheme:dark}` を加えた frames-dark.html も作る。iframe ごとに付けると、iframe の間とウィンドウの右端が白く残るためである。

```html
<!doctype html>
<meta charset="utf-8">
<style>body{margin:0;display:flex;gap:16px;align-items:flex-start}iframe{border:0}</style>
<iframe src="mock.html" width="1280" height="<高さ>"></iframe>
<iframe src="mock.html" width="390" height="<高さ>"></iframe>
```

撮影には draw-diagram の `render.py` の `screenshot()` を使う。次のコマンドで撮る。ウィンドウの幅は、iframe の幅と間隔の和(1686)以上にする。ウィンドウの高さは、iframe の高さと同じにする。frames-dark.html は、出力の名前を `round-<n>-dark.png` にして同じコマンドで撮る。

```sh
CHROME_BIN="$(command -v google-chrome || command -v chromium || echo '/Applications/Google Chrome.app/Contents/MacOS/Google Chrome')" python3 -c 'import sys; sys.path.insert(0, sys.argv[1]); from render import screenshot; sys.exit("\n".join(screenshot(sys.argv[2], sys.argv[3], int(sys.argv[4]), int(sys.argv[5]))) or None)' <design-ui のディレクトリ>/../draw-diagram/scripts <出力先>/frames.html <出力先>/round-<n>-light.png 1700 <高さ>
```

- `<design-ui のディレクトリ>` は、design-ui の SKILL.md があるディレクトリである。
- 撮れたら終了コードは 0 になる。撮れなかったら、終了コード 1 と理由を標準エラー出力に出す。
- Claude Code のサンドボックス内では Chrome が起動できないため、サンドボックス外で実行する。
- PNG の下端で状態が切れていたら、高さを上げて撮り直す。
- 撮れないとき(Chrome が無い、起動できない、60 秒で打ち切られた)は、mock.html と文言の表で往復を続ける。往復の記録には「撮影なし(<理由>)」と書く。

### 3.5. 往復の上限

- 往復は 3 回までとする。上限を 3 回にする理由は develop 6. と同じで、3 回で合意しないときは問いの立て方か範囲に無理がある。
- 3 回目で合意しなければ、4 回目の案は作らない。合意した点と未合意の点を一覧にして本人に示し、未合意の点を本人に決めてもらう。
- 本人が決めた点は brief の該当する節に書く。本人が決めない点は brief の未決事項に書く。

## 4. 確かめて終える

次をすべて満たしたら終える。

- brief の全節が埋まり、雛形のコメントが残っていない。
- 「状態ごとの表示」と「文言」の状態名が一致している。
- 合意した往復の PNG があるか、撮影なしの理由が往復の記録に書いてある。
- brief・mock.html にダミー以外の値が無い。
- 本人が合意した。または、3 往復を終えて、未合意の点を本人が決めたか未決事項に書いた。

終えたら、brief の状態の行を `合意 <日付>` か `打ち切り <日付>` にする。本人が途中で打ち切ったら、未決の点を未決事項に書いて `打ち切り <日付>` で終える。

## 5. 次の一手

最後に、brief のパスと次の一手を本人に示す。次の一手は、PRD の有無と終わり方で変わる。

| 場合 | 次の一手 |
| :-- | :-- |
| PRD があるとき | PRD の 4.(制約と決定事項)の `UI モック:` の行に brief のパスを書き、本人に確かめる。そのうえで「build で PRD をタスクに分解する」と示す |
| PRD が無いとき | 「develop で、要件の UI モックの行にこの brief のパスを書いて実装する」と示す |
| 打ち切ったとき | 「未決事項を解消してから」と示す |

## 6. 他スキルとの関係

- specify・build・develop・planner が UI モックを使う。
- 状態の洗い出しは recover 2.1 と `checklist.md` 2. に従う。
- 撮影は draw-diagram の `render.py` を使う。
- 往復での指摘は、retro の「本人の指摘」に含めない。
