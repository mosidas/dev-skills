# UI 設計規範

## 1. 適用範囲

- 適用範囲は Web・iOS・Android・デスクトップの画面・コンポーネント・ページの設計と実装。
- 作図は対象外。ポンチ絵や構造図は draw-diagram が扱う。グラフ・チャートも扱わない。
- HTML で配布する説明資料(図・表・切り替えの UI を持つ 1 ページの文書)は write-page が扱う。write-page が本スキルから参照する範囲は、write-page の SKILL.md 4. の表にある(閲読モード・スケール・階層と強調・構造は情報・anti-ai.md・checklist.md・session.md の往復の形)。
- 優先順位は次のとおりとする。上位が下位に優先する。
  1. ユーザーの言葉。配色・書体・見た目を名指しで指定されたら、本スキルの既定より従う。
  2. プロジェクトに既にあるデザインシステム・トークン・コンポーネント集。
  3. OS の規約(Apple Human Interface Guidelines・Material Design 3)。ネイティブアプリを設計・実装するときに従う。
  4. 本スキルの規範。

## 2. モードの選択

実装の前に、次の 4 つのモードから 1 つを選択する。基準は画面の役割である。製品の種類では選ばない。同じツールでも、ランディングページは説得、資料集のトップページは閲読になる。

| モード | 訪問者の成功 | 例 |
| :-- | :-- | :-- |
| 説得 | 判断して行動する | LP、料金表、キャンペーン |
| 操作 | 作業を完了する | ダッシュボード、設定画面、フォーム |
| 閲読 | 内容を理解する | ドキュメント、記事、変更履歴 |
| 体験 | 作品そのものに没入する | ポートフォリオ、ギャラリー |

操作モードと閲読モードでは、一覧性・一貫性・既定の挙動を表現より優先する。説得モードと体験モードでは、逆に題材固有の表現を優先してよい。

## 3. 工程

1. 題材と画面の仕事を決める。何を扱う画面か、誰が何のために見るかを、依頼から具体化する。依頼に実体が無ければ、こちらで具体案を 1 つ立て、ユーザーに確認する。
2. トークン案を書く。色 4〜6 色(名前と HSL 値)、書体 2 役割(見出しと本文。同じ書体を 2 役割に使ってもよい)、間隔スケール(本ファイル 4. のスケールから選ぶ)を短く書く。
3. トークン案と画面構成を「どの類似案件でも出る既定か」に照らして書き直す。`references/anti-ai.md` の一覧と一致する箇所を洗い出し、その箇所だけを描き直す。ユーザーがその見た目を名指しで求めていたら描き直さない。
4. 実装する。文言の配置・分量・日本語の文体は `references/text.md` に、アクセシビリティ・フォーカス・フォーム・モーション・状態など実装の品質床(共通と Web 固有の節に分かれる)は `references/checklist.md` に、それぞれ従う。
5. 有限回の検証で止める。1 巡のスクリーンショット確認 → 見つかった欠陥の一括修正 → 確認の 1 巡で終える。際限のない自己レビューを続けない。

新しい Web の画面・フォームを実装の前に本人と決めるときは、1〜3 と文言を `references/session.md` の工程で決める。UI モックがあれば、4. 以降はその brief.md に従う。

## 4. スケール

値は次の段階から選ぶ。新しい値を都度作らない。

- 間隔: `4 8 12 16 24 32 48 64 96 128 192 256 384 512 640 768`(px)。小さい側の値では隣接する値どうしの差を約 25% 以上空ける。
- 文字サイズ: `12 14 16 18 20 24 30 36 48 60 72`(px または rem。em は使わない)。
- 太さ: 本文は 400 か 500、強調は 600 か 700 の 2 段階だけを使う。400 未満は使わない。
- 色: グレー 8〜10 階調、主色 5〜10 階調、用途別のアクセント(破壊的操作の赤、警告の黄、肯定の緑など)ごとに 5〜10 階調。HSL で定義し、実行時に `lighten()` 等で生成しない。
- 影: 5 段階(ボタン程度の控えめな影からモーダルの強い影まで)を z 軸の位置で選ぶ。見た目の好みで選ばない。

## 5. 階層と強調

- 階層は大きさでなく太さと色で作る。大きさだけに頼ると、主要な要素が大きすぎ、副次的な要素が小さすぎる結果になる。
- 目立たせたい要素は 1 か所に絞る。それ以外は削る。周囲の要素は色と太さを抑え、題材の理解に貢献しない飾りをすべて取り除く。
- 主要な操作は塗り、副次的な操作は輪郭線か低コントラストの背景、三次的な操作はリンク調にする。1 画面の主要な操作は原則 1 つにする。

## 6. 構造は情報

カード・番号(01/02/03)・見出し上のラベルは構造を示す装置である。意味を運ぶときだけに使う。番号付けは、内容が本当に手順や時系列の連なりであるときに限って使い、そうでない一覧に付けた番号や見出しのないラベルは、内容の理解を助けない。

## 8. 他スキルとの関係

- コード自体の最小化は ponytail に従う。依存の選定・抽象化の要否も含む。
- 図・ポンチ絵を作るときは draw-diagram に従う。UI モックの撮影には draw-diagram の `render.py` を使う。
- UI モックは、specify の PRD と組で build に渡すか、単独で develop に渡す。planner は UI モックの決定を決め直さない。
- 画面内の日本語の文言は `references/text.md` 8. に従う。語の選び方と文の組み立ては `../write-doc/references/sentence.md` の 1.〜5. に従い(漢語基調の項を除く)、同 6.〜8. と `../write-doc/references/format/` は適用しない。文体は text.md 8. を優先する。
- 見た目を変えずに実装を置き換える移行は develop の `../develop/references/kinds.md` 6. の移行の 1 つであり `references/migration.md` がその基準(旧版の出力を状態ごとに撮った画像)と完了条件(画像差分 0)を定める。
- 失敗の状態の洗い出しと、失敗時にシステムがすること(タイムアウト・再試行・二重送信の防止・エラーページ)は、品質がプロダクトのとき recover に従う。本スキルは各状態の見せ方と文言を定める。
