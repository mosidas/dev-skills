# コードの可観測性の規範

## 1. 適用範囲

- develop の要件で品質がプロダクトのコード、またはユーザーが運用性・監視を求めたコードに適用する。
- ponytail と同時に適用する。プロジェクトに既存のロガー・計装があればそれを使い、新しい監視基盤やベンダーの SDK を導入しない。
- 2.2・2.3・2.5 は、要求やメッセージを受けて常駐するプロセス(サーバー・ワーカー)に適用する。CLI・ライブラリ・一回きり・定期実行のバッチには 2.1・2.4・2.6・2.7 だけを適用する。
- タイムアウト・リトライ・冪等は recover が扱う。

## 2. 規則

### 2.1 構造化ログ

- 1 つのイベントを、キーと値の組で 1 行に出す。形式は既存ロガーの形式(JSON など)に合わせる。
- メッセージは固定の文字列にし、変化する値は属性に入れる。例: メッセージは「注文を確定した」、属性は `order.id`。
- レベルは次の基準で選ぶ。
  - error: 人による対応を必要とする。
  - warn: 異常が発生したが、自動で回復した。
  - info: 業務上の節目(要求の受付・完了など)。
  - debug: 開発時にだけ使い、本番では出さない。

### 2.2 相関 ID

- 入口(HTTP 要求・キューのメッセージ)で相関 ID を受け取り、無ければ生成する。W3C Trace Context の `traceparent` ヘッダーがあれば、それを優先して使う。
- 相関 ID を、ログの属性と下流への呼び出しに載せる。ロガーのコンテキストに 1 度設定し、個々のログ呼び出しで渡し直さない。
- エラー応答に載せるかは secure のエラー応答の規則に従う。

### 2.3 メトリクス

- 入口ごとに、golden signals のうちレイテンシ・トラフィック・エラーを取る。
- 飽和はサービス単位で、もっとも制約の強い資源(接続プールの使用数・キューの長さ・メモリなど)を 1 つ以上取る。
- レイテンシはヒストグラムで取り、成功と失敗を属性(`error.type` など)で分ける。失敗の速い応答が混ざると、成功のレイテンシが実際より短く見えるためである。
- メトリクスと属性の名前は、既存のメトリクスに命名の慣習があればそれに合わせ、無ければ OpenTelemetry のセマンティック規約に従う(例: `http.server.request.duration`)。
- カーディナリティの高い値(ユーザー ID・URL のパス変数など)を属性にしない。パスはルートのテンプレート(`/users/{id}`)で載せる。

### 2.4 トレース

- フレームワークやクライアントライブラリの自動計装があれば、それを有効にする。手で書くスパンは、自動計装で足りない箇所に限る。
- 外部への呼び出し(HTTP・DB・キュー)ごとにスパンを張る。失敗したスパンにはエラーの状態を設定する。

### 2.5 ヘルスチェック

- liveness と readiness を別のエンドポイントに分ける。
- liveness はプロセスが応答できるかだけを返し、依存先を確かめない。依存先の障害で再起動が連鎖するのを防ぐためである。
- readiness は、要求の処理に必要な依存先(DB など)へ接続できるかを確かめる。

### 2.6 エラーの分類

- エラーを 2 つの軸で分類し、ログの属性に載せる。利用者起因かシステム起因か、一時的か恒久的かである。例: OpenTelemetry の `error.type` に例外の種別、独自の属性 `app.error.origin` に `client` か `system`、`app.error.transient` に真偽値を載せる。独自の属性には、OpenTelemetry の名前と衝突しない接頭辞を付ける。
- 例外を捕捉したら、その場で処理するか、呼び出し元へ送出する。捕捉したまま何も残さずに処理を続けない。
- 同じエラーのログは、境界(要求の入口・ジョブの最上位など)で 1 回だけ出す。途中の層は文脈を付けて送出し、ログには出さない。

### 2.7 完了条件

- 計画のステップの完了条件に、正常時と失敗時のそれぞれで、どのログ・メトリクスに何が出るかを書く。
- 運用者がそのログとメトリクスを見て、正常か、何がどこで失敗したかを判断できることを完了の基準にする。
- 2.3 を適用しない対象(CLI・ライブラリ・バッチ)では、完了条件にログだけを書けばよい。

## 3. 他スキルとの関係

- 秘密・個人情報をログに出さない規則は secure(`skills/secure/SKILL.md`)に従う。
- 計装の書き方(既存の部品を優先し、差分を最小にする)は ponytail に従う。
- 計装を省いた箇所には、ponytail 3. の `shortcut:` コメントと同じ形で理由を残す(例: `# shortcut: メトリクスなし, 利用者が社外に広がったら計装する`)。
