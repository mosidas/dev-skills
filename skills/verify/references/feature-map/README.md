# Tasks の機能マップ

このディレクトリは Tasks の利用者から見た振る舞いを検証するための正本である。操作の前に本書を読む。次に該当する機能ファイルを開く。

## 共通の前提

- `docs/verify/README.md` の起動の手順で Tasks を `http://127.0.0.1:5173` に起動する。データのディレクトリは使い捨てにする。
- 並行する実行が状態を共有しないように `TASKS_DATA_DIR=docs/verify/runs/$RUN_ID/data` を設定する。
- 証拠の保存先として `EVIDENCE_DIR=docs/verify/runs/$RUN_ID/evidence` を設定する。後始末はこのディレクトリを削除しない。
- 初期データとして `週次の報告` と `請求書の送付` の 2 件のタスクを投入する。`請求書の送付` は完了済みにする。
- `docs/verify/scripts/drive` と `tasks` の CLI を `PATH` に通す。
- `drive doctor` を実行して期待する URL・データのディレクトリ・ビルドのリビジョンが出ることを確かめる。
- この検証の実行で起動していないインスタンスを操作しない。

## 操作の約束

- 前提に別の指定が無ければ各手順を共通の前提の状態から始める。
- 要素は CSS のセレクターと DOM の位置でなく ARIA のロールとアクセシブルな名前で指す。
- コマンドは書かれたとおりに実行する。引用符で囲んだ名前とフラグを変えない。
- ブラウザーの操作は `drive browser` で行う。
- 端末の操作は `drive cli -- <コマンド>` で行う。
- データを変えた後は初期データに戻す。後始末で証拠を削除しない。

## 証拠と省略の報告

- 利用者の操作とその結果の状態を取る。最後の画面だけでは足りない。
- 画面の証拠は ARIA のスナップショットとスクリーンショットの 2 つである。スクリーンショットにはアプリの名前を写す。
- CLI の証拠はコマンド・標準出力・標準エラー・終了コードである。
- データを変える操作の証拠には保存した値を読み取りだけの別の画面で読み戻した結果を含める。
- 証拠には機能の ID と使った入口を書く。
- 届かなかった経路は試したコマンドと満たせなかった前提を書いて報告する。
- 別の経路で通したことを届かなかった入口の合格として報告しない。

## 機能ファイルの形

各機能ファイルは H1 の題と利用者から見た振る舞いの 1 段落で始める。続けて次の 4 つの H2 を持つ。順は変えない。

1. `サブ機能`: 短い ID と 1 行の振る舞いを並べる。
2. `利用者からの到達`: 利用者の入口をすべて並べる。
3. `操作`: `前提:` で始める。利用者の操作・正確なコマンド・観測する結果を組にしたラベル付きの箇条を続ける。
4. `落とし穴`: 検証の時間を無駄にするか結果を無効にする罠を並べる。

実装の詳細を書かない。書くのは利用者の経路・安定した手掛かり・必要な状態・コマンド・観測できる証拠だけである。
