# 検証の手引きの生成と保守

本スキルは統括が読む。検証の手引きは対象リポジトリの `docs/verify/` にある文書と補助スクリプトである。実アプリの起動から利用者と同じ経路での操作と証拠の取得を経て後始末までの手順を持つ。手引きの読み手は次のエージェントである。そのエージェントはアプリを一度も見ないまま作業の途中で手引きを開く。だから手引きには説明でなくそのまま実行できるコマンドと観測する結果を書く。

## 1. 適用範囲

- 対象リポジトリに `docs/verify/README.md` と `docs/verify/features/` の両方があれば保守(4.)を行う。どちらかが無ければ生成(2.)を行う。
- 手引きの構成は次のとおりである。`docs/verify/` の外に手引きを作らない。

  ```text
  docs/verify/
  ├── README.md        # 起動・健康診断・操作・証拠・後始末・補助スクリプトの 6 節
  ├── .gitignore       # runs/ を git の管理から外す
  ├── features/
  │   ├── README.md    # 機能マップの索引と共通の約束
  │   └── <機能>.md    # 機能ごとに 1 ファイル
  ├── scripts/         # 補助スクリプト(必要なときだけ)
  └── runs/            # 実行ごとのデータと証拠(コミットしない)
  ```

- 対象リポジトリへの書き込みは develop の工程で行う。生成と保守の修正はどちらも develop のタスク・ブランチ・計画・実装と点検・gate-reviewer の点検・PR を通す。統括は要件の完了条件に本スキルの節を書く(例: 「verify 2.2 の 6 節がある」)。planner と implementer は完了条件が引く本スキル(`dev-skills:verify`)を読み込む。2.1 と保守の手順 1〜6 は統括が develop の前に行う。これらの工程は git が追跡するファイルを書き換えない。書いてよいのは git が追跡しないもの(`docs/verify/runs/` のデータと証拠・ビルドの出力・作業ツリーの外の記録)だけである。
- 製品のコードを変えない。手引きと製品の挙動が食い違ったときに製品を直すのは別のタスクである。
- 手引きの操作の道具は対象リポジトリの中のコマンドとスクリプトにする。MCP の道具(ブラウザーの拡張など)に頼らない。手引きを使う implementer と gate-reviewer はサブエージェントである。サブエージェントは MCP の道具を使えないものとして扱う。

## 2. 生成

### 2.1. リポジトリから調べる

次の 5 項目をリポジトリから調べる。本人に聞くのはコードと文書から観測できないこと(本番だけにある認証情報など)に限る。

| 項目 | 調べること | 主な情報源 |
| :-- | :-- | :-- |
| 触る面 | 利用者が触るもの(Web の画面・CLI・TUI・デスクトップアプリ・API・モバイルアプリ・ライブラリ)。複数あれば主な面を 1 つ定めて残りを記録する | README・ルーティング・コマンドの定義・エントリポイント |
| 起動 | README とパッケージのスクリプトに書かれた起動のコマンドを先に使う。ローカルで起動するコマンド・ポート・環境変数・初期データ・認証 | パッケージのスクリプト・Makefile・README の手順 |
| 操作 | エージェントがプログラムでアプリを操作する方法。既存の仕組み(E2E テスト・PTY の補助・curl で呼べるエンドポイント・デバッグ用のポート)を先に使う。無ければ汎用の方法にする。Web と Electron はブラウザーの CDP・CLI と TUI は tmux か PTY・サービスは HTTP である | E2E テスト・テストの補助・開発用の設定 |
| 観測 | 証拠として取れるもの(スクリーンショット・端末の記録・応答の本文・ログ・終了コード・DB の状態) | ログの設定と出力先・DB のスキーマ |
| 隔離 | 2 つのインスタンスを同時に動かせるか(ポート・データのディレクトリ・プロファイル) | 設定の読み込み・データの保存先 |

- 同時に動かせないときは手引きにそう書く。共有のインスタンスを 2 つの作業で操作して本人のセッションを汚すより操作を断るほうがよい。
- 今のリポジトリが手順どおりにビルドか起動できないときは手引きを書く前に原因を正確に報告する。起動しない土台で書いた手引きは誤った手順を教える。直すのは別の develop のタスクである。
- 検証に関係しない欠けたファイル(API が配信しない静的ファイルのディレクトリ・設定の見本)が起動を妨げるときは手引きの起動の手順で作ってよい。作ったものは検証の足場と明記して後始末で削除する。

### 2.2. README の 6 節

`docs/verify/README.md` に次の 6 節をこの順に書く。各節は 2.1 で調べた事実だけで書く。プレースホルダーを残さない。冒頭の段落にはアプリの名前・触る面・手引きを開く場面を書く。

1. 起動: 検証のためにアプリを起動するコマンドと準備ができたことの見分け方(ログの行・プロンプト)を書く。空のデータのディレクトリから使える状態まで進める。データのディレクトリを指定できるアプリでは `docs/verify/runs/<実行の ID>/data/` を使う。移行と初期データの投入も含める。準備ができたとは使える状態になったことである。プロセスが応答するだけでは足りない。DB の死活監視は初期化のスクリプトが走っている間にも通ることがある。停止の手順も書く。短時間で終わる CLI と TUI には常駐するサーバーが無い。その起動はバイナリのビルドか依存の導入を 1 回行うことである。操作ごとに隔離した PTY か tmux のセッションを始める。
2. 健康診断: 「このインスタンスを操作してよいか」に答える読み取りだけの確認を 1 つ書く。確かめるのはプロセスの稼働・期待する版とビルド・ポートを持つプロセスが自分の起動したものであること・認証の有効性である。何かがおかしく見えたら最初にこれを実行する。
3. 操作: 道具の使い方をこのリポジトリの実際のセレクターとコマンドで書く。例を書かない。座標とタブの順でなく安定した手掛かり(ARIA のラベル・データ属性・プロンプトの文字列・ルートのパス)を使う。
4. 証拠: 証明のために取るものと保存先を書く。基準は 3. の証拠の基準を写す。保存先は `docs/verify/runs/<実行の ID>/evidence/` にする。作業ディレクトリの外にしない。手引きを使うサブエージェントは作業ディレクトリの外のファイルを使えないものとして扱うためである。`runs/` は `docs/verify/.gitignore` で git の管理から外す。
5. 後始末: 検証で作ったインスタンスを止める手順を書く。プロセス名で止めない。止めるのは自分が起動したもの(記録した PID・コンテナの名前)だけである。後始末はインスタンスと一時的な状態を削除する。証拠は削除しない。証拠は 4. の保存先に残る。
6. 補助スクリプト: 手引きが持つスクリプト(`docs/verify/scripts/` の中)の一覧と呼び方を書く。スクリプトには実行権限を付ける。呼び方を本文に書かないスクリプトは読み手が中身を読み解く必要がある。それは補助にならない。補助スクリプトが無ければ「なし」と書く。

### 2.3. 機能マップ

`docs/verify/features/README.md` と利用者が触る機能ごとに 1 ファイルを作る。最初は主な 3〜5 機能でよい。機能はルート・コマンド・メニュー・文書から拾う。形は `references/feature-map/` の例に従う。

- 索引(`features/README.md`)には共通の前提・操作の約束・証拠と省略の報告・機能ファイルの形・機能の一覧を書く。
- 機能ファイルは H1 の題と利用者から見た振る舞いの 1 段落で始める。続けて次の 4 つの H2 をこの順に書く。

  | H2 | 書くこと |
  | :-- | :-- |
  | `サブ機能` | 短い ID と 1 行の振る舞い |
  | `利用者からの到達` | 利用者が機能に入る入口のすべて |
  | `操作` | 冒頭に `前提:` の箇条。続けて利用者の操作・実行するコマンド・観測する結果を組にしたラベル付きの箇条 |
  | `落とし穴` | 検証の時間を無駄にするか結果を無効にする罠 |

- 機能マップには実装の詳細を書かない。書くのは利用者の経路・安定した手掛かり・必要な状態・コマンド・観測できる証拠である。
- 初期データに道のりの前提が欠けているときは道のりを失敗として報告する。理由はその機能の `落とし穴` に書く。通すために道のりを弱めない。
- 機能マップは対象リポジトリで保守する検証の正本である。マップが複数の入口を挙げているのに都合のよい 1 つだけを通した証明は不完全である。

### 2.4. 1 度動かして証明する

生成した手引きを最初から最後まで 1 回実行する。起動・健康診断・機能マップの 1 機能の操作・証拠の取得・後始末の順である。1 機能で足りる。残りの機能を後の実行で通すためにマップがある。

- 後始末の後に証拠が保存先に残っていることを確かめる。証拠を削除する後始末はこの工程で不合格である。
- 失敗したら直して実行し直す。失敗した回のたびに手引きの後始末を実行する。失敗した試行がプロセスとポートを残さないためである。
- 一度も実行していない手引きは下書きである。成果に数えない。
- 本物の対象の代わり(新しい VM の代わりのコンテナ・リモートの代わりのローカルの環境)で証明することがある。そのときは代わりの環境だけが行う準備の手順をすべて書き出す。それらの手順は本物の対象で実行するまで未検証として報告する。
- 証明の実行は develop の implementer の検証である。統括は検収で証拠の保存先を開いて確かめる(develop 6.)。証明の develop は Claude Code で進める。Codex CLI・Antigravity CLI ではアプリを起動しないためである(4.5)。

## 3. 証拠の基準

手引きの証拠の節(2.2 の 4.)は次の基準に従う。

- 利用者と同じ経路を通す。内部の setter とテスト専用のエンドポイントを使わない。
- 操作とその結果の状態の両方を取る。最後の画面だけでは足りない。
- 見えるものに加えて副作用(書いたファイル・挿入した行・送ったメッセージ)を確かめる。
- モックを使うのは本番でも外部のシステムを境界で切り離している箇所に限る。
- 安全な経路が dry-run かテスト用のモードのときは何を省くかを観測で確かめる(ファイル・ネットワーク・git の参照)。名前を信じない。dry-run でもネットワークに出るものとブラウザーを開くものがある。
- 証拠には機能の ID と使った入口を書く。届かなかった入口は試したコマンドと満たせなかった前提を書いて報告する。別の入口で通したことを届かなかった入口の合格に数えない。

## 4. 保守

機能マップはアプリが変わった時点で古くなる。保守は手引きとマップを今のアプリに合わせる定期の点検である。確かさの単位は機能である。文の 1 つずつではない。すべての機能ファイルをソースから読む。すべての機能をライブで動かす。箇条を 1 つずつ端末で確かめることまではしない。

### 4.1. 結果

結果は次の 3 つのどれかにする。どれにしたかを報告に書く。

| 結果 | 条件 | 成果 |
| :-- | :-- | :-- |
| 変更なし | すべての機能をソースとライブで確かめて直すものが無い | 報告だけ。ブランチと PR を作らない |
| 1 PR | 記録した修正案(手引き・補助スクリプト・マップ)がある | develop の工程で出す 1 つの PR。修正の証明は develop の完了条件にする(4.3 の 7) |
| 停止 | 確かめ終えられなかったか修正案を develop で証明できなかった | 報告だけ。止めた原因を正確に書く |

### 4.2. 書き換えの範囲

書き換えるのは `docs/verify/` の中だけである。製品のコードは変えない。マップに書いた振る舞いをアプリがもうしないときは記述のずれか製品の後退のどちらかである。記述のずれならマップを直す。製品の後退なら報告する。文書で覆い隠さない。

### 4.3. 手順

1. 対象を特定する。対象リポジトリの `docs/verify/README.md` と `docs/verify/features/` を探す。無ければ止まって生成(2.)を示す。対象を作り出さない。
2. 索引を点検する。`features/README.md` を読む。同じディレクトリの機能ファイルを一覧する。索引に無いファイル・ファイルの無い項目・重複・行き先の無いリンクを修正案として記録する。軽い作業である。一覧を生成するスクリプトは作らない。
3. 機能ごとの調査役を並列に起動する。機能ファイル 1 つに調査役 1 体を割り当てて 1 つのメッセージで起動する(4.5)。調査役は「この機能は利用者から見てどう動くか」をソースから説明する。ずれの候補を引用付きで挙げる。ライブで確かめる手順を 1 つ返す。調査役はアプリを動かさない。ファイルに書き込まない。
4. 照合する。すべての機能ファイルに調査役の要約が返ったことを確かめる。重なる手順をなるべく少ないアプリの状態にまとめる。引用されたずれを抜き取りで確かめる。ずれが無いという主張は確かめ直さない。最近の変更(`git log` の直近の範囲)からマップに無い利用者の面を探す。無いと判定するのはソースの具体的なパスを示せるときに限る。
5. ライブで通す。ソースに問題が見えなくても省かない。操作はすべて統括が行う。起動の形は手引きの起動の節に従う。サーバーと UI は 1 つの常駐インスタンスを順に操作する。短時間で終わる CLI は操作ごとに隔離したセッションを始める。すべての機能を最低 1 回動かす。通しの間は 4.4 の不変条件 3 つを守る。
   - 健康診断の失敗の原因が手引きのずれなら記述のずれとして扱う。修正案を記録して正しい手順で 1 回だけやり直す。起動し直すのは修正で無効になったものだけである。それでも通らなければ停止にする。
   - 機能に届かないときは到達不能とする。到達不能には具体的な前提(認証・権限・OS・外部の状態)と試した経路を書く。マップがその前提を書いていなければ記述のずれである。
   - 最後の後始末はやり直しを含めた最後の操作の後に行う。通しが始めたものを通しの後に残さない。証拠は手引きの保存先に残す。
6. 分類する。見つけたものを次の 3 つに分ける。

   | 分類 | 見分け方 | 扱い |
   | :-- | :-- | :-- |
   | 記述のずれ | 利用者から見た記述が誤っているか欠けている | マップか手引きの修正案を記録する |
   | 道具の欠け | 動いている振る舞いを手引きの道具で操作できない | 補助スクリプトの修正案を記録する。修正は 2.2 の 6. の規則に従う |
   | 製品の不具合 | アプリの振る舞いが実際に誤っている | 本人に報告して別のタスクとして起票する。保守の PR に入れない |

7. 出すか止める。結果が 1 PR のときは記録した修正案を要件にして develop の工程で 1 つの PR にする。完了条件には直した機能をライブで操作し直した証拠を含める。補助スクリプトを直したときも同じである。統括は PR の前に変えたファイルをすべて読み直す。変更なしと停止のときは PR を作らない。結果と確かめた範囲をそのまま報告する。

通しの記録(確かめた機能・到達不能の前提・確かめたずれと修正案・結果)は作業ツリーの外に短く書く。コミットしない。

### 4.4. 不変条件

通しの間はどの失敗のときも次の 3 つを守る。

1. 健康診断を通していないインスタンスを操作しない。健康診断は最初の操作の前に行う。セッションを単位にする面ではセッションごとに行う。失敗した操作の後とインスタンスが予想外の振る舞いをした後にも行う。健康診断で見えない失敗(プロセスは正常で UI が固まった状態)では既知の状態に戻すか起動し直す。様子を見て続けない。
2. それまでに取った証拠はどの後始末の後も残る。保存先を開いて確かめる。残ったと仮定しない。
3. 操作が始めたものはその操作の用が済んだ後に残さない。失敗した回の残骸はセッションが固まっても終わっても片付ける。共有のインスタンスでは残骸だけを片付けてインスタンスは止めない。

### 4.5. 調査役

Claude Code では調査役に `general-purpose` を使う。

- 調査役は機能ファイル全体とソースを読んで照合する役である。抜粋を読んで所在を探す `Explore` は照合に向かない。`general-purpose` は書き込みの道具を持つ。そのためブリーフに書き込まない指示を書く。下の雛形にはその指示を書いてある。
- 調査役は作業ディレクトリの中のソースだけを読む。MCP の道具と作業ディレクトリの外のファイルを使えないものとして扱う。
- 並列の起動は develop の `references/parallel.md` 2. の作法に従う。同じブリーフ・単独で読めるブリーフ・1 つのメッセージでの起動・脱落・報告の規則を使う。調査役は書き込まないので書き込み先の分離(worktree)は使わない。脱落した調査役の機能ファイルは統括が雛形の進め方で読む。手順 4 ですべての機能ファイルに要約が必要なためである。
- Codex CLI・Antigravity CLI ではサブエージェントを起動しない。統括が機能ファイルを 1 つずつ順に調べる。所見は雛形の報告の形で書く。並列の起動を省いたことを 1 行で報告する(develop の冒頭の段落と同じ扱い)。それらの CLI ではアプリの起動と操作を行わない。サンドボックスで許されるかを確かめていないため使えないものとして扱う。それらの CLI では 2.1 をファイルの調査だけにして起動の確認は 2.4 に回す。生成の証明(2.4)と保守のライブの通し(4.3 の 5)は Claude Code で行う。それらの CLI で保守を頼まれたら手順 1〜4 まで行い結果を停止として報告し Claude Code で続きを行うよう示す。

調査役のブリーフの雛形は次のとおりである。

