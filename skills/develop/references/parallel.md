# 並列の起動

統括がサブエージェントを並列に起動するときの作法を定める。扱うのは 3 つの形(同じ課題の競争・分担の点検・敵対役)と別系統のレビューの並走である。1 回の試行は最初に思い付いた形に固まりやすい。1 体の点検は 1 つの切り口しか見ない。並列の起動はこの 2 つを補う。

## 1. 適用範囲

- Claude Code に限る。Codex CLI・Antigravity CLI はサブエージェントを並列に起動できないので本書を使わない。それらの CLI で本書の手順に当たったときは develop の冒頭の段落に従って省いた手順と理由を報告して次の手順へ進む。
- 既定の進め方は develop 6. の順次のループである。本書の工程は任意である。ループの代わりにはならない。
- 使う場面は次の 3 つである。

| 場面 | 形 |
| :-- | :-- |
| 自明でない成果物を作るときに 1 回の試行では形が固まるおそれがある | 同じ課題の競争(3.) |
| 範囲を分けて点検・検証する | 分担の点検(4.) |
| 変更か設計を壊そうとして欠陥を探す | 敵対役(5.) |

- 別系統のレビューの並走(6.)は develop 7. で gate-reviewer と並べて使う。

## 2. 共通の作法

3.〜5. のどの形でも次に従う。

- 書き込み先: 候補と作業者ごとに書き込み先を分ける。Agent の `isolation: "worktree"` で各自に git worktree を与える。書き込まない作業者(読むだけの点検)には与えない。worktree が使えないときは作業ツリーの外のディレクトリを各自に与える。同じ書き込み先を共有すると後の書き込みが先の成果を上書きする。
- 同じブリーフ: 全員に同じブリーフを渡す。作業者ごとに違うのは担当の切り口と書き込み先だけにする。ブリーフが違うと結果の違いが作業者によるのかブリーフによるのかを区別できない。
- 単独で読めるブリーフ: ブリーフには目標・範囲・担当の切り口・検証の方法・報告の形を書く。作業者は統括の会話を読めないためである。
- 起動: 1 つのメッセージで全員を起動する。サブエージェントはバックグラウンドで動く。全員の完了の通知を待ってから結果を読む。
- モデルと推論の強さ: `model` と `effort` はジョブに合わせて起動ごとに選定する。`effort` の選定は develop 6. の冒頭の規則に従う。
- 脱落: 出力を返さなかった作業者は脱落として扱う。残りの N-1 体で続行して脱落を記録する。
- SHA と方法: 検証か計測をする作業者には対象のコミットの SHA と方法をブリーフで名指しする。計測の方法は回数・1 回の定義・実行の順である(`benchmark.md`)。作業者は結果にその SHA と方法を書く。SHA と方法のどちらかが書かれていない結果は捨てて同じブリーフで 1 回だけ起動し直す。2 回目も書かれていなければ欠落として記録する。欠落は合格に数えない。どのコミットをどう確かめたかが分からない結果は合格の根拠にならないためである。
- 報告: 作業者の生の出力を統括の会話に貼らない。要約と表にする。大きな出力は develop 6. の手順 2 に従って作業ツリーの外のファイルに書かせる。

## 3. 同じ課題の競争

同じ課題を N 体の候補に解かせる。統括は候補を採点して土台を 1 つ選定する。ほかの候補の良い点は土台に移植する。develop 5. で planner を並列に起動するときはこの形を使う。

### 3.1. 枠組み

1. 候補が作る成果物を 1 文で書く。
2. 採点基準を 3〜6 項目書く。基準はこの課題の成功を判定できる具体的な項目にする。採点基準は統括の道具であり候補には見せない。候補が見るのは課題だけである。
3. 候補の数 N を定める。2 体以上にする。設計の方向が複数あるときは方向の数に合わせて候補を加える。生成が主で判断が軽い作業では同じモデルを N 回起動する。判断が重い作業では候補ごとに `model` を変えてよい。
4. ファイルに書き込む候補には 2. の書き込み先を与える。

### 3.2. 起動

2. に従って全候補を起動する。各候補には課題・共通の資料のパス・自分の書き込み先を渡す。候補には成果物と短い根拠を作らせる。根拠には検討した代替と捨てた理由を書かせる。

### 3.3. 土台の選定

- 全候補を最後まで読んでから選定する。採点基準の項目ごとに各候補を採点する。全体の印象で選定しない。
- 土台は将来の保守者が不変条件を壊さずに拡張しやすい案にする。
- 同点のときは境界が小さい方を取る。境界が小さい案は同じ選択を 1 か所に集めやすい。変えるときに直す場所が少ない(ponytail 3. の「同じ選択を 2 か所以上に書かない」規則)。
- 別系統のモデルの判定役は設けない。Claude Code の中では別系統のモデルを用意できないためである。別系統の目は 6. のレビューで得る。

### 3.4. 移植

- 負けた候補をもう一度読む。土台に移植する価値のある点を各候補から 1〜2 点だけ拾う。
- 移植は手で書き直して土台に入れる。機械的に貼らない。成果物を 1 つの考え方で読める状態に保つためである。
- 候補が同じ形に収束したら強い合意として扱う。合意の形を取り入れて移植はしない。
- 候補が大きく割れたら課題の指定が足りない。3.1 の枠組みを作り直して再実行する。割れた案を平均しない。

### 3.5. 検証と記録

- 合成した成果物をその成果物の通常の手順で検証する(コードは develop 6.・計画は develop 5. の承認)。
- 検証で問題が見つかったら原因を次の 2 つのどちらかとして扱う。枠組みの誤りなら 3.1 に戻って再実行する。候補の 1 つが問題を捕らえていたのに移植が漏れたなら 3.4 に戻る。問題を繕って先へ進まない。
- 合成の記録を Implementation Notes に書く。書くのは土台と選定の理由・各移植とその出所の候補・捨てたものと理由・収束か脱落の有無・検証の結果である。

## 4. 分担の点検

範囲を作業者に分けるか同じブリーフで競わせて点検・検証する。統括は結果を 1 つの報告にまとめる。

### 4.1. 枠組み

1. 完了の述語と返す報告の形を先に書く。完了の述語は点検を終えたと判定する条件である。
2. 形を定める。

| 形 | 作業者への割り当て |
| :-- | :-- |
| 分担 | 範囲を切り口に分けて作業者ごとに 1 つ担当させる |
| 競争 | 同じブリーフで N 体に同じ作業をさせる |
| 混合 | 切り口ごとに複数の作業者を競わせる |

3. 競争と混合では選定の規則を起動の前に Implementation Notes に書く。規則は次の 3 つのどれかである。結果を見てから規則を定めると都合のよい結果を取りやすい。

| 規則 | 取る結果 |
| :-- | :-- |
| 最初の合格 | 最初に合格した結果 |
| 全順位 | 全結果とその順位 |
| 最良 | 全結果のうち最良の 1 つ |

### 4.2. 結果の形

- 2. に従って全員を起動する。
- 結果は `PASS`・`ISSUES`・`BLOCKED` のどれかと証拠で返させる。`BLOCKED` は作業を進められなかった(権限・環境・入力の不足)ときに使う。理由を書かせる。
- 欠陥を証明できた作業者は `ISSUES` を返す。最初の 1 件だけでなく証明できた欠陥をすべて列挙させる。

### 4.3. 集約

- 結果を読んだら 2. の SHA と方法の規則を先に当てる。
- 分担では必要な切り口のすべてに結果が必要である。結果の無い切り口は欠落である。欠落は合格に数えない。
- 競争では 4.1 で書いた選定の規則を当てる。
- 完了の述語を満たさなければ点検を終えたと報告しない。

### 4.4. 報告

報告は 1 つにまとめる。含めるものは次の 4 つである。

- 切り口か作業者ごとの結果の表
- issue ごとの 1 行
- 欠落と脱落
- 競争のときは選定の規則

## 5. 敵対役

敵対役は変更か設計を壊そうとするサブエージェントである。所見は実行で示したものだけを残す。develop 7.(ゲートを通す)の前の任意の工程として使う。統括も敵対役も変更を直さない。直すのは implementer である。

### 5.1. 範囲と意図

- 範囲は `main` との差分と作業ツリーの未コミットの変更である。
- 意図は要件の 4 行(目的・完了条件・対象外・品質)で渡す。統括は意図を自分の言葉で言い直す工程を持たない。言い直すと本人と確かめた意図(要件の 4 行)がずれるためである。

### 5.2. 起動

- 2. に従って敵対役を起動する。各敵対役に自分の worktree を与える。未コミットの変更があれば統括が `git diff HEAD` を作業ツリーの外のファイルに書く。敵対役には自分の worktree で `git apply <パス>` させる。
- ブリーフには範囲・意図と次の指示を書く。
  - 変更を壊すことを目標にする。
  - 所見は実物のコードに対する実行で証明する。証明は失敗するテスト・再現のスクリプト・誤った出力を示すコマンドの出力のどれかである。
  - 対象が設計か計画のときは試作を実行するか現在のツリーを探索して示す。
  - 再現のスクリプトは自分の worktree に書く。
  - 所見ごとに題・実行したコマンド・出た出力・意図が求める出力を報告する。
  - 実行しなかったものは書かない。様式・命名・構造の指摘もこれに含む。将来の変更があって初めて問題になるリスクも含む。
  - 所見が無いことも正当な結果である。

### 5.3. 検証

- 統括は各所見のコマンドを再実行する。
- 出力が失敗を示してその失敗が意図を壊す所見だけを残す。残りは捨てる。
- 同じ根本原因の所見は 1 つにまとめる。
- 敵対役はそれぞれ別の失敗を見つける。どれか 1 体の一覧に絞らず全員の確かめた所見をすべて残す。3.3 と 3.4 は使わない。

### 5.4. 出力と受け渡し

統括は確かめた結果を次の形で Implementation Notes に書く。確かめた所見が無ければ **所見** の下に「確かめた所見なし」と書く。

```markdown
**意図**

<要件の 4 行>

**所見**

- <題>
  - コマンド: `<コマンド>`
  - 出力: <出た出力>
  - 意図をどう壊すか: <壊す完了条件か目的>
  - 見つけた敵対役: <敵対役の番号>

**捨てた所見**

- <敵対役の番号>: <件数>。理由: <再実行で失敗が出なかった・失敗が意図を壊さないなど>
```

残った所見は develop 7. で gate-reviewer に渡す。gate-reviewer は再現のコマンドと出力がある所見を欠陥として差し戻しの判定に含める(`agents/gate-reviewer.md` の進め方 3)。敵対役の worktree は所見の再実行が済んだら削除する。

## 6. 別系統のレビューの並走

- Claude Code の中では別系統のモデルを用意できない。同じ系統のモデルは同じ見落としを共有しやすい。別系統の目は Codex CLI のレビューで得る。
- Codex CLI がある環境では gate-reviewer の起動と並行して `codex review --base main > "$TMPDIR/codex-review.md" 2>&1` を Bash の `run_in_background` で実行する。
- 所見は `review-triage.md` の fix・dismiss・ask で仕分ける。PR に投稿されない Codex CLI のレビューは同書 1. で対象に含めている。fix の所見は gate-reviewer の修正点と合わせて implementer に渡す(develop 7.)。
- Codex CLI が無い環境ではこの並走を省く。省いたことを Implementation Notes に書く。
