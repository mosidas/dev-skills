# 種類別の工程

タスクの種類ごとに工程の最初に固定するものと止まる条件を定める。種類はバグ修正・リファクタ・性能・試作・移行の 5 つである。統括は要件を確かめるときに種類を見分ける。planner は種類の節を計画のステップと完了条件に写す。reviewer は種類の節の確認を点検に加える。どの種類にも当たらないタスク(機能の追加と変更)には本書を適用しない。

## 1. 適用範囲

| 種類 | 見分け方 | 最初に固定するもの | 計画のステップ 1 |
| :-- | :-- | :-- | :-- |
| バグ修正 | 報告された不具合を直す。原因の診断だけを求める依頼を含む | 報告と同じ面での再現 | 再現と原因の特定 |
| リファクタ | 利用者が観測できる挙動を変えずに構造を変える | 挙動の契約 | 挙動の固定 |
| 性能 | 計測した遅さか資源の消費を目標の値まで下げる | 基準の計測 | 基準の取得 |
| 試作 | 1 つの判断の材料を使い捨ての実物の観測で得る | 試作で確定する判断 | なし(統括が作業ツリーの外で行う) |
| 移行 | ライブラリ・データの形式・基盤を入れ替えて同じ結果を出す | 旧版の入力と出力 | 旧版の入力と出力の保存 |

- 統括は要件の確認で種類を見分けて 4 行の確認に添える。見分けた種類は planner と reviewer に渡す。
- 1 つのタスクには 1 つの種類を当てる。作業中に別の種類の作業(リファクタの途中で見つけた不具合・移行の途中で見つけた不具合)が見つかったら同じブランチで扱わずに別のタスクとして起票する。種類の混ざった差分では固定したものとの比較が成り立たないためである。
- 試作と診断だけの依頼はコミット・ブランチ・PR を作らない。作業は作業ツリーの外で行う。担当は統括である。design-ui の `references/session.md` の UI モックを統括が作るのと同じ分担である。
- ponytail 3.(旧 API の削除)・`agents/planner.md` の進め方 3(並べ方の型と移行の例外)は種類を問わず適用する。本書はそれらを繰り返さずに種類に固有の手順だけを書く。

## 2. バグ修正

### 2.1. 固定するもの

- 報告と同じ面(画面・CLI・API・ジョブ)で自分で再現する。単体テストの失敗は再現に数えない。単体テストは分岐の挙動を示すがバグが無いことは示さないためである。
- 再現しないときは条件(入力・環境・操作の順)を絞るか計装(ログ・計測の出力)を加えて起こす。本人に再現を頼むのは自分で届かない面(本番だけにあるデータ・本人の端末)に限る。頼むときは届かない理由を書く。

### 2.2. 進め方

- 原因の仮説を複数立てる。残る範囲を最も減らす分け方(コミットの範囲・入力の半分・処理の段)で二分探索する。分けるたびに実行時の証拠(ログ・計装の出力・デバッガで見た値)で仮説を退ける。ソースを読んだ推測だけでは退けない。
- 残った仮説の仕組みを実行時の証拠で確かめてから修正を計画する。
- 修正は証拠が裏づける最小の変更にする。根本原因を直す規則は ponytail 2. に従う。「改善するかもしれない」変更は修正でなく仮説である。出荷しない。
- 証拠に否定された仮説のために入れた変更(ガード・設定の変更・計装)は戻す。
- 修正の後に元の再現を報告と同じ面で実行して通ることを出力で確かめる。別の面での確認は合格に数えない。

### 2.3. 診断だけを返す場合

依頼が修正でなく原因の診断のとき(稼働中のメモリのリーク・入力が無いのに回り続ける CPU・表示の乱れ)は引用付きの診断を成果にする。修正はしない。診断は統括が作業ツリーの外で行う(1.)。

- 生の信号(CPU プロファイル・ヒープスナップショット・トレース)を対象の面で取る。
- 信号を決定的な証拠(ホットパスの関数・解放されない参照の連鎖・入力なしで回るループ)に絞る。大きな成果物はファイルに書き出してパスと要約で扱う。
- 仕組みは安い介入(計装の追加・一時的な書き換え)で確かめてから信じる。介入は診断の後に戻す。
- 所見をソースの位置(ファイル・シンボル・行)に対応付ける。
- 報告には取った信号・絞った所見・仕組みを確かめた方法・ソースの位置・成果物の所在を書く。修正はバグ修正か性能の新しいタスクとして起票する。

### 2.4. 止まる条件

- 再現しないうちは修正に進まない。条件を絞っても計装しても再現しないときは試した条件と観測を報告して止まる。
- 残った仮説の仕組みを証拠で確かめられないうちは修正に進まない。
- 元の再現が報告と同じ面で通ったら完了とする。

## 3. リファクタ

### 3.1. 固定するもの

- 構造を変える前に挙動の契約を固定する。手段は特性テスト(現在の出力を期待値にするテスト)・スナップショット・等価性の比較(旧と新の出力の差分を取るスクリプト)である。既存のテストが契約を覆っていればそれを固定に使う。
- 特性テストは現在の挙動を写すことが目的である。ponytail 5. のテストの判定の「期待値をコードの実行結果から作らない」の例外とする。
- 型検査と lint は固定に数えない。型と書式が通っても挙動は変わるためである。

### 3.2. 進め方

- コードに欠けている構造を名指しする(ponytail の `references/design.md` 2.1)。今作るならどうするかの目標の形(モジュールの配置・型・呼び出しの関係)を書く。目標の形は分岐か不正な状態を減らす形にする。間接の層を増やす形にしない。形が明確で局所的なコードは動かさない。
- コミットは削除・形の変更・後片付けの順に分ける。各コミットで固定した検査を通す。
- 名前を変えたら旧い名前を grep して文字列・文書・逆参照に残っていないかを実ファイルで確かめる。
- 挙動が変わっていないことを実物で示す。比較のスクリプト・保存した入力の再生・利用者が触る面での実行のどれかで示す。ビルドが通ることは根拠に数えない。

### 3.3. 止まる条件

- 挙動を固定できないうちは構造を動かさない。
- 読み手の負荷(新しい読み手が「X はどこから来るか」と「何が X を変えうるか」に答える手間)が下がらない変更は戻す。
- 作業中に見つけた不具合と欠けた機能は直さずに別のタスクとして起票する。直すと固定した契約と比べられなくなる。
- 固定した検査が変更の前後で同じ結果になり読み手の負荷が下がったら完了とする。

## 4. 性能

### 4.1. 固定するもの

- 処置の前に基準を計測する。計測の対象・方法・環境・回数と値を記録する。
- 完了条件には目標の値と計測の方法を書く。要件に目標の値が無いときは統括が要件の確認で補う。
- 数値を報告と判断に使う前に `benchmark.md` の 7 つの問いで計測を確かめる。基準の値にも適用する。

### 4.2. 進め方

- 仮説は計測(トレース・プロファイル)から立てる。ソースを読んだ推測で処置しない。
- 処置は次の 7 つの指針を安い順に試す。
  1. やらない。結果を誰も使わない処理をやめる。
  2. 繰り返さない。一度求めた結果を再利用する。
  3. 減らす。処理の回数か量を減らす。
  4. 後でやる。結果が必要になるまで処理を遅らせる。
  5. 待たせない時にやる。利用者が結果を待っていない間に処理する。
  6. 並行にやる。
  7. 安くやる。同じ結果をより安い手段で得る。
- 1 つの変更ごとに計測する。1 つのコミットには処置を 1 つだけ入れる。実行の回数は `benchmark.md` 3. の問い 5 に従う。計測の値はコミットの本文と implementer の報告に書く。処置をまとめて計測するとどの処置が数値を変えたかを区別できない。
- PR 本文の数値は `benchmark.md` 4.2 の形で書く。

### 4.3. 止まる条件

- 基準が取れないうちは処置に進まない。
- 目標に届いたら止める。残りの指針は試さない。
- 数値が改善しない処置(`benchmark.md` 4.1 の結論が遅いか差なし)は戻す。
- 結論が判定不能の処置は合格に数えない。implementer の報告の結果は「確定できず」とし、判定不能にした条件を書く。

## 5. 試作

### 5.1. 固定するもの

- 試作で確定する判断を 1 つに絞る(どの配置か・どの操作か・どの挙動か・どの手段が速いか)。判断が無ければ試作せずに通常の工程で作る。
- 計画の未確定事項のうち試作で確定する事実(develop 5.)を確かめるときも本節に従う。

### 5.2. 進め方

- 本番のソースと分けて作業ツリーの外で使い捨てに作る。テスト・抽象化・本番のフレームワークは使わない。
- 見た目の判断は design-ui の `references/session.md` の工程を正とする。保存先とコミットは session.md に従う。本節の作業ツリーの外の規則と 1. のコミットを作らない規則は適用しない。挙動と時間の判断は問いを動かす最小のスクリプトで作る。
- 判断する対象を観測する(出力の表示・時間の計測・撮影)。試作では観測がテストの代わりである。
- 報告には試した案・観測した証拠・トレードオフ・推奨・試作の所在を書く。試作が使い捨てであることも書く。

### 5.3. 止まる条件

- 判断の材料が観測で揃ったら止めて報告する。試作を本番の品質へ仕上げない。
- 試作のコードを本番のブランチに入れない。採用した案は通常の工程で作り直す。

## 6. 移行

### 6.1. 固定するもの

- 完了条件は旧版と出力が一致することにする。旧版の不具合も一致させる。途中で不具合を直すと新旧の差が移行の誤りか修正かを区別できないためである。
- 移行を始める前に旧版の入力と出力を保存する。

### 6.2. 進め方

- 保存した入力の再生と比較は `agents/planner.md` の規則の検証(移行)に従う。
- 直すべき不具合を見つけたら直さずに別のタスクとして起票する。
- 段階の境界と一時的に通らない検査は `agents/planner.md` の進め方 3 の移行の例外に従う。

### 6.3. 止まる条件

- 比較で差が出たら次の段階へ進まない。差の原因を調べて新版を直す。
- 保存したすべての入力で一致したら完了とする。
