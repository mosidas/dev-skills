# 計測の吟味

性能の数値を報告と判断に使う前に 7 つの問いで計測を確かめる。結論と数値は 4. の形で書く。implementer は計測の値を報告するときに使う。reviewer と gate-reviewer は性能の数値を主張する変更を点検するときに使う。統括は PR 本文に数値を書くときと数値で案を比べるときに使う。性能のタスクの工程(基準の計測・処置の順・止まる条件)は `kinds.md` 4. が扱う。本書は数値そのものの確かさだけを扱う。

## 1. 適用範囲

- 次の数値に適用する: 処置の前と後の比較・性能の低下の主張・ライブラリか設定の比較・性能のタスクの基準の値。
- 種類が性能のタスクに限らない。機能の追加のコミットか PR 本文が速さか遅さを主張するときも適用する。
- 本人が概算を求めたときは 1 回の実行でよい。3. の問い 4 と問い 7 だけを確かめる。報告には 1 回の実行であることを書く。その値が不自然なとき(上限を超える・前の値と桁が違う)は残りの問いも確かめる。
- 選択肢の比較(どのライブラリを使うか・どの設定を使うか)は概算として扱わない。採用した案はその後も使われ続けるためである。

## 2. 実行の前

- 報告に書く主張の文を先に書く(例: 「6 万行のデータの書き出しが p50 で 30% 速い」)。3. の問いはこの文を確かめる。
- 計測のスクリプトを読む。何の時間を計り何を数え何を除くかを書き出す。
- `uptime` で負荷の平均を確かめる。`nproc` でコア数を確かめる。ほかの処理が動いているときはそれが何かを調べる。止められないときは比べる各側を交互に実行して両側が同じ雑音を受けるようにする。そのことを報告に書く。

## 3. 7 つの問い

各問いには実行の証拠(出力・プロファイル・数えた値)で答える。コードを読んだ推測では答えない。

1. 律速: なぜ 2 倍速くならないか。数値を抑えている資源を名指しする。
   - プロファイルは報告しない別の実行で取る。プロファイラーとトレーサーは処理を遅くするためである。
   - プロセスごとの CPU(`top`・`pidstat`)・実行時のプロファイラー(`node --cpu-prof`・`py-spy`・`perf`)・I/O 待ち・システムコールの回数(Linux の `strace -c`)を見る。熱い箇所をソースの位置に対応付ける。
   - 負荷を生む側が先に飽和していないかも見る。飽和していれば計ったのは負荷を生む側である。
   - 変更が数値を動かさなかったときも律速で理由を説明する。律速を見つける前にその変更を無駄と結論しない。
2. 調整: 各側を本番と同じ条件で動かしたか。
   - リリースビルド・本番のフラグと環境変数・バッチとトランザクションの設定・接続プール・本番と同じ温まり方のキャッシュ・同じ版とデータで両側を動かす。片側だけが既定の設定なら比べたのは実装でなく設定である。
   - 律速が設定(1 行ごとのコミット・デバッグビルド・索引の欠落)のときはその側が未調整である。調整して計り直してから優劣を書く。調整できないときはその実行から優劣を書かない。
   - 採用する案を比べるときは「今の設定のままでは」と主張を狭めても未調整は解消しない。利用者が採用するのは案であり今の設定ではないためである。
3. 上限: 物理の上限を超えていないか。
   - 算術で確かめる。1 秒あたりのバイト数をディスクとネットワークの帯域と比べる。1 秒あたりの操作数と 1 操作の費用の積をコア数と比べる。短縮した時間を変えた部分が元々かかっていた時間と比べる。実行時間の 10% を占める部分を取り除いても全体は最大で約 11% しか速くならない。
   - 上限を超えた結果は仕事以外のもの(キャッシュ・何もしない処理・不具合)を計っている。
4. エラー: 失敗を数えたか。
   - 失敗と成功以外の応答を数える。出力があることだけでなく正しいことも確かめる。失敗は数値をどちらの向きにも歪める。拒否は速く返る。タイムアウトと再試行は遅い。
   - スクリプトがエラーを数えないときは数える処理を加える。
5. 再現性: 繰り返して同じ結果が出るか。
   - 各側を 5 回以上 A・B・A・B の順に交互に実行する。暖機・遅延初期化・キャッシュ・時間による変動がどちらかの側に偏らないようにするためである。
   - 中央値と範囲を報告する。差が実行ごとのばらつきより小さいときは差なしとする。際どいときは順位和検定か計測の仕組みが持つ統計を使う。
6. 関連性: 利用者にとって意味があるか。
   - 部分の計測(関数・ヘルパーの単位)には利用者が待つ経路全体の計測を並べる。データの大きさと並行の度合いは本番に近づける。
   - 部分の結果は全体に占める割合で報告する。リクエストの 1% を占めるヘルパーはどれだけ速くしてもリクエストを最大 1% しか速くしない。
7. 仕事の有無: 計測区間の中で仕事が実際に行われたか。
   - リクエストがサーバーに届いたこと・行が書き込まれたこと・バイトが読まれたこと・コードが結果を使ったことを確かめる。
   - 遅延評価のコード(誰も回さないジェネレーター・誰も await しない Promise・JIT が捨てられる結果)とタイムアウトは起きなかった仕事に数値を出す。

## 4. 結論と報告

### 4.1. 結論

報告は結論から書く。結論は次の 4 つのどれかにする。

| 結論 | 当たる場合 |
| :-- | :-- |
| 速い | 処置の側が速く差が実行ごとのばらつきより大きい。判定不能の条件に当たらない |
| 遅い | 処置の側が遅く差が実行ごとのばらつきより大きい。判定不能の条件に当たらない |
| 差なし | 差が実行ごとのばらつきより小さい。判定不能の条件に当たらない |
| 判定不能 | 次の条件のどれかに当たる |

判定不能にする条件は次のとおりである。判定不能のときは当たった条件と欠けた証拠を書く。

- 差を主張するのに律速を名指せない(問い 1)。
- 片側が未調整のまま動いた(問い 2)。
- 問い 4 か問い 7 を確かめられなかった。
- 目標の値を定めた面と別の面で計った(問い 6)。

### 4.2. 数値の書き方

- 数値には単位・回数・範囲・律速を付ける。例: 「p50 41 ms → 33 ms。各側 7 回の中央値。処置後の範囲は 32〜35 ms。1 コアの JSON の解析が律速」。
- 概算の 1 回は 4.1 の結論を付けずに値と「1 回の実行」を書く。実行ごとのばらつきが無いため差なしと速い・遅いを区別できない。
- PR 本文の検証の節には主要な数値を 1 つだけ結論と合わせて書く。実行の回数・範囲・律速の証拠は計測の成果物か Implementation Notes に書く。PR 本文にはその所在を書く(`git-flow.md` 3.)。
