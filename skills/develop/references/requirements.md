# 要件の 4 行

要件は、目的・完了条件・対象外・品質の 4 行で書く。develop の要件の確認、specify の PRD の要求、build のタスクの本文が、この形式を使う。

## 1. 形式

```
目的: <誰の何を解決するか>
完了条件: <満たしたら終わりと言える挙動>
対象外: <今回やらないこと>
品質: <簡易 / プロダクト>
```

目的の「誰」は画面の利用者に限らない。ライブラリや内部 API を呼び出す開発者と次にそのコードを保守する人も利用者に含める。

新しい Web の画面・フォームでは、4 行の後に次の行も書く。

```
UI モック: <brief.md のパス / 不要>
```

- brief.md は、`../../design-ui/references/session.md` の工程で本人と往復して作る UI モックの brief であり、既定の置き場所は、backlog を初期化したリポジトリのルートからの `docs/ui-mock/<slug>/brief.md` である。
- `不要` は、UI モックを作らずに実装すると本人が答えたことを示す。

## 2. 聞く範囲

聞くのは「何を作るか」に限る。「どう作るか」(実現方針の選択)は planner の仕事なので、要件では決めない。

新しい Web の画面・フォームでは、UI モックの有無も聞く。ここでいう新しい画面・フォームは Web のものに限る。ネイティブアプリの画面では聞かず、UI モックの行も書かない(`../../design-ui/references/session.md` の対象外)。既存の画面の変更では聞かない。実装そのものが見本になるためである。既存の画面でも、ユーザーが明示して求めたときは、`../../design-ui/references/session.md` の工程で UI モックを作る。

## 3. 品質の決め方

- 簡易は、試作や手元のスクリプトなど、使うのが自分だけのコードである。
- プロダクトは、他者が使うコード、または本番で動くコードである。
- 品質が依頼に書かれていなければ、依頼から判断する。判断がつかないときはプロダクトにする。
