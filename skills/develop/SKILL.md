# 開発の手順

本スキルは統括セッションが読む。統括の仕事は計画・委譲・検収・PR である。サブエージェントを起動できない CLI(Codex CLI・Antigravity CLI)では、統括が planner・implementer・reviewer の役割を 1 つずつ順に担い、役割を切り替えるたびに前の役割の判断を引き継がずに `agents/` の各ファイルの手順で作業する。コードは書かない。書くのは implementer サブエージェント、点検するのは reviewer サブエージェントである。統括がコードを書かない理由は 2 つある。統括の文脈をタスク全体の判断に使い続けること、そして書いた本人がレビューする状態を避けることである。

## 1. 工程

| 工程 | 担当 | 成果 |
| :-- | :-- | :-- |
| タスクを決める | 統括 | Backlog.md のタスク(既存または新規) |
| ブランチを切る | 統括 | `main` から切ったブランチと、有効な git hook |
| 計画する | planner(小さな変更では統括) | ステップごとの完了条件を持つ計画 |
| 実装する | implementer | ステップ 1 つ分のコミット |
| 点検する | reviewer | 承認、または修正点の一覧 |
| PR を出す | 統括 | push・PR・CI の通過 |
| 閉じる | 統括 | マージ後のタスクの Final Summary |

各工程の終わりに、ユーザーへ 1 行で進捗を報告する(例: 「ステップ 2/4 完了: `a1b2c3d` 承認」)。ユーザーは途中の会話を追っていない前提で書く。

## 2. タスクを決める

- `backlog` コマンドは、Backlog.md を初期化したリポジトリのルートで実行する(サブモジュールの中では動かない)。Backlog.md が無いリポジトリでは、この工程を省き、計画と経過を PR 本文に書く。
- 既存のタスクがあればその id を使う。なければ作る。

```sh
backlog task create "<タイトル>" -l <area> -d "<目的と完了条件>"
```

- 以後の経過はすべてタスクの Implementation Notes に追記する(`backlog task edit <id> --append-notes "<経過>"`)。`--notes` は既存の Notes を置換するので使わない。日付ごとのファイルを作らない。

## 3. ブランチを切る

- `main` を最新にし、`<type>/<TASK-id>-<slug>` の名前でブランチを切る(`type` は `feat`・`fix`・`refactor`・`chore`。タスクが無いときは `<type>/<slug>`)。
- git hook が無ければ入れる(`references/hooks.md`)。pre-commit で lint、pre-push でテストを実行する。hook は implementer の「テストが通った」という報告を機械的に裏づける。
- 手順の詳細は `references/git-flow.md` に従う。
- リポジトリの規約が `main` への直接コミットを定めているとき(private の設定リポジトリなど)は、ブランチと PR を省き、`main` 上でステップごとにコミットする。実装と点検のループはそのまま行う。

## 4. 計画する

- planner サブエージェント(`dev-skills:planner`)を起動し、タスクの目的・完了条件・対象リポジトリのパスを渡す。
- 変更するファイルが明らかで 1 ステップで済む変更(誤字の修正、設定値の変更、1 関数の追加など)は、planner を起動せず統括が planner と同じ形式で計画を書く。reviewer は省かない。
- planner は計画を返す。統括は計画をユーザーに見せ、承認を得てからタスクの Implementation Notes に記録する。ユーザーが最初から「全部進めて」と指示しているときは、計画を報告して先へ進む。
- 計画のステップは 1 つずつ実装とレビューを回せる大きさにする。1 ステップが 1 コミットになるので、レビューの範囲が明確になり、問題があればそのコミットだけを戻せる。

## 5. 実装と点検のループ

ステップごとに次を繰り返す。サブエージェントは毎回新しく起動し、前のステップの会話を引き継がない。前のステップの試行錯誤が次のステップの判断に混ざるのを防ぎ、reviewer が実装の経緯を知らずに結果だけを見る状態を保つためである。

1. ステップ開始時の HEAD の SHA を `git rev-parse HEAD` で取り、文字列として控える。シェル変数はコマンドごとに消えるので使わない。この SHA が reviewer に渡す範囲の起点になる。
2. implementer サブエージェント(`dev-skills:implementer`)を起動する。渡すのは、対象リポジトリのパス、ブランチ名、そのステップの計画(変更するファイル・手順・完了条件・検証コマンド)、変更してよい範囲である。implementer は実装してテストを通し、コミットして、変更ファイルとテスト結果を報告する。
3. reviewer サブエージェント(`dev-skills:reviewer`)を起動する。渡すのは、対象リポジトリのパス、レビューする範囲(`<控えた SHA>..HEAD`)、そのステップの計画、implementer の報告事項である。reviewer は「承認」か「要修正」と修正点の一覧を返す。
4. 要修正なら、修正点をそのまま implementer に渡して直させ、再び reviewer に点検させる。3 回直しても承認されないときは、計画か指摘のどちらかに無理があるので、統括がユーザーに状況を報告して判断を仰ぐ。
5. 承認されたら、ステップの結果をタスクの Implementation Notes に書き、ユーザーに進捗を報告する。

統括は各報告を鵜呑みにせず、検証コマンドの実行結果と `git log`・`git diff` で検収する。サブエージェントの報告は要約であり、報告と実物が食い違うことがある。

## 6. PR を出す

- 全ステップが承認されたら push し、PR を作る。
- CI の結果を確認する。失敗したら、失敗ログを implementer に渡して直させ、再 push して再確認する。
- PR のマージはユーザーの指示を得てから行う。手順は `references/git-flow.md` に従う。

## 7. 閉じる

- マージ後に `main` を更新し、作業ブランチを削除する。
- タスクを Done にし、Final Summary に結果(何ができるようになったか、PR 番号、残した課題)を書く。

```sh
backlog task edit <id> -s Done --final-summary "<結果>"
```

## 8. 参照ファイル

| ファイル | 内容 | 読むとき |
| :-- | :-- | :-- |
| `references/git-flow.md` | ブランチ・コミット・push・PR・CI 確認・マージのコマンド | ブランチを切るとき、PR を出すとき |
| `references/hooks.md` | git hook(lefthook・husky)の導入 | hook が無いリポジトリで作業を始めるとき |

サブエージェントの定義(`agents/`)は統括が読まなくてよい。役割と出力形式はサブエージェント自身が持つ。
