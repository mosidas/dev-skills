# 開発の手順

本スキルは統括セッションが読む。統括の仕事は計画・委譲・検収・PR である。サブエージェントを起動できない CLI(Codex CLI・Antigravity CLI)では、統括が planner・implementer・reviewer・gate-reviewer の役割を 1 つずつ順に受け持ち、役割を切り替えるたびに前の役割の判断を引き継がずに `agents/` の各ファイルの手順で作業する。コードは書かない。書くのは implementer サブエージェント、点検するのは reviewer と gate-reviewer サブエージェントである。統括がコードを書かない理由は 2 つある。統括の文脈をタスク全体の判断に使い続けること、そして書いた本人がレビューする状態を避けることである。

## 1. 工程

| 工程 | 担当 | 成果 |
| :-- | :-- | :-- |
| 要件を確かめる | 統括 | 目的・完了条件・対象外・品質の 4 行(新しい Web の画面・フォームを作るときは UI モックの行も書く) |
| タスクを決める | 統括 | Backlog.md のタスク(既存または新規) |
| ブランチを切る | 統括 | `main` から切ったブランチと、有効な git hook |
| 計画する | planner(小さな変更では統括) | ステップごとの完了条件を持つ計画 |
| 実装する | implementer | ステップ 1 つ分のコミット |
| 点検する | reviewer | 承認、または修正点の一覧 |
| ゲートを通す | gate-reviewer | ブランチ全体のマージ可の判定 |
| PR を出す | 統括 | push・PR・CI の通過 |
| 閉じる | 統括 | マージ後のタスクの Final Summary |

各工程の終わりに、ユーザーへ 1 行で進捗を報告する(例: 「ステップ 2/4 完了: `a1b2c3d` 承認」)。ユーザーは途中の会話を追っていない前提で書く。

## 2. 要件を確かめる

要件の 4 行(目的・完了条件・対象外・品質)と UI モックの行の形式・聞く範囲・品質の決め方は、`references/requirements.md` に従う。

- 依頼に 4 行が揃っていれば、次の箇条の UI モックの確認を除いてこの工程を省く。品質だけが無いときは質問せず、`references/requirements.md` 3. の決め方で品質を書く。ほかの行が欠けていれば、統括がユーザーに 1 問ずつ、最大 3 問まで聞く。一度に列挙しないのは、答えによって次に聞くべきことが変わるからである。
- 新しい Web の画面・フォームを作るタスクで依頼に UI モックの行が無ければ、4 行が揃っていても、4 行の確認の後に、UI モックを先に作るか不要かを 1 問聞く。この 1 問は、最大 3 問には数えない。既存の画面の変更では聞かない。
  - 先に作ると答えたら、design-ui の `references/session.md` の工程で UI モックを作るよう示して停止する。タスクもブランチも作らない。
  - 不要と答えたら、UI モックの行に `不要` と書く。
- 結果を 4 行(UI モックの行があればその行も含める)にまとめ、ユーザーに確認する。これらの行がタスクの本文と planner への入力になる。

## 3. タスクを決める

- `backlog` コマンドは、Backlog.md を初期化したリポジトリのルートで実行する(サブモジュールの中では動かない)。Backlog.md が無いリポジトリでは、この工程を省き、計画と経過を PR 本文に書く。
- 既存のタスクがあればその id を使う。なければ作る。

```sh
backlog task create "<タイトル>" -l <area> -d "<要件の 4 行と、あれば UI モックの行>"
```

- 以後の経過はすべてタスクの Implementation Notes に追記する(`backlog task edit <id> --append-notes "<経過>"`)。`--notes` は既存の Notes を置換するので使わない。日付ごとのファイルを作らない。

## 4. ブランチを切る

- `main` を最新にし、`<type>/<TASK-id>-<slug>` の名前でブランチを切る(`type` は `feat`・`fix`・`refactor`・`chore`。タスクが無いときは `<type>/<slug>`)。
- git hook が無ければ入れる(`references/hooks.md`)。pre-commit で lint、pre-push でテストを実行する。hook は implementer の「テストが通った」という報告を機械的に裏づける。
- 品質がプロダクトのとき、シークレット検知と依存監査を hook と CI に入れ、CI に SAST を入れる(`references/hooks.md` 4.)。
- 手順の詳細は `references/git-flow.md` に従う。
- リポジトリの規約が `main` への直接コミットを定めているとき(private の設定リポジトリなど)は、ブランチと PR を省き、`main` 上でステップごとにコミットする。実装と点検のループはそのまま行う。

## 5. 計画する

- planner サブエージェント(`dev-skills:planner`)を起動し、要件の 4 行(目的・完了条件・対象外・品質)、UI モックの行があればその行、タスクに受け入れ条件があればその一覧、対象リポジトリのパスを渡す。
- 変更するファイルが明らかで 1 ステップで済む変更(誤字の修正、設定値の変更、1 関数の追加など)は、planner を起動せず統括が planner と同じ形式で計画を書く。品質がプロダクトのときは、統括も secure・observe・recover を読んで計画に反映する。UI を含むときは design-ui も読む。UI モックの行が brief.md のパスなら、計画の「利用者に見せる文言」の表は brief の文言の表を写す。reviewer は省かない。
- planner は計画を返す。統括は計画をユーザーに見せ、承認を得てからタスクの Implementation Notes に記録する。UI を含むときは、統括は承認の前に計画の「利用者に見せる文言」の表を照合する。UI モックの brief があれば、表が brief の文言の表と一致するかを確かめる。状態名の後ろに「(brief に無い状態、planner が決めた)」または「(brief の未決事項、planner が決めた)」と付けた行と、UI モックが無いときの表は、design-ui の `references/text.md` 8. に照らす。ユーザーが最初から「全部進めて」と指示しているときは、計画を報告して先へ進む(未確定事項の扱いは次の箇条)。
- 統括は計画の未確定事項を 1 件ずつ処理する。決め方が「事実」のものは統括が調べて決め、根拠を Implementation Notes に書く。調べても決まらないとき、または調べた結果が要件の行と両立しないときは、本人の判断として扱う。統括は決め方を本人の判断から事実へ変えない。「本人の判断」のものは、依存するステップの前にユーザーに 1 問ずつ聞き、答えを Implementation Notes に書く。既定で進めて完了時にまとめて確認することはしない。要件の行に反する既定は置かない。「全部進めて」の指示は計画の承認を省くものであり、本人の判断が必要な未確定事項には及ばない。build の反復では、build の要判断の扱い(決め方を問わず反復を止める)に従う。
- 計画のステップは 1 つずつ実装とレビューを回せる大きさにする。1 ステップが 1 コミットになるので、レビューの範囲が明確になり、問題があればそのコミットだけを戻せる。

## 6. 実装と点検のループ

ステップごとに次を繰り返す。サブエージェントは毎回新しく起動し、前のステップの会話を引き継がない。前のステップの試行錯誤が次のステップの判断に混ざるのを防ぎ、reviewer が実装の経緯を知らずに結果だけを見る状態を保つためである。

1. ステップ開始時の HEAD の SHA を `git rev-parse HEAD` で取り、文字列として控える。シェル変数は次のコマンドに引き継がれないので使わない。この SHA が reviewer に渡す範囲の起点になる。
2. implementer サブエージェント(`dev-skills:implementer`)を起動する。渡すのは、対象リポジトリのパス、ブランチ名、そのステップの計画(変更するファイル・手順・完了条件・検証コマンド)、変更してよい範囲、要件の品質の行である。implementer は実装してテストを通し、コミットして、変更ファイルとテスト結果を報告する。
3. reviewer サブエージェント(`dev-skills:reviewer`)を起動する。渡すのは、対象リポジトリのパス、レビューする範囲(`<控えた SHA>..HEAD`)、そのステップの計画、implementer の報告事項、要件の品質の行である。reviewer は「承認」か「要修正」と修正点の一覧を返す。
4. 要修正なら、修正点をそのまま implementer に渡して直させ、再び reviewer に点検させる。3 回直しても承認されないときは、計画か指摘のどちらかに無理があるので、統括がユーザーに状況を報告して判断を仰ぐ。
5. 承認されたら、ステップの結果をタスクの Implementation Notes に書き、ユーザーに進捗を報告する。

5.〜8. のどの時点でも、ユーザーが計画・実装・文言・PR を直させたときは、そのつど「ユーザーの指摘」として Implementation Notes に書く。retro が後から Notes を読んで指摘を集めるためである。

統括は各報告を鵜呑みにせず、検証コマンドの実行結果と `git log`・`git diff` で検収する。サブエージェントの報告は要約であり、報告と実物が食い違うことがある。

## 7. ゲートを通す

- 全ステップが承認されたら、push の前に gate-reviewer サブエージェント(`dev-skills:gate-reviewer`)を起動する。渡すのは、対象リポジトリのパス、レビューする範囲(`main..HEAD`)、要件の 3 行(目的・完了条件・対象外)、計画の全体、PR 本文案である。
- Claude Code では、品質がプロダクトのとき、gate-reviewer を起動する前に統括が組み込みの `/security-review` を実行する。指摘があれば implementer に渡して直させ、直したあとで gate-reviewer を起動する。
- gate-reviewer はブランチ全体でしか分からないこと(完了条件の充足、ステップ間の整合、残骸、PR 本文との一致)を見て、「マージ可」か「差し戻し」を返す。ステップごとの reviewer が見た内容は蒸し返さない。品質がプロダクトのとき、計画に含まれる secure・observe・recover 由来の変更(ヘルスチェック・メトリクス・拒否のテスト・タイムアウト・エラーページなど)は要件内として扱う。
- 差し戻しなら、修正点を implementer に渡して直させ、再びゲートを通す。2 回直しても通らないときは、統括がユーザーに状況を報告して判断を仰ぐ。ゲートを push の前に通すのは、CI を回す前に直すほうが安いからである。

## 8. PR を出す

- ゲートを通ったら push し、PR を作る。本文はゲートに渡した本文案を、指摘があれば直して使う。
- CI の結果を確認する。失敗したら、失敗ログを implementer に渡して直させ、再 push して再確認する。
- PR のマージはユーザーの指示を得てから行う。手順は `references/git-flow.md` に従う。

## 9. 閉じる

- マージ後に `main` を更新し、作業ブランチを削除する。
- タスクを Done にし、Final Summary に結果(何ができるようになったか、PR 番号、残した課題)を書く。

```sh
backlog task edit <id> -s Done --final-summary "<結果>"
```

- 本人の指摘(ユーザーが計画・実装・文言・PR を直させた指摘)が 1 回以上あったタスクでは、Final Summary を書いた後に retro(`dev-skills:retro`)を実行する。build の反復では実行しない(retro 1.)。

## 10. 参照ファイル

| ファイル | 内容 | 読むとき |
| :-- | :-- | :-- |
| `references/requirements.md` | 要件の 4 行の形式、聞く範囲、品質の決め方 | 要件を確かめるとき |
| `references/git-flow.md` | ブランチ・コミット・push・PR・CI 確認・マージのコマンド | ブランチを切るとき、PR を出すとき |
| `references/hooks.md` | git hook(lefthook・husky)の導入、シークレット検知と依存監査、CI での同じ検査と SAST | hook が無いリポジトリで作業を始めるとき、品質がプロダクトのとき |

サブエージェントの定義(`agents/`)は統括が読まなくてよい。役割と出力形式はサブエージェント自身が持つ。
