# 開発の手順

本スキルは統括セッションが読む。統括の仕事は計画・委譲・検収・PR である。サブエージェントを起動できない CLI(Codex CLI・Antigravity CLI)では、統括が planner・implementer・reviewer・gate-reviewer の役割を 1 つずつ順に受け持ち、役割を切り替えるたびに前の役割の判断を引き継がずに `agents/` の各ファイルの手順で作業する。その CLI に無い機能を使う手順(サブエージェントの `effort`・`/security-review` など)に当たったら省いた手順と理由を 1 行でユーザーに報告して次の手順へ進む。止まって聞かない。報告が無いとユーザーは手順が省かれたことに気付かない。コードは書かない。書くのは implementer サブエージェント、点検するのは reviewer と gate-reviewer サブエージェントである。ただし試作と診断(5. の未確定事項を確かめる試作を含む)で作業ツリーの外に作る使い捨てのスクリプトは統括が書く(`references/kinds.md` 1.)。統括がコードを書かない理由は 2 つある。統括の文脈をタスク全体の判断に使い続けること、そして書いた本人がレビューする状態を避けることである。

## 1. 工程

| 工程 | 担当 | 成果 |
| :-- | :-- | :-- |
| 要件を確かめる | 統括 | 目的・完了条件・対象外・品質の 4 行(新しい Web の画面・フォームを作るときは UI モックの行も書く) |
| タスクを決める | 統括 | Backlog.md のタスク(既存または新規) |
| ブランチを切る | 統括 | `main` から切ったブランチと、有効な git hook |
| 計画する | planner(小さな変更では統括) | ステップごとの完了条件を持つ計画 |
| 実装する | implementer | ステップ 1 つ分のコミット |
| 点検する | reviewer | 承認、または修正点の一覧 |
| ゲートを通す | gate-reviewer | ブランチ全体のマージ可の判定 |
| PR を出す | 統括 | push・PR・CI の通過 |
| 閉じる | 統括 | マージ後のタスクの Final Summary |

作業を始めるときは工程の表を todo(CLI のタスク管理の機能)に写す。省く工程(要件の確認・計画など)も todo から外さずに `省略: <理由>` と書いて残す。省いた工程が todo に無いとユーザーは省いたのか忘れたのかを区別できない。中断と再開は工程の途中で起きる操作である。手順は 10.(中断する)と 11.(再開する)に従う。

各工程の終わりに、ユーザーへ 1 行で進捗を報告する(例: 「ステップ 2/4 完了: `a1b2c3d` 承認」)。ユーザーは途中の会話を追っていない前提で書く。

## 2. 要件を確かめる

要件の 4 行(目的・完了条件・対象外・品質)と UI モックの行の形式・聞く範囲・品質の決め方は、`references/requirements.md` に従う。

- 依頼に 4 行が揃っていれば、次の箇条の UI モックの確認を除いてこの工程を省く。品質だけが無いときは質問せず、`references/requirements.md` 3. の決め方で品質を書く。ほかの行が欠けていれば、統括がユーザーに 1 問ずつ、最大 3 問まで聞く。一度に列挙しないのは、答えによって次に聞くべきことが変わるからである。
- 新しい Web の画面・フォームを作るタスクで依頼に UI モックの行が無ければ、4 行が揃っていても、4 行の確認の後に、UI モックを先に作るか不要かを 1 問聞く。この 1 問は、最大 3 問には数えない。既存の画面の変更では聞かない。
  - 先に作ると答えたら、design-ui の `references/session.md` の工程で UI モックを作るよう示して停止する。タスクもブランチも作らない。
  - 不要と答えたら、UI モックの行に `不要` と書く。
- 統括は関係するコードを読んで要件を満たす期待する最小の変更(変える箇所と規模の見込み)を 1 文で書く。この見込みを 4 行の確認に添えてユーザーに示す。この工程を省くときは最初の進捗の報告に添える。見込みを示すと依頼の読み違いを計画の前に見つけられる。見込みは実現方針の決定ではない。方針は planner が確定する(`references/requirements.md` 2.)。
- 統括は `references/kinds.md` 1. に従ってタスクの種類(バグ修正・リファクタ・性能・試作・移行)を見分ける。見分けた種類は 4 行の確認に添える。どれにも当たらないタスク(機能の追加と変更)では添えない。試作と診断だけの依頼ではブランチと PR を作らない(`references/kinds.md` 1.)。3. 以降の工程は省く。`references/kinds.md` 2.3 または 5. の手順で報告して停止する。
- 調べた結果が依頼された変更を不要か不可とするとき(既に実装されている・前提の機能が無いなど)は根拠(ファイルと行・コマンドの出力)を示して止まる。タスクもブランチも作らない。不要な変更を進めると使われない差分か動かない差分が残る。
- 依頼の完了条件に確かめ方(`references/requirements.md` 1.)が無いときは統括が補う。補った確かめ方は 4 行の確認で示す。
- 結果を 4 行(UI モックの行があればその行も含める)にまとめ、ユーザーに確認する。これらの行がタスクの本文と planner への入力になる。

## 3. タスクを決める

- `backlog` コマンドは、Backlog.md を初期化したリポジトリのルートで実行する(サブモジュールの中では動かない)。Backlog.md が無いリポジトリでは、この工程を省き、計画と経過を PR 本文に書く。
- 既存のタスクがあればその id を使う。なければ作る。

```sh
backlog task create "<タイトル>" -l <area> -d "<要件の 4 行と、あれば UI モックの行>"
```

- 以後の経過はすべてタスクの Implementation Notes に追記する(`backlog task edit <id> --append-notes "<経過>"`)。`--notes` は既存の Notes を置換するので使わない。日付ごとのファイルを作らない。
- Notes の 1 件は判断・理由・根拠・結果の 4 行で書く。根拠は文章でなく所在(コミットの SHA・PR 番号・ファイルと行・ログの置き場)で示す。結果は承認・テスト通過・差し戻し・戻した・未決のような状態で書く。後から読む人(retro・再開する統括)は根拠をたどって判断を確かめる。

```sh
backlog task edit <id> --append-notes $'判断: <選んだこと・したこと>\n理由: <選んだ理由>\n根拠: <SHA・PR 番号・ファイルと行・ログの置き場>\n結果: <承認・テスト通過・戻した・未決など>'
```

- ユーザーの指摘(6.)は判断の行を「ユーザーの指摘」で始める。計画の全文(5.)と再開メモ(10.)はこの形に入れずにそれぞれの形で書く。

## 4. ブランチを切る

- `main` を最新にし、`<type>/<TASK-id>-<slug>` の名前でブランチを切る(`type` は `feat`・`fix`・`refactor`・`chore`。タスクが無いときは `<type>/<slug>`)。
- git hook が無ければ入れる(`references/hooks.md`)。pre-commit で lint、pre-push でテストを実行する。hook は implementer の「テストが通った」という報告を機械的に裏づける。
- 品質がプロダクトのとき、シークレット検知と依存監査を hook と CI に入れ、CI に SAST を入れる(`references/hooks.md` 4.)。
- 手順の詳細は `references/git-flow.md` に従う。
- リポジトリの規約が `main` への直接コミットを定めているとき(private の設定リポジトリなど)は、ブランチと PR を省き、`main` 上でステップごとにコミットする。実装と点検のループはそのまま行う。

## 5. 計画する

- planner サブエージェント(`dev-skills:planner`)を起動し、要件の 4 行(目的・完了条件・対象外・品質)、UI モックの行があればその行、タスクに受け入れ条件があればその一覧、タスクの種類があればその種類、対象リポジトリのパスを渡す。
- 変更するファイルが明らかで 1 ステップで済む変更(誤字の修正、設定値の変更、1 関数の追加など)は、planner を起動せず統括が planner と同じ形式で計画を書く。品質がプロダクトのときは、統括も secure・observe・recover を読んで計画に反映する。UI を含むときは design-ui も読む。UI モックの行が brief.md のパスなら、計画の「利用者に見せる文言」の表は brief の文言の表を写す。reviewer は省かない。
- planner は計画を返す。統括は計画をユーザーに見せ、承認を得てからタスクの Implementation Notes に記録する。UI を含むときは、統括は承認の前に計画の「利用者に見せる文言」の表を照合する。UI モックの brief があれば、表が brief の文言の表と一致するかを確かめる。状態名の後ろに「(brief に無い状態、planner が決めた)」または「(brief の未決事項、planner が決めた)」と付けた行と、UI モックが無いときの表は、design-ui の `references/text.md` 8. に照らす。ユーザーが最初から「全部進めて」と指示しているときは、計画を報告して先へ進む(未確定事項の扱いは次の箇条)。
- 統括は計画の未確定事項を 1 件ずつ処理する。決め方が「事実」のものは統括が調べて決め、根拠を Implementation Notes に書く。事実には実行して観測できる事実(試作・計測で決まるもの)を含む。調べても決まらないとき、または調べた結果が要件の行と両立しないときは、本人の判断として扱う。統括は決め方を本人の判断から事実へ変えない。「本人の判断」のものは、依存するステップの前にユーザーに 1 問ずつ聞き、答えを Implementation Notes に書く。質問には planner の推奨・根拠・リスクを付けて本人が返答だけで決められる形にする。案から選ぶ問いではリスクの代わりに各案の得るものと費用を付ける。本人の答えを待つステップを完了と報告しない。既定で進めて完了時にまとめて確認することはしない。要件の行に反する既定は置かない。「全部進めて」の指示は計画の承認を省くものであり、本人の判断が必要な未確定事項には及ばない。build の反復では、build の要判断の扱い(決め方を問わず反復を止める)に従う。
- 計画のステップは 1 つずつ実装とレビューを回せる大きさにする。1 ステップが 1 コミットになるので、レビューの範囲が明確になり、問題があればそのコミットだけを戻せる。

## 6. 実装と点検のループ

ステップごとに次を繰り返す。サブエージェントは毎回新しく起動し、前のステップの会話を引き継がない。前のステップの試行錯誤が次のステップの判断に混ざるのを防ぎ、reviewer が実装の経緯を知らずに結果だけを見る状態を保つためである。

Claude Code ではサブエージェントを起動するたびに Agent の `effort` をジョブに合わせて選ぶ。planner と gate-reviewer の起動にも当てはまる。`effort` を渡さなければセッションの値で動く。この値を出発点にする。最も難しいジョブ(横断的な設計・並行処理・自明でない欠陥の点検)ではセッションの値が `high` より低いときだけ `high` を渡す。定型作業(誤字の修正・設定値の変更・機械的な置き換え)ではセッションの値が `low` より高いときだけ `low` を渡す。選ぶのは起動ごとの引数である。agents の frontmatter は書き換えない。この選び方は Claude Code に限る。Codex CLI・Antigravity CLI では統括が役割を受け持つためである。

1. ステップ開始時の HEAD の SHA を `git rev-parse HEAD` で取り、文字列として控える。シェル変数は次のコマンドに引き継がれないので使わない。この SHA が reviewer に渡す範囲の起点になる。
2. implementer サブエージェント(`dev-skills:implementer`)を起動する。渡すのは、対象リポジトリのパス、ブランチ名、そのステップの計画(変更するファイル・手順・完了条件・検証コマンド)、変更してよい範囲、要件の品質の行である。implementer は実装してテストを通し、コミットして、変更ファイルとテスト結果を報告する。Claude Code ではこのループで起動するサブエージェントに大きな出力(テストの全ログ・長い差分・調査の生データ)を作業ツリーの外のファイルに書かせてパスと要約で報告させる。
3. reviewer サブエージェント(`dev-skills:reviewer`)を起動する。渡すのは、対象リポジトリのパス、レビューする範囲(`<控えた SHA>..HEAD`)、そのステップの計画、implementer の報告事項、要件の品質の行、タスクの種類があればその種類である。reviewer は「承認」か「要修正」と修正点の一覧を返す。
4. 要修正なら新しい implementer を起動して直させる。前の implementer を再開しない。渡すのは手順 2 で渡したもの(ステップの計画を含む)・reviewer の修正点(要約せずそのまま)・前回の implementer の報告である。前の会話を再開すると後から加えた指示が伝わらないことがある。7.・8. で implementer に直させるときも同じである。直したら再び reviewer に点検させる。同じ前提を共有する修正が 2 回続けて同じ指摘で要修正になることがある。そのときは 3 回目の修正を implementer に渡す前に統括がその前提を 1 文で書き出す。次に、前提が偽なら結果が変わる観測を 1 つ行う。観測は統括が読み取りのコマンドで行うか implementer に依頼する。観測では指摘や失敗の大きさだけでなく出る箇所の分布も見る。前提と観測の結果は Implementation Notes に書く。前提が否定されたら原因を前提の外で探してから修正点を渡す。implementer が同じ形の回避策の必要を報告して止まったときは修正を重ねない。reviewer の指摘が同じ形の回避策を 2 か所以上で求めたときも同じである。統括は承認されていない変更(止まった implementer の未コミットの変更・要修正になったステップのコミット)を手順 1 で控えた SHA まで戻して破棄してから計画の設計を捨てて planner を新しく起動する。渡すのは 5.(計画する)で渡すものに加えて回避策の箇所と形と承認済みのステップのコミットである。planner はその制約が最初からあったものとして設計し直す。承認済みのコミットを残すか戻すかは新しい計画の方針に書かせる。新しい計画のステップでは修正の回数を数え直す。新しい計画は 5. と同じく本人の承認を経る。3 回直しても承認されないときは、計画か指摘のどちらかに無理があるので、統括がユーザーに状況を報告して判断を仰ぐ。
5. 承認されたら、ステップの結果をタスクの Implementation Notes に書き、ユーザーに進捗を報告する。

5.〜8. のどの時点でも、ユーザーが計画・実装・文言・PR を直させたときは、そのつど「ユーザーの指摘」として Implementation Notes に書く。retro が後から Notes を読んで指摘を集めるためである。

作業中に dev-skills の規範の不具合(手順どうしの矛盾・実行できない手順・誤ったコマンド)を見つけたらその場で規範を直さずに dev-skills の改善のタスクとして backlog に起票する。起票したら作業を続ける。回避した方法は Implementation Notes に書く。規範を直すのは retro と同じく別のタスクである。止まると目の前のタスクが進まない。記録せずに回避すると次のタスクで同じ不具合に当たる。

統括は各報告を鵜呑みにせず、検証コマンドの実行結果と `git log`・`git diff` で検収する。サブエージェントの報告は要約であり、報告と実物が食い違うことがある。

## 7. ゲートを通す

- 全ステップが承認されたら、push の前に gate-reviewer サブエージェント(`dev-skills:gate-reviewer`)を起動する。渡すのは、対象リポジトリのパス、レビューする範囲(`main..HEAD`)、要件の 3 行(目的・完了条件・対象外)、計画の全体、PR 本文案である。
- Claude Code では、品質がプロダクトのとき、gate-reviewer を起動する前に統括が組み込みの `/security-review` を実行する。指摘があれば implementer に渡して直させ、直したあとで gate-reviewer を起動する。
- gate-reviewer はブランチ全体でしか分からないこと(完了条件の充足、ステップ間の整合、残骸、PR 本文との一致)を見て、「マージ可」か「差し戻し」を返す。ステップごとの reviewer が見た内容は蒸し返さない。品質がプロダクトのとき、計画に含まれる secure・observe・recover 由来の変更(ヘルスチェック・メトリクス・拒否のテスト・タイムアウト・エラーページなど)は要件内として扱う。
- 差し戻しなら、修正点を implementer に渡して直させ、再びゲートを通す。2 回直しても通らないときは、統括がユーザーに状況を報告して判断を仰ぐ。ゲートを push の前に通すのは、CI を回す前に直すほうが安いからである。

## 8. PR を出す

- ゲートを通ったら push し、PR を作る。本文はゲートに渡した本文案を、指摘があれば直して使う。
- PR のレビューコメントを `references/review-triage.md` に従って fix・dismiss・ask に分ける。fix は implementer に直させる。dismiss には反証を返信する。ask はユーザーに 1 問で聞く。修正は 1 回の push にまとめる。push のたびに CI が最初から実行されるためである。レビューコメントと CI の失敗が両方あるときは先にコメントを仕分ける。CI の失敗の直しも同じ push に含める。
- CI の結果を確認する。失敗したら `references/git-flow.md` 4. の分類に従って直させるか再実行する。
- PR のマージはユーザーの指示を得てから行う。手順は `references/git-flow.md` に従う。

## 9. 閉じる

- マージ後に `main` を更新し、作業ブランチを削除する。
- タスクを Done にし、Final Summary に結果(何ができるようになったか・PR 番号・残した課題・次にこのコードを触る人が知るべきこと)を書く。次に触る人が知るべきことは前提・落とし穴・`shortcut:` を残した箇所である。差分とコミットメッセージからは読み取りにくい。

```sh
backlog task edit <id> -s Done --final-summary "<結果>"
```

- 本人の指摘(ユーザーが計画・実装・文言・PR を直させた指摘)が 1 回以上あったタスクでは、Final Summary を書いた後に retro(`dev-skills:retro`)を実行する。build の反復では実行しない(retro 1.)。

## 10. 中断する

ユーザーが中断を明示したときだけ止まる。「続けて」「寝るので進めて」は中断の指示ではない。中断の目的は別のセッションが会話の文脈なしで続きから再開できる状態を残すことである。

1. 安全な境界で止める。新しいステップもサブエージェントも始めない。動いているサブエージェントを止める。
2. 中断のために取り消せない操作をしない。PR をまだ出していなければ push も PR の作成もしない。
3. 未コミットの変更はコミットせずに作業ツリーに残すか `git stash push -m "<TASK-id> 中断"` で退避する。途中の変更は pre-commit の lint を通らないことがある。`--no-verify` は使わない(`references/git-flow.md` 2.)。途中のコミットが入ると reviewer に渡す範囲が 1 ステップ 1 コミットにならない。
4. 再開メモを Implementation Notes に書く。Backlog.md が無いリポジトリでは PR 本文に書く。PR が無ければユーザーへの報告に書く。

   ```sh
   backlog task edit <id> --append-notes $'再開メモ\n意図: <要件の目的・中断した工程とステップ>\nブランチ: <ブランチ名>\n済んだステップ: <承認済みのステップと SHA>\n未コミットの変更: <なし / 作業ツリー / stash の名前>と変更したファイル\n次の手: <再開して最初に行うこと>'
   ```

5. 止まった位置・再開メモの所在・作業ツリーの状態をユーザーに報告する。

## 11. 再開する

中断・セッションの終了・別のエージェントからの引き継ぎの後で途中のタスクを続けるときは次の手順で再開点を判断する。記録を読まずにやり直すと済んだステップを二重に行う。

1. タスクの Implementation Notes を読んで再開メモ・承認済みのステップ・未決の事項を拾う。Backlog.md が無いリポジトリでは PR 本文を読む。
2. タスクのブランチ(`git branch --list '*<TASK-id>*'` で探す。`main` へ直接コミットするリポジトリでは `main`)へ切り替える。ブランチと PR の実物を確かめる。`git log --oneline main..HEAD`・`git status`・`git stash list`・`gh pr view --json number,state,statusCheckRollup` を実行する。PR が無ければ `no pull requests found` が出る。PR を出す前として扱う。
3. 再開点を判断する。Notes で承認済みとされていて SHA が現在のブランチの履歴にある(`git merge-base --is-ancestor <SHA> HEAD` の終了コードが 0)ステップを済んだステップとする。済んだステップは繰り返さない。計画も作り直さない。Notes にあっても SHA が履歴に無いステップは済んだと数えない。
4. 未コミットの変更が作業ツリーか stash にあれば作業ツリーに戻す。そのステップは 6. の手順 1 から行う。implementer には再開メモと未コミットの変更の所在も渡す。
5. 再開点・引き継いだもの・やり直したものを 1 行でユーザーに報告してから再開点の工程へ進む。

build の反復が In Progress のタスクを取ったときも本節で再開点を判断する。どのタスクを取るかは build 4. の手順 2 に従う。タスクの中のどこから続けるかは本節に従う。

## 12. 参照ファイル

| ファイル | 内容 | 読むとき |
| :-- | :-- | :-- |
| `references/requirements.md` | 要件の 4 行の形式、聞く範囲、品質の決め方 | 要件を確かめるとき |
| `references/git-flow.md` | ブランチ・コミット・push・PR・CI 確認・マージのコマンド | ブランチを切るとき、PR を出すとき |
| `references/review-triage.md` | PR のレビューコメントを fix・dismiss・ask に分ける基準と dismiss の返信と却下のパターンの一覧 | PR にレビューコメントが付いたとき |
| `references/kinds.md` | バグ修正・リファクタ・性能・試作・移行の種類ごとに最初に固定するもの・進め方・止まる条件 | 要件を確かめるときに種類を見分けるとき |
| `references/hooks.md` | git hook(lefthook・husky)の導入、シークレット検知と依存監査、CI での同じ検査と SAST | hook が無いリポジトリで作業を始めるとき、品質がプロダクトのとき |
