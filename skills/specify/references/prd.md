# PRD の雛形

PRD(製品要求仕様書)は次の雛形から書く。要求 1 項目は、build 3. の `backlog task create` の引数へそのまま写せる形にする。

## 1. 雛形

```markdown
# PRD: <名前>

## 1. 背景と利用者

<誰が、どんな場面で、何に困っているか>

## 2. 対象外

- <この製品で作らないもの>

## 3. 品質

<簡易 / プロダクト>(<そう決めた理由>)

## 4. 要求一覧

### R1. <タイトル>

目的: <誰の何を解決するか>
完了条件: <満たしたら終わりと言える挙動>
対象外: <この要求でやらないこと>
品質: <簡易 / プロダクト>

受け入れ条件:

- <検証できる条件 1>
- <検証できる条件 2>

### R2. <タイトル>

目的: <誰の何を解決するか>
完了条件: <満たしたら終わりと言える挙動>
対象外: <この要求でやらないこと>
品質: <簡易 / プロダクト>

受け入れ条件:

- <検証できる条件 1>

## 5. 依存と順序

| 要求 | 依存先 |
| :-- | :-- |
| R1 | なし |
| R2 | R1 |

## 6. 未決事項

- <答えが出なかった問い>(<影響する要求の ID>)
```

## 2. 節と行の書き方

| 節・行 | 意味と書き方 | build 3. での写し先 |
| :-- | :-- | :-- |
| `# PRD: <名前>` | 作る製品または機能の名前 | 写さない |
| `1. 背景と利用者` | 誰が、どんな場面で、何に困っているか。各要求の目的の行は、ここから導く | 写さない。分解するときに読む文脈になる |
| `2. 対象外` | 製品全体で作らないもの | 写さない。要求ごとの対象外は、要求の対象外の行に書く |
| `3. 品質` | 製品全体の既定の品質と、その理由。develop 2. の決め方で決める | 写さない。要求の品質の行の既定値になる |
| `### R<n>. <タイトル>` | 1 つの PR で実装できる要求。ID は R1 からの連番とする。要求を削除しても、ほかの要求の ID は変えない | `backlog task create` のタイトル |
| 4 行(`目的:`・`完了条件:`・`対象外:`・`品質:`) | develop 2. の要件の形式。品質は、3. と異なる要求だけ変える | `-d`(`$'目的: ...\n完了条件: ...'` の形で渡す) |
| `受け入れ条件:` の箇条 | 1 件を 1 箇条にし、コマンドの結果や画面の挙動など検証できる形で書く。1 要求に 1 件以上 | 1 件ごとに `--ac` |
| `5. 依存と順序` | 全要求を実装の順に 1 行ずつ並べる。依存先は要求一覧の ID で書き、複数なら `R1, R2`、無ければ `なし` とする。依存先の要求は、依存する要求より上の行に並べる | 表の行の順にタスクを作り、依存先の ID をその要求から作ったタスクの ID(`TASK-12` の形)に置き換えて `--dep` に渡す。複数なら `--dep TASK-1,TASK-2` のようにカンマで区切る |
| `6. 未決事項` | 答えが出なかった問いと、影響する要求の ID。無ければ `なし` とする | 写さない。build 3. でユーザーに聞く問いの候補になる |
