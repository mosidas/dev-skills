# 着想からの PRD の作成

本スキルは、曖昧な着想から、ユーザーとの対話で PRD(製品要求仕様書)を書く。PRD は build の入力である。build がそのままタスクに分解できるよう、PRD の要求 1 項目は、develop 2. の要件の 4 行と build 3. の `--ac`・`--dep` に写せる形にする。

## 1. 工程

| 工程 | 担当 | 成果 |
| :-- | :-- | :-- |
| 聞く | 統括(ユーザーとの対話) | PRD の各節への答えと、答えが出なかった問い |
| PRD を書く | 統括(ユーザーとの対話) | 雛形から書いた PRD のファイル |
| 確かめて終える | 統括(ユーザーとの対話) | ユーザーが承認した PRD と、次の一手の提示 |

## 2. 聞く

- 聞く範囲は develop 2. に従う。
- 1 問ずつ聞く。答えによって次に聞くべきことが変わるため、一度に列挙しない。
- develop 2. の最大 3 問では、着想から PRD の 6 節を埋められない。そのため質問数の上限は設けず、4. の終了条件を満たすまで聞く。
- 雛形(`references/prd.md`)の節の順に埋める。順序は、背景と利用者、対象外、品質、要求一覧、依存と順序である。受け入れ条件は要求ごとに聞く。
- 推測で埋めない。答えが出ないものは、PRD の未決事項に書く。ただし品質は、3. の決め方で書く。

## 3. PRD を書く

- `references/prd.md` の雛形から書く。各節の書き方と build 3. への写し方は、同ファイルの表に従う。
- 1 つの要求を 1 つの PR の大きさにする(build 3. と同じ)。1 つの PR に収まらない要求は、複数の要求に分ける。
- 要求の 4 行(目的・完了条件・対象外・品質)は develop 2. の形式で書き、品質は develop 2. の決め方で決める。
- 受け入れ条件は、コマンドの結果や画面の挙動など、検証できる形で書く。build 4. の反復が、受け入れ条件を 1 件ずつコマンドの結果や差分で確かめるためである。
- PRD にシークレット・個人情報を書かない。PRD はリポジトリにコミットされ、build の反復のセッションも読む。認証情報などが要求に関わるときは、値でなく置き場所(環境変数の名前など)を書く。
- 保存先はユーザーに聞く。既定のパスは、backlog を初期化したリポジトリのルートからの `docs/prd/<slug>.md` である。

## 4. 終了条件

次をすべて満たしたら終える。

- 雛形の全節が埋まっている。
- 各要求が、4 行と 1 件以上の受け入れ条件を持つ。
- 依存と順序の表の依存先が、すべて要求一覧の ID を指す。
- ユーザーが PRD を承認した。

ユーザーが途中で打ち切ったら、埋まっていない節と答えの出ていない問いを未決事項に書いて終える。

最後に、PRD のパスと次の一手をユーザーに示す。次の一手は「build で PRD をタスクに分解する」である。打ち切ったときの PRD は承認されていないため、「未決事項を解消してから build で分解する」と示す。

## 5. 参照ファイル

| ファイル | 内容 | 読むとき |
| :-- | :-- | :-- |
| `references/prd.md` | PRD の雛形と、節ごとの書き方・build 3. への写し方 | PRD を書くとき |
| `../develop/SKILL.md` | 要件の 4 行の形式と品質の決め方(2.) | 要求の 4 行を書くとき |
| `../build/SKILL.md` | PRD をタスクに分解する手順(3.)と、受け入れ条件の確かめ方(4.) | 要求の大きさ・受け入れ条件・依存を決めるとき |
