# 着想からの PRD の作成

本スキルは、曖昧な着想から、ユーザーとの対話で PRD(製品要求仕様書)を書く。PRD は build の入力である。build がそのままタスクに分解できるよう、PRD の要求 1 項目は、要件の 4 行(`../develop/references/requirements.md`)と build 3. の `--ac`・`--dep` に写せる形にする。

## 1. 工程

| 工程 | 担当 | 成果 |
| :-- | :-- | :-- |
| 聞く | 統括(ユーザーとの対話) | 聞くたびに答えを書き進めた PRD のファイルと、答えが出なかった問い |
| PRD を書く | 統括(ユーザーとの対話) | 全節を埋め、コメントを削除した PRD のファイル |
| 確かめて終える | 統括(ユーザーとの対話) | ユーザーが承認した PRD と、次の一手の提示 |

要求が 1 つ(1 つの PR)に収まるときは、PRD を書かない。要件の 4 行(`../develop/references/requirements.md`)にまとめてユーザーに確認し、次の一手として develop での実装を示して終える。聞く途中で 1 つに収まると分かったときは、制約と決定事項と未決事項に書いた内容を 4 行に添えてユーザーに示す。次の一手には、その内容を develop で planner への入力に加えることを書き、そのあとでコピーした PRD のファイルを削除する。

## 2. 聞く

- 聞く範囲は `../develop/references/requirements.md` に従う。
- 1 問ずつ聞く。答えによって次に聞くべきことが変わるため、一度に列挙しない。ユーザーの答えを評価する言葉(「いいですね」など)を挟まず、次の問いへ進む。
- 対象リポジトリや既存の文書で答えが出る問いは、先に調べる。試して分かることも、先に試す。調べて答えが出たことは、結果を示してユーザーの確認を得る。調べても試しても決まらないことだけを、問いとして聞く。
- develop 2. の最大 3 問では、着想から PRD の 7 節を埋められない。そのため質問数の上限は設けず、4. の条件を満たすまで聞く。
- 聞き始める前に保存先を聞き、雛形をコピーする。既定の保存先は、backlog を初期化したリポジトリのルートからの `docs/prd/<slug>.md` である。答えは聞くたびに PRD のファイルへ書く。対話の進み具合を会話でなく PRD のファイルに持つため、中断しても PRD のファイルから再開できる。
- 5〜8 問ごとに、埋まった節・未決の問い・今聞いている節をユーザーに示す。
- 雛形(`references/prd.md`)の節の順に埋める。順序は、背景と利用者、対象外、品質、制約と決定事項、要求一覧、依存と順序である。要求一覧では、1 つの要求の目的・完了条件・対象外・受け入れ条件・依存を聞き終えてから、次の要求へ移る。依存は要求ごとに聞いて依存と順序の表へ書き、表の並べ替え(3.)は全要求を聞き終えてから行う。
- 推測で埋めない。答えが出ないもの、ユーザーが後回しにした問いは、PRD の未決事項に書いて次の問いへ進む。ただし品質は、3. の決め方で書く。
- 問いは次の 5 つの型から選ぶ。答えは、表の書き先の節に書く。

| 型 | 問い | 書き先 |
| :-- | :-- | :-- |
| 範囲 | これは対象内か、対象外か | 製品全体なら PRD の 2.(対象外)、要求ごとなら要求の対象外の行 |
| 境界 | この入力・状態のときはどうなるか | 受け入れ条件 |
| 失敗 | 失敗したとき、利用者は何を見るか | 受け入れ条件 |
| 順序と依存 | 先に必要なものは何か | 依存と順序 |
| 代替 | なぜこの方法か | 制約と決定事項 |

## 3. PRD を書く

- 2. でコピーした PRD のファイルで、各節の直下のコメントに従って残った `<...>` を埋める。コメントは、すべての節を埋めたあとに削除する。
- 1 つの要求を 1 つの PR の大きさにする(build 3. と同じ)。1 つの PR に収まらない要求は、複数の要求に分ける。
- build 4. の反復は、受け入れ条件を要求ごとに単独で確かめる。そのため要求は、単独で動かして確かめられる縦の一切れにし、DB だけ・API だけのような層ごとの横割りにしない。
- 要求の 4 行(目的・完了条件・対象外・品質)は、`../develop/references/requirements.md` の形式と品質の決め方に従って書く。
- 受け入れ条件は、コマンドの結果や画面の挙動など、検証できる形で書く。build 4. の反復が、受け入れ条件を 1 件ずつコマンドの結果や差分で確かめるためである。
- 依存と順序の表では、依存の制約を満たす範囲で、不確かさの大きい要求を先に並べる。不確かさの大きい要求で前提の誤りが分かったとき、後の要求の作り直しを減らせる。
- PRD にシークレット・個人情報を書かない。PRD はリポジトリにコミットされ、build の反復のセッションも読む。認証情報などが要求に関わるときは、値でなく置き場所(環境変数の名前など)を書く。

## 4. 確かめて終える

承認を求める前に、要求一覧をユーザーに見せる。一覧の列は、ID・タイトル・依存先・その要求で動くようになることである。見せたら、次の 3 点を聞く。

- 要求の粒度は適切か(粗すぎないか、細かすぎないか)。
- 各依存は本当に必要か。
- 分割または統合する要求はあるか。

答えに応じて PRD を直す。直す箇所が無くなってから、承認を求める。

次をすべて満たしたら終える。

- 雛形の全節が埋まっている。
- 各要求が、4 行と 1 件以上の受け入れ条件を持つ。
- 依存と順序の表の依存先が、すべて要求一覧の ID を指す。
- 要求一覧の全要求が、依存と順序の表に並んでいる。build 3. は表の行の順にタスクを作るため、表に無い要求はタスクにならない。
- 依存先の要求が、依存する要求より上の行にある。build 3. は依存先の ID を、作成済みのタスクの ID に置き換えるためである。
- 対話で気づいたが聞かなかったリスクが、未決事項に書いてある。
- 雛形のコメントが残っていない。
- ユーザーが PRD を承認した。

ユーザーが途中で打ち切ったら、埋まっていない節と答えの出ていない問いを未決事項に書いて終える。

最後に、PRD のパスと次の一手をユーザーに示す。次の一手は「build で PRD をタスクに分解する」である。打ち切ったときの PRD は承認されていないため、「未決事項を解消してから build で分解する」と示す。
