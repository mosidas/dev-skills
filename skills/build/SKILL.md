# 要求一覧からの連続開発

本スキルは、PRD(製品要求仕様書)から起こした複数のタスクを、develop の手順で 1 つずつ PR まで進める。develop は 1 タスクを進める内側のループであり、本スキルはそれを繰り返す外側のループである。develop と `agents/` は変えない。反復のセッションが develop の統括を務め、planner・implementer・reviewer・gate-reviewer を起動する。

## 1. 工程

| 工程 | 担当 | 回数 | 成果 |
| :-- | :-- | :-- | :-- |
| 分解する | 統括(ユーザーとの対話) | 1 回 | backlog のタスク一覧と進捗ファイル |
| 反復する | 新しいプロセスで起動した統括 | 1 回で 1 タスク | 1 タスク分の PR と、記録の 1 行 |

![build は、分解の AI セッションがタスクと進捗ファイルを書いた後、loop.py が停止条件を判定しながら反復の AI セッションを新しいプロセスで起動し、反復は develop スキルで PR まで進めて受け入れ条件を検証し、結果を進捗ファイルと backlog に書く](references/flow.svg)

分解の AI セッションは build の 3. を 1 回だけ行う。反復の AI セッションは build の 4. をタスクごとに新しいプロセスで行い、その中で develop スキルが planner・implementer・reviewer・gate-reviewer を起動して PR と CI まで進める。loop.py は反復のセッションが終わるたびに進捗ファイルを読み、停止条件(停止の行が `なし` 以外・失敗の上限・無更新・回数の上限・0 以外の終了コード)に当たらなければ次のセッションを起動する。止まった後は、ユーザーが要判断への回答または失敗の行の解決を進捗ファイルに書き、停止を `なし` に戻してから loop.py を再び起動する。図は失敗の経路を省く。

状態は backlog と進捗ファイルだけに持つ。前の反復の試行錯誤が次の判断に混ざるのを防ぐため、反復はセッションの会話を引き継がない。

## 2. 進捗ファイル

進捗ファイルは、分解の工程で次の雛形から作る。

```markdown
# build: <slug>

- PRD: <パス>
- 対象リポジトリ: <パス>
- ラベル: build-<slug>
- マージ: 不許可
- 失敗の上限: 3
- 停止: なし

## 要判断

## 記録

| 日時 | タスク | 結果 | PR | 要点 |
| :-- | :-- | :-- | :-- | :-- |
```

| 行 | 意味 | 書く者 |
| :-- | :-- | :-- |
| `PRD` | 分解の元にした PRD のパス | ユーザー |
| `対象リポジトリ` | 実装するリポジトリのパス | ユーザー |
| `ラベル` | 分解したタスクに付けた backlog のラベル | ユーザー |
| `マージ` | `許可` なら反復が PR をマージする。`不許可` なら PR を開いたまま残す | ユーザー |
| `失敗の上限` | 同じタスクの `失敗` の行がいくつに達したら止めるか(正の整数) | ユーザー |
| `停止` | `なし` なら反復を続ける。それ以外は停止の理由 | 反復・ユーザー |
| `要判断` の節 | 反復からユーザーへの質問と、その回答 | 反復・ユーザー |
| `記録` の表 | 反復 1 回につき 1 行 | 反復 |

- 反復が書いてよいのは、停止の行・要判断の節・記録の表だけである。PRD・対象リポジトリ・ラベル・マージ・失敗の上限の行は、ユーザーだけが書き換える。
- 記録の結果は `完了`・`失敗`・`要判断` のどれかにする。
- 記録のタスク列は、`backlog task list --plain` が出す `TASK-12` の形で書く。loop.py はタスク列の文字列が完全一致する行を同じタスクとして数える。
- 要判断の節には、反復が `- TASK-x: <質問>` の行を書き、ユーザーがその直下に `  - 回答: <回答>` を書く。
- 置き場所は、backlog を初期化したリポジトリのルートにする。backlog はサブモジュールの中では動かない。既定のパスは `backlog/build/<slug>.md` である。
- 進捗ファイルと backlog の変更は、反復ごとにコミットしない。ループが止まった後にユーザーがコミットする。

## 3. 分解する

- PRD を読み、「何を作るか」の不明点をユーザーに 1 問ずつ、最大 3 問まで聞く(develop 2. と同じ)。
- 1 つのタスクを 1 つの PR の大きさにする。本文は要件の 4 行(目的・完了条件・対象外・品質)にし、品質は develop 2. の決め方で書く。
- 受け入れ条件は `--ac` で 1 件ずつ付け、コマンドの結果や画面の挙動など、検証できる形で書く。依存するタスクは `--dep` で指定する。
- PRD が specify の雛形(`../specify/references/prd.md`)に沿っているときは、次のように写す。
  - 要求一覧の 1 項目(`### R<n>. <タイトル>`)を 1 タスクにする。タイトルを `backlog task create` のタイトルに、4 行を `-d` に、`受け入れ条件:` の箇条を 1 件ずつ `--ac` に渡す。
  - PRD の「依存と順序」の表の行の順にタスクを作る。依存先の要求の ID(`R1` の形)は、その要求から作成済みのタスクの ID(`TASK-12` の形)に置き換えて `--dep` に渡す。複数なら `--dep TASK-1,TASK-2` とする。
  - 不明点の質問は、PRD の「未決事項」に残った項目から選ぶ(最大 3 問は変わらない)。
  - PRD の 1.(背景と利用者)・2.(対象外)・3.(品質)・4.(制約と決定事項)の節はタスクに写さず、分解と反復で読む文脈にする。

```sh
backlog task create $'<タイトル>' -l build-<slug> -d $'<要件の 4 行>' --ac $'<条件 1>' --ac $'<条件 2>' --dep <TASK-id>
```

- PRD の文(タイトル・要件の 4 行・受け入れ条件)は `$'...'` で渡し、先に `\` を `\\` にし、次に `'` を `\'` にエスケープする。`"..."` の中では `$` とバッククォートが展開され、受け入れ条件に書いたコマンドがタスクを作る時点で実行される。`$'...'` の中ではどちらも展開されないため、そのまま書く。
- `-d` の改行は `$'目的: ...\n完了条件: ...'` のように `\n` で書く。
- タスクの一覧をユーザーに見せ、承認を得る。
- 失敗の上限(既定 3)・マージの許可・進捗ファイルのパスをユーザーに聞き、2. の雛形から進捗ファイルを作る。
- マージの許可を聞くのは、この 1 度だけである。反復は `- マージ:` の行を読むだけで、書き換えない。
- `不許可` のときは依存先の PR が開いたまま残る。依存を持つタスクに来るたびに反復は要判断で止まり、ユーザーが PR をマージしてから再開する。
- 最後に、反復を回すコマンド(6.)をユーザーに示す。

## 4. 反復する

1 回の反復は、次の手順で 1 タスクを進める。

1. 進捗ファイルを読む。停止の行が `なし` でなければ、何もせずに終える。
2. タスクを 1 つ取る。先に In Progress のタスクを探し、無ければ To Do のうち依存が解けたタスクの先頭を取る。前の反復が途中で終わっても Implementation Notes を読んで続きから再開するため、In Progress を先に取る。

   ```sh
   backlog task list -s "In Progress" -l <ラベル> --plain
   backlog task list -s "To Do" -l <ラベル> --ready --sort ordinal --plain
   ```

   どちらも無く、ラベルのタスクがすべて Done なら、停止の行に `全 Done` を書いて終える。Done でないタスクが残っていれば(`backlog task list -l <ラベル> --exclude-status Done --plain`)、停止の行に `要判断(依存が解けない)` を書いて終える。
3. タスクを In Progress にする(`backlog task edit <id> -s "In Progress"`)。要判断の節に、このタスクへの回答があれば読む。タスクに依存先があれば、依存先の Final Summary または記録の表の PR 列から PR 番号を取り、`gh pr view <番号> --json state` で MERGED でなければ要判断で止める。
4. develop を 3. から 8. まで進める。次の箇所は置き換える。
   - develop 2. の要件の確認は、タスク本文の 4 行と受け入れ条件で置き換える。planner が変えてはいけない決定はタスク本文に無いため、進捗ファイルの PRD の行が指す PRD に「制約と決定事項」の節があれば、その内容も planner への入力に加える。
   - develop 5. の計画の承認は、ユーザーに見せずに計画を Implementation Notes に記録して先へ進む。develop 5. で「全部進めて」と指示されたときと同じ扱いである。
   - develop 6. で 3 回直しても承認されないとき、develop 7. で 2 回直しても通らないとき、8. で CI の失敗を 3 回直しても通らないときは、結果が `失敗` の行を記録の表に追加し、タスクを In Progress のまま反復を終える(手順 7 は行わない)。`失敗` の行は 1 反復につき 1 行だけ記録する。
   - develop 8. は CI の通過までとし、マージはここでは行わない(手順 6 で行う)。
5. CI が通ったら、受け入れ条件を 1 件ずつ、コマンドの結果や差分を根拠に確かめる。満たした条件に `backlog task edit <id> --check-ac <n>` で印を付け、根拠を Implementation Notes に書く。満たせない条件があれば、結果が `失敗` の行を記録の表に追加し、タスクを In Progress のまま反復を終える(手順 7 は行わない)。
6. マージが `許可` なら、develop 8.・9. の手順でマージし、タスクを Done にする。`不許可` なら PR を開いたまま Done にし、Final Summary に「PR #<番号> 未マージ」と書く。
7. この反復の結果を 1 行にまとめて記録の表に追加し、反復を終える。

ユーザーの判断が必要な事項に当たったら、その時点で反復を止める。該当するのは、仕様の解釈、planner の未確定事項、手順 3 の依存先の確認である。止めるときは、要判断の節に質問を書き、結果が `要判断` の行を記録の表に追加する。最後に停止の行に `要判断(TASK-x)` を書いて終える(手順 7 は行わない)。

## 5. 停止と再開

| 停止条件 | 判定する者 |
| :-- | :-- |
| ラベルのタスクがすべて Done(`停止: 全 Done`) | 反復のセッション |
| ユーザーの判断が必要(`停止: 要判断(TASK-x)`) | 反復のセッション |
| 依存が解けない(`停止: 要判断(依存が解けない)`) | 反復のセッション |
| 同じタスクの `失敗` の行数が失敗の上限以上 | loop.py |
| 反復の後も進捗ファイルが変わっていない | loop.py |
| 反復の回数が `--max-iterations` に達した | loop.py |
| エージェントが 0 以外の終了コードで終わった | loop.py |

費用を止める条件を LLM の数え方に任せないため、失敗の回数は loop.py が数える。loop.py は結果が `失敗` と完全一致する行をタスクごとに数える。

- 要判断で止まったときは、要判断の節に回答を書き、停止の行を `なし` に戻して再開する。
- 失敗の上限で止まったときは、原因を直して失敗の上限を上げるか、該当する行の結果を `失敗(解決済み)` に書き換えて再開する。loop.py は `失敗(解決済み)` を数えない。

## 6. 反復を回す

Claude Code では、loop.py が反復のたびに新しい `claude -p` のプロセスを起動する。backlog を初期化したリポジトリのルートで実行する。

```sh
python3 <プラグインのパス>/skills/build/scripts/loop.py backlog/build/<slug>.md --max-iterations 20 -- --permission-mode auto --max-budget-usd 20
```

- `--` より後ろの引数は claude に渡す。
- 終了コードは、0 が全 Done、1 がそれ以外の停止、2 が進捗ファイルの不備(読めない・形式が不正)または引数の誤りである。
- 起動するコマンドは環境変数 `BUILD_AGENT_CMD` で差し替えられる(既定は `claude -p`)。
- 反復のプロンプトは loop.py の `PROMPT` にある「dev-skills の build スキルの「反復する」工程を 1 回行う。進捗ファイル: <絶対パス>」である。
- `claude -p` は、バックグラウンドのサブエージェントの完了を待ってから終了する(Claude Code 2.1.290 で確認した)。

Codex CLI・Antigravity CLI 向けのスクリプトは提供しない。次のどちらかのコマンドを 1 回ずつ実行し、毎回進捗ファイルを読んで、5. の停止条件に当たったら止める。

```sh
codex exec "dev-skills の build スキルの「反復する」工程を 1 回行う。進捗ファイル: <絶対パス>"
agy --new-project -p='dev-skills の build スキルの「反復する」工程を 1 回行う。進捗ファイル: <絶対パス>'
```

サブエージェントを起動しない CLI では、develop の定めどおり、統括が planner・implementer・reviewer・gate-reviewer の役割を順に担う。
