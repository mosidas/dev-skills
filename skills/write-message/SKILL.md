# 短いメッセージの規範

## 1. 役割と適用範囲

本スキルは、第三者へ送る短い日本語のメッセージ本文を書く・直すときの規範を定める。対象は issue・PR のコメント、レビューコメント、業務チャット、短いメールである。ユーザーへの応答の形は respond、長い文書は write-doc、スライドは write-slide が扱い、英語のメッセージとメッセージの送信(gh や Slack API の実行)は本スキルの対象外である。

write-doc の規範のうち、次を適用する。

- `../write-doc/references/sentence.md` の 1.〜7.: 語の選び方、文の組み立て、動詞と語彙、事実と意見、翻訳調、表記、記号

本スキルの規則と食い違うところは、本スキルを優先する。食い違いは次のとおりである。

- 文体は敬体(です・ます)で統一する。`sentence.md` 6. の「常体を推奨」は適用しない。
- メッセージの送り手はユーザーであるため、`sentence.md` 4. の人称と確信度のラベル(【要確認】)の規則は適用しない。推測は「〜と推測しています」と書き、根拠を同じメッセージに書く。
- Markdown の可否は場で決まる(`references/places.md`)。
- 疑問符「？」を使う(`references/keigo.md` 9.)。`sentence.md` 7. の記号の一覧に無い。

## 2. 工程

1. 宛先と場と用件を確かめる。宛先は相手との関係(社外・社内・OSS の利用者やメンテナー)、場は issue・PR のコメント、レビューコメント、チャット、メールのいずれか、用件は報告・依頼・質問・断り・謝罪・返答のいずれかである。依頼文から読み取れなければユーザーに確かめる。確かめられないときは推測で書き進め、依頼文にあったことと推測したことを応答の冒頭で分けて示す(`../write-doc/references/readers.md` 1. と同じ扱い)。
2. 書く。3. から 5. と、`references/keigo.md`、`references/places.md` に従う。
3. 検査する(6.)。
4. ユーザーへ渡す。メッセージ本文をコードブロックに入れ、そのまま貼れる形にする。本文がコードブロックを含むときは、外側を本文中より長いフェンス(````)で囲む。本文の前後の説明は respond に従う。

## 3. 構成

- 用件から書き始める。
- 1 つのメッセージには 1 つの用件だけを書く。
- 相手にしてほしいこと(依頼・質問)は 1 文で明示する。期限は日付で書く。
- ユーザーの原文を直すとき、1 文に頼みごとが 2 つ以上あれば、頼みごとごとに文を分ける。分け方が 1 つに決まらないとき(期限がどちらの頼みに掛かるか分からない)は書き換えず、ユーザーに確かめる。
- 長さは、チャットで 3 文程度、issue・PR のコメントで 10 文以内を目安にする。超えるなら write-doc で文書にし、メッセージにはそのリンクを貼る。
- 相手の発言、コードの箇所、ログの値、issue 番号など、その相手とその状況に固有の語を少なくとも 1 つ含める。固有の語が無いメッセージは定型に見える。

## 4. 書式

- 見出し・太字・装飾の絵文字を使わない。
- 箇条書きは、並列の項目(再現手順・選択肢)に限って使い、1 段までにする。
- コード・コマンド・ログ・パスは、コードブロックかインラインコードにする。
- Markdown を描画しない場では、Markdown の記号を書かない。

## 5. AI らしさの抑制

短いメッセージでは定型の 1 文が全体に占める割合が大きく、柔らかい文体ほど AI らしさに気付かれやすいという報告もあるため、write-doc より厳しく次を守る。

- 謝辞・同意・共感の定型(「ご質問ありがとうございます」「おっしゃる通りです」「まさにその通りです」)で書き出さない。
- 申し出・問い返し(「必要なら対応します」「ご希望があれば修正できます」「何かあればお知らせください」)で締めない。社外メールの結びの挨拶は `references/places.md` に従って残す。
- 定型の結び(「お役に立てれば幸いです」)を置かない。
- 謝るときは、起きたことを書いて謝る。事実のない謝罪(「ご不便をおかけしたかもしれず申し訳ありません」)を書かない。
- ユーザーの原文を直すとき、同じ詫びや礼が 3 回以上並ぶときだけ減らし、1 つは残す。2 回までは残す。ただし、書き出しの定型の謝辞(本節の先頭の項目)は削り、事実のない謝罪(前の項目)は直す。どちらも回数に関わらない。
- 確認したことを伝えるときは、確認した内容(実行したコマンド・読んだログ)を書く。「慎重に確認しました」のような主張だけを書かない。
- ヘッジ(「可能性があります」「かもしれません」)は 1 つのメッセージに 1 つまでにする。
- 依頼の前置き(「お手数ですが」「恐れ入りますが」)は 1 つのメッセージに 1 つまでにする。
- 結論・理由・詳細・お願い・締めの型を機械的に当てはめず、用件に必要な要素だけを書く。
- 数の宣言(「3 点あります」)を書かない。
- 称賛は、どこがなぜ良いかを書けるときだけ書く。

## 6. 検査

メッセージをスクラッチパッドの `.md` に書き、次を実行する。Claude Code の hooks も書き込みの後に lint を実行するが、ジャンルを指定せず、日本語が 30 字未満のファイルは検査しないため、hooks の結果に関わらず次を実行する。

```sh
uv run <スキルのディレクトリ>/../write-doc/scripts/lint.py <file.md> --genre business
```

write-doc では検出を「残す(理由)」にできるが、本スキルでは `references/places.md` で「残す」とした定型句の検出だけを残し、それ以外の検出はすべて直す。文数が少ないため、`low_burstiness` は対象外とする。

lint が検出する 5. の項目は、定型の結びの一部だけである。lint の後に、次を目視で確かめる。

- 用件が 1 つか。
- 相手の次の行動が 1 文で書かれているか。
- 固有の語があるか。
- 5. の各項目に当たる文が無いか。
- 敬語の誤用が無いか(`references/keigo.md`)。
- 秘密情報(トークン・アカウント ID・社外に出せない名前)が無いか。
