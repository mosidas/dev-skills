# コードの安全性の規範

## 1. 適用範囲

- develop の要件で品質がプロダクトのコード、またはユーザーが安全性を求めたコードに適用する。
- ponytail と同時に適用する。
- 言語やフレームワークに固有の手順は扱わない。タイムアウト・リトライ・冪等は recover が扱う。

## 2. 規則

### 2.1 信頼境界と入力検証

- 信頼境界をすべて列挙する。HTTP 要求・ファイル・環境変数・外部 API の応答・キューのメッセージが該当する。
- 境界を越えた入力は、信頼できる側で許可リスト方式で検証する。型・長さ・範囲・形式を確かめる。
- 出力するときは出力先(HTML・URL・JavaScript など)に応じてエンコードする。クエリはパラメータ化する。
- シェルのコマンドは引数の配列で渡し、シェルを経由して実行しない。ファイルパスは、入力を結合したあとで正規化(シンボリックリンクと `..` を解決)し、許可したディレクトリの配下にあることを確かめる。

### 2.2 認証・認可

- 認証・セッション管理・パスワード保存・暗号の仕組みは自作せず、フレームワークや既存の仕組みを使う。認可の判定は、フレームワークの仕組み(ミドルウェア・ポリシーなど)の上に、アプリケーションの規則として書く。
- 既定は拒否とする。許可は明示した場合に限る。
- 認可は信頼できる側で、要求ごとに判定する。
- オブジェクトを扱うときは、要求者がその所有者か、権限を持つかをオブジェクト単位で確かめる。
- パスワードは適応型ハッシュ(Argon2id・bcrypt など)で保存する。
- 認可や検証の処理自体が失敗したときは、要求を拒否する。

### 2.3 シークレットと設定

- シークレットをコードとリポジトリに置かない。実行環境から注入する。
- 設定の既定値は安全側にする(デバッグ表示を無効にするなど)。
- シークレットが漏れたら、先に失効させ、そのあとで再発行する。

### 2.4 依存の脆弱性

- 依存を追加する前に、保守が続いているかと既知の脆弱性を確かめる。
- ロックファイルをコミットする。
- 依存の監査は hook か CI で機械的に実行する。仕組みが無ければ planner が計画に挙げる。implementer は計画に無いまま実装の範囲に加えない。
- GitHub Actions の `uses:` は、タグでなくコミットの SHA で固定し、行末のコメントにバージョンを書く(例 `uses: actions/checkout@<SHA> # v7.0.1`)。タグは付け替えられるためである。
- `.github/dependabot.yml` に `github-actions` のエコシステムを入れ、固定した SHA を更新させる。
- ワークフローの先頭に `permissions: contents: read` を書いて既定にし、書き込みが必要な job だけに、job 単位で権限を追加する。
- `actions/checkout` に `persist-credentials: false` を付ける。後続の step が `.git/config` のトークンを読めないようにするためである。
- CI の監査と SAST の設定例は `skills/develop/references/hooks.md` 4. にある。

### 2.5 ログに秘密を出さない

- トークン・パスワード・個人情報をログに出さない。必要な項目はマスクする。
- 入力をログに書くときは改行を除去またはエスケープし、偽の行の注入を防ぐ。

### 2.6 エラー応答の情報漏えい

- 利用者への応答に、スタックトレース・内部パス・SQL を含めない。
- 応答は汎用のメッセージにとどめ、詳細はサーバー側のログに残す。
- 相関 ID は、利用者から受け取った相関 ID で運用者がログを照合する窓口(サポート窓口など)が要件にあるときだけ応答に載せる。要件から分からなければ載せず、ログだけに残す。

### 2.7 検査

- 認可と入力検証には、不正な要求が拒否されることを確かめるテストを 1 つ以上残す。

## 3. 他スキルとの関係

- ponytail 5. はセキュリティ対策を単純化の対象から外す。何を対策すれば十分かは本規範が定め、どう書くか(既存の部品を優先し、差分を最小にする)は ponytail が定める。
- ログの形式と相関 ID は observe(`skills/observe/SKILL.md`)に従う。秘密をログに出さない規則は本規範が持つ。
