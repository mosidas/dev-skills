# コードの安全性の規範

## 1. 適用範囲

- develop の要件で品質がプロダクトのコード、またはユーザーが安全性を求めたコードに適用する。
- ponytail と同時に適用する。
- 言語やフレームワークに固有の手順は扱わない。タイムアウト・リトライ・冪等も扱わない。

## 2. 規則

### 2.1 信頼境界と入力検証

- 信頼境界をすべて列挙する。HTTP 要求・ファイル・環境変数・外部 API の応答・キューのメッセージが該当する。
- 境界を越えた入力は、サーバー側で許可リスト方式で検証する。型・長さ・範囲・形式を確かめる。
- 出力するときは出力先(HTML・URL・SQL など)に応じてエンコードする。クエリはパラメータ化する。
- シェルのコマンドやファイルパスを組み立てるとき、入力を文字列として連結しない。

### 2.2 認証・認可

- 認証と認可は自作しない。フレームワークや既存の仕組みを使う。
- 既定は拒否とする。許可は明示した場合に限る。
- 認可はサーバー側で、要求ごとに判定する。
- オブジェクトを扱うときは、要求者がその所有者か、権限を持つかをオブジェクト単位で確かめる。
- パスワードは適応型ハッシュ(Argon2id・bcrypt など)で保存する。

### 2.3 シークレットと設定

- シークレットをコードとリポジトリに置かない。実行環境から注入する。
- 設定の既定値は安全側にする(デバッグ表示を無効にするなど)。
- シークレットが漏れたら、先に失効させ、そのあとで再発行する。

### 2.4 依存の脆弱性

- 依存を追加する前に、保守が続いているかと既知の脆弱性を確かめる。
- ロックファイルをコミットする。
- 依存の監査は hook か CI で機械的に実行する。

### 2.5 ログに秘密を出さない

- トークン・パスワード・個人情報をログに出さない。必要な項目はマスクする。
- 入力をログに書くときは改行を除去またはエスケープし、偽の行の注入を防ぐ。

### 2.6 エラー応答の情報漏えい

- 利用者への応答に、スタックトレース・内部パス・SQL を含めない。
- 応答は汎用のメッセージと相関 ID にとどめ、詳細はサーバー側のログに残す。
- 認可や検証の処理自体が失敗したときは、要求を拒否する。

### 2.7 検査

- 認可と入力検証には、不正な要求が拒否されることを確かめるテストを 1 つ以上残す。

## 3. 他スキルとの関係

- ponytail 5. はセキュリティ対策を単純化の対象から外す。何を対策すれば十分かは本規範が定め、どう書くか(既存の部品を優先し、差分を最小にする)は ponytail が定める。
- ログの形式と相関 ID は observe(`skills/observe/SKILL.md`)に従う。秘密をログに出さない規則は本規範が持つ。
