# 失敗時の挙動の規範

## 1. 適用範囲

- develop の要件で品質がプロダクトのコード、またはユーザーが失敗時の挙動を求めたコードに適用する。
- ponytail と同時に適用する。既存のクライアント・フレームワークにタイムアウトや再試行の仕組みがあればそれを使い、回復のための新しいライブラリを導入しない。
- 2.6・2.7 は、利用者が画面を見る Web サイト・Web アプリに適用する。API・CLI・バッチ・ジョブには 2.1〜2.5 と 2.8 を適用する。
- 言語に固有の手順と、分散システムの詳細なパターン(サーキットブレーカー・バルクヘッド・分散トランザクション)は扱わない。

## 2. 規則

### 2.1 失敗の列挙

- 入口(画面・フォーム・API のエンドポイント・バッチ・ジョブ)ごとに、失敗の状態を列挙する。
- 列挙した失敗は、計画の「失敗の一覧」の表に書く。表の列は、入口・状態・原因・利用者が見るもの・システムがすること・ログである。
- 列挙には、少なくとも次の失敗を含める。
  - 入力の不備。
  - 外部への呼び出しの失敗(応答なし・タイムアウト・想定外の形の応答)。
  - サーバー内部の例外。
  - 上限の超過(サイズ・回数)。
- 失敗を、利用者が直せるものと直せないものに分ける。直せる失敗には直し方を示し、直せない失敗には次の行動(時間をおいて再試行するなど)を示す。文言は design-ui の `references/text.md` に従う。
- 同じ入力に複数の層(画面の入力制限・サーバーの検証・プラットフォームや中継)が上限を課すときは、単位(文字数・エンコード後のバイト数)をそろえて突き合わせ、もっとも厳しい上限を入力の段階で利用者に分かる形にする。例: 本文をエンコードしてから送ると、日本語の本文は文字数の上限より手前で要求サイズの上限に当たる。
- 応答が想定の形でないときと、呼び出し自体が例外を送出したときは、失敗として扱う。成功とみなして処理を続けない。

### 2.2 タイムアウト

- 外部への呼び出し(HTTP・DB・キュー)と、利用者の操作から見た待ち(ブラウザーの fetch など)のすべてに上限を付ける。
- ライブラリの既定値が無制限でないかを確かめる。
- 上限は、呼び出し先で実測したレイテンシのパーセンタイルか、SLA から決める。パーセンタイルは、許容する誤タイムアウトの率に合わせて選ぶ(例: 0.1% まで許すなら p99.9)。根拠はコメントに 1 行で残す。
- 実測が無いときは仮の値を置き、ponytail の `shortcut:` の形で見直す条件を残す(例: `# shortcut: 仮に 5 秒, 呼び出し先の p99.9 を実測したら置き換える`)。
- 外側が打ち切った後も内側の処理が残るため、入れ子の呼び出しでは、外側の残り時間を内側の上限にする。
- タイムアウトも失敗の 1 つとして、2.1 の表に載せる。

### 2.3 リトライと冪等

- 再試行は一時的な失敗に限る。一時的か恒久的かは observe のエラーの分類の軸で判定し、恒久的な失敗は再試行しない。
- 再試行の回数に上限を決め、待ち時間はジッター付きの指数バックオフで延ばす。応答に Retry-After があれば、その指定に従って待つ。
- 複数の層がそれぞれ再試行すると試行の回数が掛け算で増えるため、再試行は呼び出しの層の 1 か所だけで行う。
- 再試行する操作は冪等にする。冪等でないメソッド(POST など)の要求には、冪等キーを付ける。
- サーバーは、同じ冪等キーの再送に最初の結果を返し、同じキーで内容が異なる要求を拒否する。
- 冪等キーには有効期限を付ける。キーに個人情報を使わない。

- データの移行・投入・初期化のスクリプトは、空の環境から 1 回の実行で最終状態(件数・公開状態・並び・項目の値)を作る。同じ入力での 2 回目の実行は何も変えず、途中で止まった後の再実行も同じ最終状態に収束させる。既存の環境へ差分を重ねて最終状態に至る形にしない。
- 前の箇条の例外は、外部サービスの API で設定できない状態(手作業が必要なもの)があるときに限る。このときスクリプトはその状態を検出し、手作業の手順を出力して止まり、手作業の後の再実行で続きから最終状態まで進む。前の箇条の「1 回の実行」は、手作業を挟んだ一連の実行と読む。
- 再実行される操作(スクリプト・ジョブ・ライフサイクルの手順)は各ステップを前の実行の意図でなく今ある状態から導く。途中で止まった後の再実行を同じ最終状態に収束させるためである。現状を読んで目標と比べる。目標に足りない分だけを作る。目標に無い余分は消す。実行が残すもの(ロック・一時ファイル・書きかけのレコード・取得済みのジョブ)は前の実行がどこで止まったかによらず次の実行が古いと判定できる形にする。例えば、一時パスに書いてから rename する。成果物も作成順でなく内容で比べる。

### 2.4 二重送信の防止

- 送信が始まってから結果が出るまで送信の操作を無効に保ち、送信中の表示を出す。無効化と表示の時機の詳細は design-ui の `references/checklist.md` に従う。
- 送信の前提(CAPTCHA のトークンなど)が揃っていないときは、送信せずに理由を表示する。
- 二重に処理すると害がある操作(課金・在庫の引き当てなど)に限り、サーバー側でも 1 回限りのトークンか冪等キーを使い、同じ送信を 1 回だけ処理する。害がある操作では、この重複排除を省かない。
- 失敗したときは、入力を残したまま再送できる状態に戻す。1 回限りのトークンを使っていれば、取り直す。
- 再読み込みによる再送を防ぐため、成功したときは、フォームを結果の表示に置き換えるか、POST の応答を転送にする。

### 2.5 段階的なフォールバック

- 失敗したときに返すものを段階で決める。例: 本来の応答、静的なエラーページ、固定文のプレーンテキストの順に試す。
- 最後の段は外部(ストレージ・テンプレート・別のサービス)に依存させず、コードに埋め込んだ固定の内容で返す。
- 例外は境界(要求の入口・ジョブの最上位)で捕捉し、次の段へ進める。
- 画面や応答の一部が失敗したときの扱いを、全体を失敗にするか、失敗した部分を除いて残りを返すかから選び、2.1 の表に書く。

### 2.6 エラーページ

- 404・405・500 のページを、サイトの見た目と正しい状態コードで返す。エラーの内容を 200 で返さない(soft 404)。
- 要件に応じて、403・429・503 のページも用意する。
- 405 の応答には Allow ヘッダーを付ける。429・503 の応答には、再試行できる時期が分かるときに Retry-After を付ける。
- エラーページを独立した URL で配信するとき(静的サイトの 404.html など)は、その URL を直接開くと 200 で返るため、エラーページに noindex を付ける。
- 本文は、design-ui の `references/text.md` にある利用者向けの文言の規則に従う。

### 2.7 中間状態の露出防止

- 次のページは、直接開けないようにする。
  - サーバーが置換する印(プレースホルダー)を持つページ。
  - 処理の結果としてだけ意味を持つページ(送信の完了など)。
- 直接開かれたときは、入口のページへ転送するか、印を含まない表示にする。
- 置換が失敗したときの表示に印が含まれないことを、テストで確かめる。

### 2.8 完了条件と検査

- 計画の各ステップの完了条件には、2.1 の表の失敗ごとに、利用者が見るものとシステムの挙動を書く。形は observe の完了条件と同じにする。
- タイムアウト・二重送信の防止・フォールバックの最後の段には、失敗を起こして挙動を確かめるテストか手順を、それぞれ 1 つ以上残す。
- サイズの上限には、2.1 で利用者に示した上限ちょうどの入力を、エンコード後にもっとも膨らむ文字(日本語など)で送り、受理されることを確かめるテストを残す。
- 移行・投入・初期化のスクリプトでは、空の環境で 1 回実行した結果が最終状態と一致すること、2 回目の実行で変更が 0 件であることを確かめるコマンドを、計画のステップの「検証」に書く。手作業が必要なときは、手作業を挟んだ一連の実行の後に確かめる。空の環境を用意できないときは、その旨と代わりの確かめ方を計画の方針に書く。

## 3. 他スキルとの関係

- 失敗の状態の見せ方と文言は、design-ui の `references/text.md` と `references/checklist.md` に従う。本規範は、何を失敗として列挙し、システムが何をするかを定める。
- エラー応答に内部情報を出さない規則と、相関 ID を応答に載せる条件は secure に従う。
- 失敗のログとエラーの分類は observe に従う。
- 書き方は ponytail に従う。回復の処理を省いた箇所には `shortcut:` のコメントを残す(例: `# shortcut: 再試行なし, 外部 API の一時的な失敗が月 1 回を超えたら足す`)。
- specify の PRD で、失敗したときに利用者が見るものを書いた受け入れ条件は、planner が 2.1 の表を作るときの入力にする。
