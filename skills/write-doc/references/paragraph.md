# 段落・構成の規範

## 1. 段落

- 一つの段落には一つのトピックだけを置き、先頭の文を読めばその段落の主題が分かるようにする。段落中の他の文は、トピックセンテンスの補強・展開に限る。
- 因果と経緯は地の文で書く。箇条書きを使ってよいのは、項目が同じ文法構造・同じ抽象度で本当に並んでいる場面に限る。箇条書きは、書き手が省略した論理関係の組み立てを読者へ転嫁する。
  - Before: 「・在庫が減った ・発注担当が気づかなかった ・欠品が発生した」
  - After: 「在庫が減っても発注担当が気づかず、そのまま欠品した。」
- 項目の頭のラベルとコロンの扱いは `sentence.md` 7. に従う。
- 「次のとおり」「以下の n 点」と予告して並列の項目を挙げるときは、地の文で並べず、箇条書き・表・図にする。項目が名前と値の対なら表、順序や包含があるなら図を選ぶ。
- 論証は一方向に進める。反論と疑念を処理してから、結論を一度だけ置く。結論を出してから反論を処理し、結論を言い直す構成にしない。
- 読者が立てそうな誤った解釈は、明示的に否定してから本当の理由を述べる。否定は判定の語でなく、根拠となる事実で行う(`sentence.md` 4.)。

## 2. 論証の厳密さ

- 推量・可能性・反実仮想として書かれた文を、根拠なく断定へ変えない。断定に直せるのは、本文内の根拠で命題が確定している場合に限る。
- 区別すべき対象(別々の決定、別々の原因)を一括りの言葉でくくらない。複数の要因がある事象を単一の原因に還元しない。
- 因果を主張するときは、その機構(なぜそうなるのか)を一文で示す。
- 優劣の関係にない対象を、優劣の軸(質が高い/低い)で並べない。並べる軸は対象を実際に区別する性質にし、どの場面でどれを選ぶかを書く。
- 質・良し悪しを主張するときは、判断の観点を先に定義し、観点ごとに水準の高い例と低い例を示す。
- 主張を置いたら、それを支える定義・例・関係を同じ節に置く。同じ節で裏づけを示せないなら、断定でなく提示の形にする。
- 検出・保証・解決を「必ず」できるかのように書かない。条件付きで正確に述べる(「〜が成り立つときに限り」)。
- 章・節をまたいで、同じ概念の扱い・分類・用語の地位を一致させる。「次節で扱う」と先送りした論点は、本当にそこで回収する。

## 3. 構成

書く前に、伝えたいことを「この文書は <読み手> に <伝えたいこと> を伝える。」の 1 文にする。続けて、節ごとに次の 4 列を持つ表を作る。「なぜ」が伝えたいことにつながらない節は、節ごと削る。表を文書本体に載せるかは、文書の形式と同じく読み手と目的から決める(`readers.md` 4.)。

| 列 | 書くこと |
| :- | :- |
| 節 | 節の見出し |
| 役割 | この節で言うこと 1 文 |
| 見せるもの | 役割を支える例・図・出力 |
| なぜ | この節が伝えたいことにどうつながるか |

- 前置き(「本稿では〜を解説する」)を書かず、結論から始める。ただし文脈を持たない読者(`readers.md` の「他者向け」)が読む文書では、冒頭に導入の節を設け、対象(何の話か)・経緯や用語などの前提・扱う範囲を説明してから結論を書く。前置きは本文の内容を予告するだけの文であり、導入は読み手が持たない前提を補う文なので、両者は別物として扱う。
- 書き手が AI に出した指示や除外の判断が本文に言い換えて残った文は、指示や方針を述べる部分を削り、読者に向けた中身だけを残す。手がかりは、読者が思ってもいない書き方を打ち消す語(「一般論でなく」)と、トーンや書き方の指定である。読者のために扱う範囲・対象読者・前提を示す文は、上の導入に当たるので残す。どちらか決められなければ残す。
  - Before: 「今回は一般論でなく、本番環境の事例に絞って、やさしいトーンで振り返る。3 月の障害では、証明書の期限切れで API が 40 分止まった。」
  - After: 「3 月の障害では、証明書の期限切れで API が 40 分止まった。」
  - 残す文: 「この手順書では、アカウントの削除は扱わない。」
- 見出しや、元の文書にある冒頭の要約を直すときは、本文の条件を落とさない。条件の消えた結論は、元より強い主張になる。要約には条件も書き、長くなるなら 2 文に分ける。見出しは 6. のとおり話題を示す名詞句にし、本文の条件を落とした結論を見出しに書かない。原文の見出しが結論を言うときは、条件なしで言える結論に限って残す。
  - 本文: 「本番環境で、同時接続が 500 を超えたときだけ、接続プールが枯渇する。」
  - Before(要約): 「接続プールが枯渇する。」
  - After(要約): 「本番環境で同時接続が 500 を超えると、接続プールが枯渇する。」
- 推敲では、元の文書にない要約の節(「この文書の要点」「まとめ」)を足さない。結論の置き場所は元の文書の組み立てのとおりにし、冒頭に置くほうが探しやすいと判断したら、そうすることをユーザーに提案する。列挙の前に一文で枠を示すことは、これに当たらない。
- すべての節を同じ厚みで書かない。重要な節は厚く書き、軽い節は 1 文で済ませてよい。濃淡は強弱であって順序づけではないので、並列な項目に本文が持たない優先順位や段階を与えない。
- 調査・分析の結びは、事実の再統合で終えず、根拠が支える範囲で次に何をすべきかを 1 段落書く。根拠がなければ再統合で止める。
- 調査の結びで提案を書くときは、「決める前にできる検証」と「決める場で選ぶ選択肢」に分ける。選択肢ごとに、支える数字・確かめること・選ぶ条件(「検証で〜なら A、〜なら B」)を添える。選択肢は、素材にある関係者の案・検証の結果で決まる案・何もしない案から作り、素材にない施策や数字(期間・費用・効果の見込み)は足さない。事実・解釈・打ち手を分け、どの文がどれに当たるかが分かるように書く。依頼に決めたいことがない定点観測では、選択肢を作らない。節の順序はここでは定めない(`readers.md` 4.)。

## 4. 接地と省略

- 議論を支える具体(固有名詞・数値・実例)で接地する。段落から固有名詞・数値・実例をすべて抜いても文意が変わらないなら、それは素材の不足なので、言い回しを変え続けず素材を集め直す。
- 議論を支えない装飾的精度(時刻、HTTP ステータス、後で参照しない識別子)は省き、一般的な言い方で済ませる。接地と省略の基準は同じで、「その具体が読み手の理解を実際に助けるか」で決める。
- 括弧の補足は、読者がその補足だけで理解を進められるものに限る。一言では説明しきれない内容を括弧へ押し込まない。本文で説明するか、図にするか、削る。
- 手順・依頼・先に済ませる作業を括弧に入れた文は、括弧から出し、行う順に文で並べる。順序を示す語のほかは足さない。
  - Before: 「マイグレーションを適用する(先にステージングで試す)。」
  - After: 「先にステージングで試す。その後、マイグレーションを適用する。」
- 図表の凡例・注記・キャプション・表の列名・本文に、見れば分かること(「(赤)」「太字は〜」「青い枠は〜」のような色・書式・線種・形の説明)や図表の読み方の説明を書かない。凡例には要素の意味だけを書く。書くかどうかは、その記述を削除しても図や表から読み取れるかで判定し、読み取れるなら書かない。

## 5. 見直し

書き上げたら、見出しと各段落の先頭文だけを続けて読む(スケルトン通読。`outline.py` の出力を使う)。確かめるのは次の 5 点で、骨組みだけで判定できないなら、文書自体が骨組みの水準で崩れている。

- 論旨が通っているか。
- 見出しがラベルでなく内容を伝えているか。
- 同じ書き出しの型が 3 回続いていないか。
- 節ごとに濃淡がついているか(3.)。
- 結びが次に何をすべきかへ接続しているか(3.)。

続けて削除テストを 2 回行う。どちらかで崩れたら、主張と根拠の配分を直す。

1. 根拠(例・出力・図)をすべて消す。残った文だけで伝えたいことが言えなければ、主張が書けていない。
2. 主張(読み手にとって何が変わるか)を述べた文をすべて消す。それでも文書が成り立って見えるなら、根拠を読み上げているだけである。

## 6. 見出し

- 見出しは、その節が報告する内容を特定する名詞句にする。命題を「〜こと」で名詞化した見出し、結論を言い切るセリフ、数値を含む見出しにしない。
  - Before: 「失敗が 60 秒で起きること」「この取込だけが重いこと」
  - After: 「失敗までの経過時間の測定」「クエリごとの所要時間の比較」
- 推敲では、原文にある短い動作の見出し(「設定を見直す」)を名詞句に言い換えない。文書の題(レベル 1)も変えない。新しく書く見出しは、上の名詞句の規則に従う。
- 「〜とは」とコロンで話題をつないだ見出しは、コロンの後の語句を落とさずに名詞句にする。文書の種類と対象を区切るラベルのコロン(「議事録: 10 月定例会」)は残す。
  - Before: 「uv とは: インストール手順」
  - After: 「uv のインストール手順」
- 見出しから外した警告・条件・結論・範囲・順序・手段・書き手の評価は、本文になければ本文へ移して同じ意味で残す。
- 見出しの後ろに括弧で補った語句と、結びの「〜について」は外す。括弧の中の条件・期限は、本文になければ本文へ移す。節が括弧の中身だけを扱うときは、括弧の語を見出しにしてよい。管理番号・画面の項目名を示す括弧(「(REQ-118)」)は残す。
  - Before: 「デプロイの手順(本番前まで)」「ログの保存期間について」
  - After: 「デプロイの手順」「ログの保存期間」
- 一つの見出しに「と」「・」で二つの主題を並べない。主題が二つあるなら節を分ける。「A と B の照合」のように結び付き自体が主題のときに限って使う。
- 同じレベルの見出しは粒度を揃える。文書全体の構成要素を指す見出しと個別の対象を扱う見出しを同じレベルに並べない。
- 議事録を推敲するときは、話題の順と見出しを変えない。散文の記録を項目に分けるのはよい。話題ごとに並べ替えるのは、会議のメモから新しく作るときに限る。
