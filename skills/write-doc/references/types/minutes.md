# 議事録

本ファイルは、議事録(会議で話したこと・決めたこと・アクションアイテムを残す文書)の決まりを定める。

## 1. 読み手

読み手は出席者と欠席者である。欠席者は会議の文脈を持たない。出席者は、決定事項と自分のアクションアイテムを確かめるために読む。

## 2. 節の並び

- 依頼者か宛先に議事録の雛形があるときは、節の並び・見出しの形・日時や出席者の書き場所を雛形に合わせる(`../process.md` 2.)。組織の議事録は決まった形で保管され、読み手はその形で決定事項と自分のアクションアイテムを探す。
- 雛形が無いときは、日時・場所・出席者、議題、話題ごとの記録、決定事項、アクションアイテム、次回の順に置く。Markdown では日時・場所・出席者を frontmatter に書き(`../format/markdown.md` 2.)、本文に同じ内容の節を作らない。同じ内容を 2 か所に書くと、片方だけが直される。
- 決定事項・アクションアイテムが無い会議では、その節を作らない。話題は会議で出た順に並べる。アクションアイテムには担当と期限を書く。決定事項とアクションアイテムは並列の項目として箇条書きにしてよい(`../paragraph.md` 1.)。

## 3. 足す規則

- 議事録を推敲するときは、話題の順と見出しを変えない。散文の記録を項目に分けるのはよい。話題ごとに並べ替えるのは、会議のメモから新しく作るときに限る。
- 発言を引用するときは、`../sentence.md` 4. の「引用した話し言葉と、改行で区切る書き方は、読解を妨げない限り均さない」に従う。
- 素材に無い担当・期限は作らない。会議で確定しなかった担当と期限は「未確定」と書く。
- 話題ごとの記録に書くのは、会議の中の発言と質疑応答である。会議で使った資料に書いてある内容の説明は書かず、資料へのリンクを日時・出席者と同じ場所に書く。読み手は資料を持っており、議事録でしか得られないのは資料に無い発言である。
- 発言は「〜(名前)」の形で書く。「名前は〜と述べた」の文にすると、どの項目も名前で始まり、読み手は内容で項目を探せない。発言者を確定できない発言には名前を付けない。
- 質疑応答は発言の箇条書きに混ぜない。話題ごとに、発言の箇条書きの後へ「質問」「回答」の 2 列の表を書き、1 組を 1 行にする。セルも「〜(名前)」の形で書く。箇条書きに混ぜると、どの回答がどの質問に対応するかを読み手が組み立てることになる。
- 確認が済んだ時点で削除する記述は、成果物に書かない。該当するのは、確認待ちの印(【要確認】)・確認事項の一覧・作成方法と未確認の範囲の注記である。確認したい事項は、依頼者への返答に書いて聞く。非対話の実行では、返答の冒頭に書く(`../readers.md` 1. の推測の示し方と同じ)。素材から特定できない名前と数値(聞き取れない名前、言い間違いが疑われる数値)は本文に書かず、回答を受けてから書く。数値を抜くと意味が変わる発言は、発言ごと書かずに聞く。アクションアイテムの担当と期限も同じに扱い、特定できない担当か期限を書かずに返答で聞く。会議で確定しなかった担当と期限の「未確定」とは区別する。議事録は出席者と欠席者に配る記録であり、作り手と依頼者の間の確認は読み手の用件ではない。
- 素材のパスなど、作り手が後でたどるための参照は、本文に書かず HTML コメントで書く(`../format/markdown.md` 2.)。HTML コメントに書くのは参照(パスとタスクの識別子)だけにし、作成方法・未確認の範囲・作業の経過の説明は書かない。

## 4. 外してよい規則

- `../paragraph.md` 3. の「結論から始める」と「『なぜ』が伝えたいことにつながらない節は、節ごと削る」は外す。記録は会議の順に並べ、議題を削らない。
- `../sentence.md` 4. と `../readers.md` 3. の、未検証の内容に【要確認】のラベルを付ける規則と、`../process.md` 4. の「未確定・要確認」と書く規則は外す。ラベルを付ける代わりに、依頼者への返答で聞く(3.)。

## 5. 検査で見る点

- `lint.py --genre business` で検査する。ファイル名に `minutes` か `議事録` を含むときは、`hooks/inspection.config.json` の doctypes が検査 hook に business を割り当てる。
- アクションアイテムのすべてに担当と期限があるか。無いときは、会議で確定しなかったものに「未確定」と書いてあるか。素材から特定できない担当か期限は、書かずに依頼者への返答で聞いているか(3.)。
- 話題の順が会議の順と一致するか。
- 確認待ちの印(【要確認】)・確認事項の一覧・作成方法の注記が残っていないか(3.)。`../inspection.md` 4. の仮置きの点検は【要確認】を対象にしないため、ここで確かめる。
- 決定事項・話題ごとの記録・アクションアイテムが対応しているか。次の 4 点を 1 件ずつ確かめる。節を移した後と項目を削った後は、対応が崩れやすい。
  - 決定事項のそれぞれに、対応する発言が話題ごとの記録にあるか。
  - 話題ごとの記録で確定した事項が、決定事項にあるか。
  - 誰かが実行する決定事項が、アクションアイテムにあるか。
  - アクションアイテムの担当と期限が、話題ごとの記録の発言と一致するか。
- 素材(録音・文字起こし・メモ)から作った議事録では、事実の照合を専任の 1 エージェント(照合役)に渡す(`../inspection.md` 5.)。照合役には、全観点を 1 エージェントに渡してよい文書(`../inspection.md` 5.)でも、ほかの観点を兼ねさせない。サブエージェントを起動できない CLI では、別のセッションに渡すか、照合だけの 1 周をほかの観点と分けて行う。
- 照合役には素材を渡す。照合役には、発言・決定事項・アクションアイテムの 1 件ごとに、素材の中の位置と、次の 5 点が素材と一致するかを表で返させる。一致しない項目には、素材に合わせて書き直した文を修正案として添えさせる。5 点は `../inspection.md` 4. の言い直しテストと同じ軸である。
  - 発言者
  - 肯定と否定
  - 断定の強さ(推量・希望・条件つきの発言を言い切りにしていないか)
  - 条件と範囲
  - 数値と固有名詞
- 照合しなかった項目を見分けるため、照合の結果は全件を表で返させる。話し言葉を 1 文に要約すると、推量と希望が言い切りになり、条件が抜ける。この誤りは文として自然なので、素材と並べないと見つからない。
