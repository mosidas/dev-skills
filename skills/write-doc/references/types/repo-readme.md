# README

本ファイルは、リポジトリの README(リポジトリを開いた人が最初に読む文書)の決まりを定める。雛形は `../templates/readme.md` である。

## 1. 読み手

読み手はリポジトリを初めて開いた人である。使う人と開発に参加する人の 2 種類がいる。使う人は、何をするものかと、インストールして動かすまでを知りたい。開発に参加する人は、環境を用意してビルドとテストを動かすまでを知りたい。どちらもコードを読めるが、まだ読んでいない。README はコードを読む前に読む文書であり、コードを読めば分かることを読み手に先回りして伝える文書ではない。利用者のいないリポジトリ(社内のサイト・自分だけが使うツール)では、読み手は開発に参加する人だけである。

## 2. 節の並び

冒頭に題名と、何をするものかの 1 文を書く。機能が 2 つ以上あるときは、1 文に並べず、1 文の直後に機能ごとの箇条書きで書く(`../paragraph.md` 1. は 3 つ以上を箇条書きにするが、README の冒頭では 2 つから箇条書きにする)。導入の節は設けない。画面を持つアプリでは、1 文と機能の箇条書きの直後に画面の画像を 1 枚置いてよい。続けて、動作環境(対応する OS と版、対応が限られるときは CPU)、インストール、使い方、開発、ライセンスの順に置く。権限の許可は動作環境に書かず、使い方の最初の流れの手順に書く。インストールには配布物の形式を、使い方には最初の流れの後に既定の保存先を書く。インストールは、配布の形(Releases・パッケージマネージャー・ソースからのビルド)が 2 つ以上あるとき、配布の形ごとにレベル 3 の見出しを設ける。使い方は、配布物(ライブラリ・CLI・GUI)ごとに、利用者が最初にする 1 つの流れだけを書く。配布物が 2 つ以上あるときは、配布物ごとにレベル 3 の見出しを設け、既定の保存先はその配布物の見出しの中に書く。開発は、環境の用意(ツールと版・devcontainer・秘密情報の置き場)、ビルド、テストをそれぞれ 1 つ書く。該当しない節は削る。利用者のいないリポジトリでは、インストールと使い方を削り、開発の節を本体にする。

## 3. 足す規則

- 2. で定めた項目(1 文・画面の画像・動作環境・配布物の形式・既定の保存先・ライセンス)は問わずに書く。それ以外を書くかどうかは 2 つの問いで決める。1 つ目は「それが無いと、読み手は最初の流れ・環境の用意・ビルド・テストを始められないか」である。始められるなら書かない。内部の層、処理の順序、失敗時の内部の挙動、設定ファイルのキーの一覧がこれに当たる。2 つ目は、始められないものについて「README が無くても、慣習で場所が決まったもの(`--help`・画面・依存の宣言・CI の設定・`LICENSE`)から得られるか」である。得られるなら書かない。ディレクトリ構成と技術スタックがこれに当たる。ただし、最初の流れの前に必要な前提(ツールと版・devcontainer)は、依存の宣言から得られても 1 行で書く。
- サブコマンド・オプション・エラーコード・キーバインドの全部の一覧は書かない。README には、最初の流れに出てくるものだけを書く。`--help` と画面が持たず、利用者がスクリプトから使う取り決め(終了コード・出力の形式)は、`docs/<名前>.md` にリファレンスとして分け、README からリンク 1 行で参照する。
- README から外す内容を `docs/` へ移す前に、「コードと画面から得られるか」を問う。得られる内容(機能ごとの操作と設定項目の説明、オプション・キー・既定値の一覧、スクリプトの動作)は `docs/` にも書かない。開発者と AI はコードを読み、利用者は画面で試すほうが早い。コードを写した文書は、コードの変更に追随せず食い違っていく。`docs/` に分けるのは、コードと画面から得られない手順と決まり(他のアプリとの連携、移行、復元、計測、方針とその理由)と、コードを読まない利用者がスクリプトから使う取り決め(終了コード・出力の形式)である。
- 分けた文書の冒頭に、内容を予告する文(「〜を説明する」)と README へ戻る参照を書かない(`../paragraph.md` 3. の前置き)。手順書は `procedure.md` 2. に従い、何の手順で誰がいつ使うかを冒頭に書く。
- 2 つ目以降の流れと場面ごとの手順(他のアプリとの連携・移行・復元)は、`docs/<場面>.md` に手順書(`procedure.md`)として分け、README からリンク 1 行で参照する。参照の行は、読み手の目的を条件にし、文書の題名をリンクテキストにして、読み手の操作を述語にする(`../sentence.md` 8.)。
- CI の仕組み、テスト用データの再生成、リリースの手順は `docs/` か `CONTRIBUTING.md` に分ける。配布物を作る手順でも、利用者が入手する手段がそれしかないときは、インストールの節にソースからのビルドとして書く。
- インストールの節は、配布の形ごとに番号付きの手順 1 つで書く。配布物が無いリポジトリでは、無いことを書かず(「配布物は無い」)、ソースからの手順だけを書く。手順は `procedure.md` 3. に従い、1 つの番号に 1 つの操作を書き、起動の操作で終える。確かめ方は、次の番号に必要なもの(ビルドの出力の場所)だけ書く。起動した結果(ウィンドウが出る)は画面が示すので書かない。初回の起動の許可(Gatekeeper)のように入手の後に必要な操作も、同じ手順の番号に入れる。手順の間に文の段落で操作を書かない。
- 1 つの事実は、2. でその役割を持つ節に 1 回だけ書く。動作環境に書いた OS と版・CPU を、インストールと使い方で繰り返さない。インストールにソースからのビルドの手順があるとき、開発の節はビルドをその手順への参照 1 文にし、テストと、その手順に無い環境の用意(devcontainer・秘密情報の置き場)だけを書く。同じ README のほかの節を指すときは、節の名前を鉤括弧で書かず、見出しへのリンク(`[ソースからビルドする](#ソースからビルドする)`)にする。読み手は鉤括弧の名前から節の場所を探せない。
- 操作の分岐の条件にできる環境は、動作環境に書いたものだけである。動作環境に無い版の操作(「macOS 14 では〜でもよい」)は書かない。同じ結果になる別の操作を「〜でもよい」で並べない(`procedure.md` 3.)。
- 分量は、画面を 2 回送らずに読める量(100 行)を目安にする。超えたら、文を削るのではなく、2. に無い節と 2 つ目以降の流れを別の文書に分ける。

## 4. 外してよい規則

- `../readers.md` 3. と `../paragraph.md` 3. の「結論の前に導入を設け、対象・経緯や用語などの前提・扱う範囲を説明する」は外す。題名の直下の 1 文が導入に当たる。経緯は書かない。
- `procedure.md` 3. の「各手順に、確かめ方を書く」は、インストールの手順には外す。起動した結果は画面と `--help` が示す。ビルドの出力の場所は 3. のとおり書く。
- `../paragraph.md` 1. の「因果と経緯は地の文で書く」と「番号・記号は、後で番号を使って参照するときだけ振る」は、使い方の操作の順序には適用しない。使い方の操作の順序は番号付きの箇条書きにしてよい。インストールは 3. のとおり番号付きの手順で書く。

## 5. 検査で見る点

- 冒頭の 1 文に機能を 2 つ以上並べていないか。機能が箇条書きになっているか。
- レベル 2 の見出しが 2. の節の名前だけか。該当する節が欠けていないか。レベル 3 の見出しが、インストールの配布の形と使い方の配布物のほかに無いか。
- 2. で定めた項目以外の各文が、3. の 2 つの問いを通るか。
- 一覧が、最初の流れに出てくるものだけか。利用者がスクリプトから使う取り決め(終了コード・出力の形式)に、分けた先があるか。
- 使い方の流れが、配布物ごとに 1 つか。
- 開発の節が、環境の用意・ビルド・テストのそれぞれ 1 つ以内か。インストールにソースからのビルドの手順があるとき、ツールとビルドを繰り返していないか。ほかの節への参照が見出しへのリンクか。CI・リリース・テスト用データの再生成が本文に無いか。
- インストールの手順が配布の形ごとに番号付きで 1 つか。各手順が起動の操作で終わるか。起動した結果の確かめ方が無いか。手順の間に文の段落が無いか。
- 動作環境に権限が書かれていないか。動作環境に書いた内容がほかの節で繰り返されていないか。操作の分岐の条件が、動作環境に書いた環境か。「〜でもよい」の別の操作が無いか。
- 分けた文書への参照が、文書の題名をリンクテキストにし、読み手の操作を述語にしているか。
- 分けた文書が、コードと画面から得られる説明(機能・オプション・キー・既定値・スクリプトの動作)でないか。利用者がスクリプトから使う取り決め(終了コード・出力の形式)のリファレンスは分けてよい。冒頭に予告の文と README へ戻る参照が無いか。
- 100 行を超えていないか。超えているとき、分ける先の文書が決まっているか。
- リンク先の文書が存在するか。
