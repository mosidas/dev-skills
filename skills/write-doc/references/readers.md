# 読み手の規範

本ファイルは、文書の形式を決める前提となる読み手の分類を定める。文書の種類(仕様書・手順書・レポート・議事録など)ごとの決まりは `types/` に置き、未作成の種類と形式は `process.md` 2. の brief で合意する。

## 1. 分類

- **本人向け**: 書き手(ユーザー)自身が読む文書。読み手は文脈を知っており、必要な知識も一通り持つ。
- **他者向け**: ユーザー以外が読む文書。読み手は文脈を知らず、持つ知識も様々である。
- どちらに当たるかをユーザーに確認してから書き始める。
- 確認できないとき(非対話の実行、回答が得られない)は、推測で分類して書き進め、次を守る。
  - 読み手について依頼文にあったことと推測したことを、返答の冒頭で分けて示し、推測には理由を添える。文書の中にだけ書くと、ユーザーに届かない。
  - 依頼文にない読み手の属性(経歴・使っている道具・困りごと)を事実として書かない。
  - 依頼文の言い換えを、読み手本人の言葉のように書かない。「依頼文から、問いを『…』と推測した」のように書く。

## 2. 本人向け

- 前提・経緯・用語の定義を省いてよい。
- 作業ツリー内のパスや中間ファイルを参照してよい。
- 結論と根拠だけを書く。

## 3. 他者向け

- 結論の前に導入を設け、対象・経緯や用語などの前提・扱う範囲を説明する(`paragraph.md` 3.)。
- 作業フォルダ内にしかない中間ファイル(調査メモ・下書き・作業用の対応表)とパスを参照せず、必要な内容を本文へ取り込む。読み手が持つリポジトリ内の相対パスは書いてよい。
- 素材の作業用の名前(実験の条件名・ブランチ名・集計の区分名)をそのまま出さず、何を指すかを言葉で書く。
- 検討の途中経過や内部的な分析を残さない。
- 読み手が持たない知識を前提にせず、本文で説明する。術語は言い換えずに使い、初出で説明を添える(`sentence.md` 1.)。
- リライトで、読み手が持たない用語(分野の用語・社内の呼び名・略語)の説明が根拠の範囲(`sentence.md` 4.)に無いときは、モデルの一般知識で定義を書かない。原文にない説明になる。次のとおり扱う。
  - 用語は消さずに残し、説明は本文に入れない。
  - 応答で、書き手に「ここに説明が必要です: 「SLO」(3 段落目。原文と資料に説明がない)」の形で返す。語ごとに説明の文案は書かない。説明は書き手が書く。
  - 返すのは 3 点までとする。多ければ見出し・最初の段落・何度も出る語の順に選び、「ほかに N か所」と添える。
  - 同じ文書の後ろの段落に説明があるとき(後の節に「検証用の環境(ステージング)」とある)は、初出へ写してよい。
- 確信度のラベル(`sentence.md` 4.)を必ず使う。
- 読み手に答えを求める問い(確認項目の一覧・質問票)は敬体で書き、問いの文に、答えに必要な文脈(何のために、何について聞くか)を含める。読み手は書き手の調査の経緯を知らないため、短い常体の問いは意図が伝わらず、詰問に読まれる。
- 書き手が調べて決められる事項(進め方・使う道具・連絡の手段)は問いにせず、案を書いて可否を聞く。問いにするのは、読み手が決める事項である。書き手が決められる問いが並ぶと、読み手は答えなくてよい事項にまで手間をかける。

## 4. 文書の形式

- `types/` に無い種類の見出し構成・必須要素・雛形は、読み手の分類と文書の目的から候補を立て、`process.md` 2. の brief で合意する。
