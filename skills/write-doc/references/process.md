# 工程の規範

## 1. 工程の一覧

文書は次の順に作る。各工程の成果を依頼者と合意してから、次の工程へ進む。ただし、検査の結果は依頼者に見せず、別のエージェントによる推敲を検査に続けて行う。依頼者には、修正案を反映した成果物を見せる。

| 工程 | 成果 | 読む束 |
| :-- | :-- | :-- |
| 着手 | 読み手・目的・種類・形式・配布先・宛先プロファイル・雛形を決めた brief(2.) | `readers.md`、`types/` |
| 骨組みの合意 | 節の表、表と一覧の列見出しと行の項目、疑問の一覧(3.・4.) | `paragraph.md` 3. |
| 肉付け | 本文 | `sentence.md`、`paragraph.md`、`format/` |
| 検査 | lint.py 等で機械検出し、構造と事実は目視で点検した結果と、検出への対応を「直した / 残す(理由)」に仕分けた判断台帳 | `inspection.md` |
| 別のエージェントによる推敲(他者向けの文書は依頼者に見せる前に行う) | 書き直した文の修正案と、その仕分け(6.) | `inspection.md` 5. |
| 指摘を受けた後 | 指摘が当たる範囲に適用して出し直した成果物と、実際に見た節・ページを書いた報告、宛先プロファイル・規範への追記(7.) | 7. |

既存文書の推敲・リライトでは、対象の粒度に応じたファイルだけを適用する。一文の修正に構成の規範までは適用しない。

## 2. 着手時の brief

書き始める前に、次の雛形を既定値で埋めて依頼者に見せ、1 往復で合意する。依頼者には、既定値と違う項目だけを返してもらう。項目を 1 つずつ聞くと、往復が項目の数だけ増える。

```text
- 読み手: 他者向け(<依頼文から推測した読み手>)
- 目的: <依頼文から推測した 1 文>
- 種類: <依頼文から推測した種類(手順書 / 仕様書と規約 / 議事録 / 調査レポート / 技術記事 / 企画書と PRD / README / その他)>
- 形式: Markdown
- 配布先: リポジトリ内
- 宛先プロファイル: なし
- 雛形: なし
違う項目だけを返してください。
```

- 種類は依頼文から推測する。該当する種類は `types/README.md` の表でファイルを引いて読み、そのファイルの 2. を骨組みの、4. を外してよい規則の既定値にする。その他は、形式と見出し構成をこの brief で合意する。
- 宛先プロファイルは、宛先ごとの固有の決まり(語の置き換え・構成の決まり・過去の指摘)を集めた文書である。置き場所は利用側のリポジトリが定める(例: `docs/doc-profiles/<宛先>.md`)。あれば読む。
- 雛形は、依頼者か宛先が同じ種類の文書に使っている形(節の並び・見出しの形・メタ情報の書き場所)である。雛形のファイルか、形を合わせる過去の文書があれば、依頼者にそのパスを返してもらう。雛形があるときは、`types/` の該当ファイルの 2. より雛形を優先する。
- 確認できないとき(非対話の実行、回答が得られない)は、`readers.md` 1. に従う。
- brief を既定値で埋められないときと本人が「詰めて」と言ったときは 1 往復の雛形の代わりに interview(`../../interview/SKILL.md`)で 1 問ずつ聞く。埋められないのは依頼文から読み手か目的を推測できないときである。答えは brief と節の表(`paragraph.md` 3.)に書く。どちらにも当たらないときは 1 往復のままにする。
- 誰に・どの場で・何を判断してもらう文書かが分からないうちは、本文を書かない。本文の代わりに、論点を 1 枚に整理して依頼者に見せる。

## 3. 骨組みの合意

- 素っ気ない依頼でも、いきなり本文で埋めない。種類と、結論の文の候補または章の並びを示し、合意を取ってから肉付けする。
- 節の表(`paragraph.md` 3.)を作り、本文を書く前に合意を取る。スライドではページごとに作る。各節の役割は、伝えたいことか、相手に決めてほしいこと・聞きたいことを 1 行で書き、書けない節は削る。表紙・章扉は対象外とする。削るか迷う節は、付録に回さず 4. の一覧に入れる。
- 表と一覧は、列見出しと行の項目を先に見せ、合意してから中身を埋める。埋めた後に列や行を組み替えると、同じ表を何度も直すことになる。
- 同じ型を 5 回以上展開するとき(手順の各節、機能ごとの説明、同じ型のページ)は、代表の 1 つを先に仕上げて確認を取ってから広げる。確認前に広げると、同じ欠陥がすべてに複製される。
- 分量(枚数・字数)を先に決めない。分量は、節の表で合意した役割から決まる。

## 4. 疑問の一覧

- 作業中の疑問は都度聞かず、一覧にためる。骨組みの合意と同じ往復で 1 度に出す。
- 疑問を一覧に加える前に、自分で調べられる範囲(リポジトリの資料・公開情報・コマンドの出力)で調べる(respond(`../../respond/SKILL.md`)の 3.11)。調べずに聞くと、依頼者は調べれば分かることにも答えることになる。一覧に書くのは、調べても確定しなかった疑問だけである。その疑問には、調べた範囲(検索した語と場所)を添える。依頼者は、どこまで調べた後の問いかを見て答えられる。
- 問いの書き方は `readers.md` 3. に従う。敬体で書き、答えに必要な文脈を含め、書き手が決められる事項は案にして可否を聞く。
- 着手を止める疑問(読み手が分からない)は、一覧にためず、2. の brief で聞く。
- 削るか迷う節・ページ(3.)は、一覧で依頼者に要否を聞く。
- 数値・固有名詞が欠けていたら、プレースホルダ(「[サービス名]」「約[金額]円」)で埋めない。依頼者に聞けるときは、成果物に書かず一覧で聞く。「未確定・要確認」と書くのは、聞いても確定しなかったときと、聞けないとき(非対話の実行)である。

## 5. 肉付けの規則

- 見出し(`paragraph.md` 6.)、表記・記号・出典(`sentence.md` 6.〜8.)と形式の束(`format/`)は文章品質の規範より優先する。
- 引用・参考文献のタイトルなど、原典の表記を保つべき箇所は本規範に従わなくてよい。
- 規範どうしが衝突するときは、読み手の得になるほうに従う。
- 規則のうち、資料の種類・読み手で答えが変わるものには、適用する条件と外してよい条件をその項に書く。種類で決まる条件は、`types/` の該当ファイルの 4. に書く。条件の外では、依頼者の指定と既存資料の作りを優先してよい。条件が書かれていない規則は、どの文書でも守る。
- 依頼者が渡した構成(節・ページの並び)と、確定した見出し・文言は、確認を取らずに変えない。渡された構成の順序を変える・統合する・分割するのは、論理が破綻しているとき(前提が後ろにある・同じことを 2 回言っている)だけにし、理由を 1 行添えて確認してから行う。文言を変えたいときは、差分を示して確認する。
- 自社で承認済みの版が決まっている定型の節・ページ(会社概要・体制・実績・裏表紙など)は、正本の最新版をそのまま差し込み、変えてよいのは日付と宛先だけにする。文書の部品で組み直したり、色・枠・アイコン・言い回しを加えたりしない。文書と合わずに浮くときも、定型の側は直さず、正本の持ち主に確認する。
- 合意した範囲だけを書く。求められていないユースケースへの横展開や、相手の役割を超えた質問を加えない。
- 定例・月次報告など続きの文書は、前回の最終版を土台にして、変わったところだけを直す。型と節・ページの並びは引き継ぎ、文言・数字はその回の一次情報(議事録・メール・実データ)から取り直す。前回の文言を残すのは、変化がないと確認できた項目だけにする。
- 現状(As-Is)の記述は、現行の画面・設定・契約を直接見て確かめる。確かめた日付と見た場所は、作業の記録に残す。提案時の資料から写すと、提案時に見ていなかった機能(既存のフォーム・自動返信)が抜ける。
- 執筆を別の CLI・エージェントに委譲したときは、作り手が原稿を節・ページごとに読み直し、採否を決めてから配布する。委譲先の原稿をそのまま通すと、作り手が読んでいない文が読み手に届く。

## 6. 推敲役に渡す物

推敲役には次の物を渡す。

- 文書のパス
- 素材(文書の元にした資料。録音の文字起こし・メモ・調査の記録など)のパス(事実の照合に使う)
- 読み手と目的(2. の brief)
- 規範: 本スキルの SKILL.md と、肉付けで使った束のファイル
- 宛先プロファイル(あれば)
- 前回の指摘の一覧(続きの文書・再提出のとき)
- 旧版(構成を組み替えた改訂のとき。`inspection.md` 5.)

執筆したセッションの文脈(会話・判断の経緯)は渡さない。理由と、観点の分け方、返った修正案の仕分けは `inspection.md` 5. に従う。

## 7. 指摘を受けた後

- 指摘は「直した / 残す(理由)」に仕分ける。
- 指摘を文書の全体へ機械的に適用しない。指摘が当たる範囲を確かめてから適用する。
- 同じ種類の指摘が 3 件以上あるときは、指摘された箇所を直して終えない。その種類だけを観点にして、全文をもう 1 度点検する(推敲役に渡すか、統括が 1 周読む)。同じ種類とは、規範の同じ項目に当たる指摘か、同じ直し方で直る指摘である。依頼者の指摘にも、推敲役の修正案にも当てる。この点検は推敲の往復(`inspection.md` 5.)に数えない。指摘は見つかった箇所の一覧であり、その種類の誤りの全件ではない。推量の文を言い切りに変えた箇所が 9 件指摘された文書には、同じ種類の箇所が指摘の外にも残る。
- 指摘の反映が、もう 1 度推敲に渡す改訂(`inspection.md` 5.。全文の書き直し・構成の組み替え・形式の変更など)に当たるときは、依頼者に見せる前に推敲に渡す。
- 消す・直すよう頼まれた要素は、出し直した成果物のすべての節・ページから除かれたことを確かめてから報告する。一部だけを見て全体を確かめたと報告しない。報告には実際に見た節・ページの番号を書く。
- 説明を追加する・書き換える改訂でも、判断に使う要素(判断の軸・優先順位・凡例)は消さない。優先度などがまだ確かめられていなければ、「仮説」と書いて残す。
- 宛先に固有の指摘は宛先プロファイルへ足し、どの宛先にも当てはまる指摘は retro で規範へ足す。
