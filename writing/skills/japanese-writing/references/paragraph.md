# 段落・論証の規範(L3)

## 1. 段落と論証

- パラグラフライティングを基本とする。一つの段落には一つのトピックだけを置き、先頭の文を読めばその段落の主題が分かるようにする。読者は段落の冒頭で「この段落は何について述べるか」を予測し、以降の文をその枠組みで処理する。トピックセンテンスが先頭になければ、読み終えてから遡って解釈をやり直す手戻りが起きる。段落中の他の文は、トピックセンテンスの補強・展開に限る。
  - Before: 「先日サーバーの負荷が急上昇した。原因を調べたところキャッシュ設定に不備があった。修正後は安定稼働している。」
  - After: 「今回のサーバー障害はキャッシュ設定の不備が原因だった。先日サーバーの負荷が急上昇し、調査の結果キャッシュ設定に不備があることが判明した。修正後は安定稼働している。」
- 段落の先頭で、前の段落との論理関係を接続表現で明示する。前段落との橋渡しがないまま話題を転換しない。話題が飛躍すると、読者は文章の地図を見失う。
- 因果と経緯は地の文で書く。ある事実が次の事実を引き起こす経緯は、接続詞でつないだ文にする。箇条書きを使ってよいのは、項目が同じ文法構造・同じ抽象度で本当に並んでいる要点圧縮の場面に限る。箇条書きは書き手が論理関係の組み立てを省略できるぶん、その負荷が読者に転嫁される。見出しの直後に箇条書きが 3 つ以上並んでいたら、項目間に「そのため」「だが」で言える関係が隠れていないか疑い、隠れているなら地の文に戻す。議事録の決定事項一覧のように、項目が独立していて互いに因果でつながらない場合は箇条書きのままでよい。
  - Before: 「・在庫が減った ・発注担当が気づかなかった ・欠品が発生した」
  - After: 「在庫が減っても発注担当が気づかず、そのまま欠品した。」
- 段落分けの偏りを避ける。改行なしで続く「壁」は視覚的な休憩点を奪い、1 文 = 1 段落の「細切れ」は本来つながっている論理を寸断する。
- 論証は一方向に進める。結論を出してから反論を処理し、結論を言い直す構成にしない。反論と疑念を処理してから、結論を一度だけ置く。
- 読者が立てそうな誤った解釈は、明示的に否定してから本当の理由を述べる。「AではなくB」と否定するときは、否定の根拠を一文添える。
- 「後の章で扱う」のような前方参照は、論証が一段落した位置に置く。途中に挟んで流れを切らない。

## 2. 論証の厳密さ

- 推量・可能性・読者の疑念・反実仮想として書かれた文を、根拠なく断定へ変えない。断定に直せるのは、本文内の根拠で命題が確定している場合に限る。
- 区別すべき対象(別々の決定、別々の原因)を一括りの言葉でくくらない。複数の要因がある事象を単一の原因に還元しない。
- 因果を主張するときは、その機構(なぜそうなるのか)を一文で示す。
- 優劣の関係にない対象を、優劣の軸(質が高い/低い、良い/悪い)で並べない。並べる軸は対象を実際に区別する性質にし、どの場面でどれを選ぶかを書く。「機械では判定できない基準に使える方法」を、判定が決定論的な方法の下位に置くのは、軸の取り違えにあたる。
- 質・良し悪しを主張するときは、判断の観点を先に定義し、観点ごとに水準の高い例と低い例を示す。観点が複数あるなら、観点ごとに節を分ける。
- 主張を置いたら、それを支える定義・例・関係を同じ節に置く。手段や方式を並べただけで、裏づけを後の節へ回さない。同じ節で裏づけを示せないなら、断定(「品質は検証の質で決まる」)でなく提示(「設計では 2 つの観点が要る」)の形にする。
- 検出・保証・解決を「必ず」できるかのように書かない。条件付きで正確に述べる(「〜しやすい」「〜が成り立つときに限り」)。
- 章・節をまたいで、同じ概念の扱い・分類・用語の地位を一致させる。「次節で扱う」と逃がした論点は、本当にそこで回収する。

## 3. 接続詞

- 接続詞は文と文の論理関係(順接・逆接・並列・因果)を明示する道しるべとして使う(石黒圭は論理・整理・理解・展開の 4 種に分類する)。なければ読者が前後関係を自力で推測することになり、多すぎたり不適切だったりすると読者の予測を裏切る。乱用と不足のどちらも避ける。
- 接続詞ごとに効力の及ぶ範囲(射程)が違うことに注意する。「あるいは」は近接する語句の並列を、「一方」は段落・文脈レベルの対比を示す。対比関係にない事柄を「一方」でつながない。
  - Before: 「今回のリリースではUIを刷新した。一方、バグを1件修正した。」
  - After: 「今回のリリースではUIを刷新した。また、バグを1件修正した。」
- 同じ接続詞(特に逆接の「しかし」)を連続させない。どこが本当の対立点か不明瞭になる。射程の合う類語に言い換える。

## 4. 読み手の負荷の管理

- 読者を知識・意欲・目的の 3 軸でとらえる(結城浩による)。何を知っているか、どの程度読みたがっているか、何を求めて読むかで、説明の詳しさ・展開の速さ・情報の優先順位を変える。個別の規範に従うかどうかで迷ったら、「この読者の知識・意欲・目的に照らして、それは負荷を下げる方向に働くか」を問い直す。
- 議論に効く具体(固有名詞・数値・実例)で接地する。段落から固有名詞・数値・実例をすべて抜いても文意が変わらないなら、その段落は一般論の域を出ていない。これは書き方でなく素材の不足のサインなので、言い回しを変え続けず、素材の収集(`composition.md`)に戻る。素材が本当に手元にないときは、推測で埋めずに、何を確認すれば書けるかを一言添えて空欄を残す。
- 議論に効かない装飾的精度(時刻、HTTP ステータス、カバレッジ率など)や、後で参照しない固有名(ファイル名、関数名、識別子)は省き、一般的な言い方で済ませる。接地と省略は同じ基準の両面であり、「その具体が読み手の理解を実際に助けるか」で決める。
- 抽象的な言い回しの指す内容が文脈から一意に決まらないときは、その場で丸括弧の同格挿入で特定し、読者に前を読み返させない。
- 括弧の補足は、想定読者がその補足だけで理解を進められるかを確かめる。読者が知らない概念を参照する補足(「Claude Agent SDK と同じ基盤」)は、調べる手間を足すだけで補足にならない。何であって何に使えるかを書くか、削る。
- 一言では説明しきれない内容を括弧に押し込まない(「(トークン間の関係数が 2 乗で増える)」)。本文で説明するか、図にするか、削る。
- 新しい例や場面を追加するときは、前の例と何が違うのか、なぜ必要なのかを前置きする。
