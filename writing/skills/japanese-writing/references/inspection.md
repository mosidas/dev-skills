## 1. はじめに

- 検査の原則は「検出は機械、判断は書き手(または AI)」とする。書き手は自分の癖を認識しにくいため、疑いの検出はスクリプトが決定的に行い、直すかどうかは文脈で判断する。検出は疑いの提示であって、機械的に全部直せという指示ではない。
- 検出件数で作業を止めない(lint であって CI ゲートではない)。各スクリプトは、入力エラー(ファイル不在等)のときだけ exit code 1 を返し、検出結果の件数に関わらず exit code 0 で終わる。
- 検査は SKILL.md の工程の「検査」「収束」を担う。修正が新しい指摘を生まなくなる状態まで、検査と修正を繰り返す(6.)。

## 2. 検査スクリプト

### 2.1. lint.py(疑いの検出)

```sh
uv run .claude/skills/japanese-writing/scripts/lint.py <file.md> [--json]
```

- 禁止語・翻訳調・否定肯定対比の反復・文長の均質さ・体言止め率・段落頭の接続詞率・語彙多様性・英語統語の疑い・段落の具体性(一般論臭)などを機械的に検出する。
- ジャンルが明確なら `--genre essay|tech|business` を指定する。コーパス校正済みの閾値プロファイルに切り替わり、誤検知が減る(未指定時は共通の保守的閾値)。
- 収束ループでは、前回の `--json` 出力をファイルに保存して `--baseline <前回のjson>` に渡すと、今回の検出を resolved / new / persisting に自動仕分けできる。台帳(4.)への追記は new と persisting だけを見れば足りる。
- `--experimental` を付けると、定量校正が済んでいない実験的検出器(段落頭接続詞率・構文テンプレート・Markdown 構造の癖など)も出力される。信頼度が低いことを踏まえて扱う。

### 2.2. outline.py(構造素材の抽出)

```sh
uv run .claude/skills/japanese-writing/scripts/outline.py <file.md> [--json]
```

- 見出し・各段落の先頭文・箇条書きプレースホルダを行番号付きで抽出する。スケルトン通読(5.)への入力に使う。見出し統計(体言止め率・テンプレ見出し語彙など)も出すが、判断はせず材料の提示に留まる。

### 2.3. terms.py(用語素材の抽出)

```sh
uv run .claude/skills/japanese-writing/scripts/terms.py <file.md> [--json]
```

- カタカナ複合語・ASCII 略語・固有名詞らしき語を、初出行・出現回数・説明マーカーの有無つきで初出順に列挙する。用語が初出で説明されているか(`sentence.md` 1.)の確認材料に使う。説明済みかどうかの判断は機械が行わない。

### 2.4. semantic.py(話題平板性の検出、opt-in)

```sh
uv run .claude/skills/japanese-writing/scripts/semantic.py <file.md> [--json] [--genre essay|tech|business]
```

- 文埋め込み(既定モデル cl-nagoya/ruri-v3-310m)で、lint.py が見ない意味の単調さを検出する(EXPERIMENTAL)。指標は 3 つで、`semantic_topic_flatness`(warn。隣接文の意味類似度の起伏の乏しさ = 一つの話題を同じ歩幅で刻み続ける癖)が主指標、`semantic_repetition_max`・`topic_jump_min`(いずれも info)は参考指標とする。
- 重量級の opt-in 検出器であり、既定の検査ループ(1 周ごとの lint)・診断モード(9.)には組み込まない。実行するのは次のときに限る。
  - lint と構造レビューが収束してもなお、話題の平板さ・言い換え反復を疑うとき。
  - ユーザーが意味的検出を指示したとき。
- 初回実行時は torch + sentence-transformers の依存解決と、モデル約 1GB の Hugging Face ダウンロードが発生する(2 回目以降はキャッシュを再利用し、オフラインでも動作する)。初回コストがかかる旨を実行前にユーザーへ一言断る。
- 文数 10 未満の文書は、統計が不安定なため検出せずスキップする。スキップされない場合でも、数十文程度の短い文書では指標が少数箇所の類似度に左右され、人間の文章に warn が出ることもある(fixtures での実測)。検出は疑いの提示として扱い、1. の原則(判断は書き手)を適用する。
- 検出への対応は 3. の表に従う。閾値は原典のコーパス校正(2026-07)の値をそのまま使う。

## 3. lint カテゴリごとの対応方針

検出されたカテゴリの節を読み直してから、文脈に照らして「直す/直さない」を判断する。一度読んだ記憶だけで直すと周回のたびに基準が緩むため、その周でヒットしたカテゴリの規範をそのつど読み直す。

| カテゴリ | 何を疑うか | 対応 |
| :-- | :-- | :-- |
| `forbidden_phrase` | LLM 常套句・結論の押し付け(一部は severity=info の弱いシグナル) | `sentence.md` 7. の該当分類を読み、その表現が本当に必要か検討する。多くは削るか具体的な言い方に置き換える |
| `translationese` / `translationese_morph` | 英語直訳調 | `sentence.md` 8. の対応パターンの before / after に沿って書き直す |
| `antithesis_repetition` | 「〜ではなく」型対比の反復(比率で severity 3 段階) | 全部直す必要はない。最も重要な対比だけ残し、他は肯定文・具体例に変える(`sentence.md` 4.) |
| `low_sentence_variance` / `low_burstiness` | 文長が均質でリズムが単調(low_burstiness はコーパス実測で弁別力が高く、信頼してよい) | 一番言いたい文を短くする、背景説明をあえて長くする。短文と長文を隣接させる(`sentence.md` 4.) |
| `nominal_ending` | 体言止めが「1 つもない」こと(人間的修辞の欠如の疑い。多用の検出ではない) | 機械的に増やさない。他の検出と合わせた総合判断の参考情報として扱う。開発ドキュメントでは体言止めを避ける規範(`format.md` 3.)が優先 |
| `uniform_paragraph_structure` | 段落あたり文数が揃いすぎ | 濃淡(`composition.md` 4.6)に立ち返り、重要な段落を厚く、そうでない段落を短くする |
| `repeated_sentence_lead` | 文頭の型の使い回し(info。人間の意図的反復と区別がつかない) | 書き出しを変えるか文構造を組み替える(`sentence.md` 4.)。強く直すべき指摘ではない |
| `low_lexical_diversity_ttr` / `_mtld` | 語彙の使い回し(4000 字未満の文書はスキップ) | 類語的言い換えでなく、より具体的な語への置き換えを探す(`sentence.md` 3.) |
| `english_syntax_inanimate_subject` / `inanimate_subject_morph` | 無生物主語 + 他動詞 | 主語を人や状況に戻すか、述語を状態描写に変える(`sentence.md` 8.) |
| `low_specificity` | 固有名詞・数値・実例が乏しい一般論の段落(info、弁別力は控えめ) | 言い回しでなく素材の問題。`composition.md` 3.6(素材の収集)と `paragraph.md` 4.(接地)に従い、集め直してから書き直す |
| EXPERIMENTAL 系(`--experimental` 指定時のみ) | 段落頭接続詞・構文テンプレート・Cleft 構文・太字多用・箇条書き偏重・定型見出し等 | 参考情報として構成を見直す。信頼度が低い前提で扱う |
| `semantic_topic_flatness`(semantic.py、opt-in) | 隣接文の意味類似度の起伏が乏しい(話題の平板さ。表層の言い換えでは消えない) | 具体例への降下・視点の転換・短い脱線で意味的な緩急をつける。修正は文単位の言い換えでなく、段落・節の再構成(`composition.md` 4.6 の濃淡)になりやすい |
| `semantic_repetition_max` / `topic_jump_min`(semantic.py、opt-in) | 言い換え反復の少なさ・話題飛躍のなさ(いずれも info の参考指標) | 単独では直さない。`semantic_topic_flatness` と合わせた総合判断の材料として扱う |

- 連体修飾の入れ子は、原典のコーパス校正で弁別力なしと判明し検出器が削除されている。機械検出はできないため、`sentence.md` 8. の before / after を参考に人手で判断する。
- lint に出ないからといって問題がないとは言い切れない。表層の検出と別種の問題(一般論臭・構成の乱れ)は、5. のレビューで拾う。
- 判断に迷ったら、その一文を声に出して読み、実際に人が話す言い回しに近いかで決める。

## 4. 判断台帳

- 検出・レビューで見つけた項目一つひとつに、「直した」か「残す(理由)」かをその場で記録しながら進める。記録しないと「見た・考えた・流した」のどこかで判断が宙に浮く。
- 台帳は第一候補としてチャットの応答テキスト内で管理する。文書が長い・周回が多いときに限りファイル化し、その場合も対象文書と同じディレクトリに置かず、スクラッチパッドか一時ディレクトリに置く(10.)。
- 1 行の形式は次のとおり。「残す」には理由の種類(固有名詞由来・文脈上必要・技術用語・ジャンル上自然など)を一言添える。理由なしの「残す」は判断の放棄にあたる。

```
- [直した] paragraph_lead_conjunction: 3段落目冒頭「しかし、」を削除し前段落と地続きにした
- [残す/固有名詞由来] forbidden_phrase「多角的」: 製品名「多角的レビュー機能」の一部なので変更不可
- [残す/文脈上必要] antithesis_repetition: この段落の対比は論旨の核なので残す
```

- 台帳は周回のたびに追記する。前の周で「残す」と決めた項目を悩み直す必要はない。

## 5. 構造レビューと読みやすさレビュー

- lint は文レベルの表層しか見ない。箇条書き主体の文書では lint がほぼ素通りするため、構造レビューが主役になる。レビューで見つけた問題も、lint の検出と同じ台帳へ 1 行として起こす。
- 構造レビュー(スケルトン通読): `outline.py` の出力(見出し・段落先頭文)だけを続けて読み、`composition.md` 7. の 5 点(論旨・見出し・書き出しの型・濃淡・結び)を確かめる。
- 読みやすさレビュー: 語順・読点・一文一義・主語述語の距離・こそあど・冗長は、機械的な閾値化ができない判断領域なので、毎周回、目視で判断する。見る対象は周回で変える。
  - 1 周目: 段落単位の粗い読みにくさ(段落あたり文数の偏り、一段落複数主張)。構成レベルの問題は文単位の修正より先に直す。
  - 2〜3 周目: 文単位に降りる。`sentence.md` 2.(文の組み立て)をその周でヒットしたカテゴリと合わせて読み直し、一文が長い箇所・読点が切れ目と一致しない箇所・こそあどが指示対象から離れた箇所を優先する。
  - 収束直前: `sentence.md` 3.〜4. と `paragraph.md` のカタログに目を通し、拾えていないパターンがないか確認する。文書タイプ・ジャンル上の意図的な逸脱は「残す/ジャンル上自然」として台帳に記録する。
  - 最終パス: 通読で全体のリズムを確かめる(7.)。

## 6. リライトの選択と収束

### 6.1. 改稿を一律に適用しない

- リライトは「直す箇所を選ぶ」作業であって、「全文を仕上げ直す」作業ではない。同じ変換(見出しの結論化、箇条書きの地の文化)を例外なく全項目へ当てると、元の文書が持つ自然な濃淡を消し、処理の均質さ自体が新しい機械臭になる。
- 着手前に原文の見出し・節を一覧し、各行に keep / change を割り振ってから手を動かす。デフォルトは keep。change に倒すのは、直すことで読者の得が具体的に言える場合だけとし、全体の 3 割を超えるなら理由を台帳に書く。この割り振りを台帳の最初の記録にする。
- 歯止めの具体則:
  - 見出しの結論化は、開いて中身を探す手間が実際に大きい 2〜3 箇所まで。
  - 箇条書きの地の文化は、因果・経緯が隠れている箇所だけ。真に並列で走査性に価値がある一覧(宿題・比較軸)は残す。
  - 素材不足の印を機械的に全欠落へ付けない。本当に埋めるべき箇所を絞る。
  - 著者の意図・方針を新設しない。元文書の「未定」を断定へ格上げするのは捏造にあたる。
  - 元版が既に良い箇所は触らない。口語の引用・略記・節ごとの不揃いといった生の痕跡は、人間が書いた証拠であり資産として扱う。整形するのは読解を実際に妨げている箇所だけにする。
- 改稿後、同じ種類の変換が全項目へ一律に及んでいないかを数え、及んでいたらいくつか元に戻して濃淡を復元する。

### 6.2. 収束の状態

- ループは回数でなく状態で終える。出口は次の 2 条件が両方そろったときだけとする。
  1. 台帳上、すべての項目が「直した」か「残す(理由つき)」に仕分けられている。
  2. 「直した」修正が新しい検出を生んでいない(lint を再実行して新規発生がない)。
- 2 条件がそろったら最終パス(7.)に進む。最終パスで違和感が出たら、台帳に追加してループへ戻る。
- 同じカテゴリの検出が減らないときは、ジャンル・文体上むしろ自然(理由をつけて「残す」)か、単発修正では直らない構成の問題(段落の並べ替えなど大きな手直し)かを疑う。

### 6.3. 発散ガード

- 同じ検出が 2 周連続で「直しては再発」するなら、機械的な修正を重ねても収束しない。台帳上「残す」に倒して理由を明記するか、文・段落の構造そのものを書き直す(語順の入れ替え、文の分割・統合、視点の変更)。書き直したら新しい項目として台帳を更新する。

## 7. 最終パス(自己点検ループ)

lint と台帳が収束しても、それは既知のパターンが消えたことしか意味しない。最後に必ず、初見の読者のつもりで通読し、次を順に当てる。

1. 冒頭の 3 段落だけを読み、結論の先取りが過剰でないか。
2. 段落ごとの文末を目で追い、同じ形が連続していないか。
3. 声に出して読んだときに息継ぎの位置が不自然でないか(長すぎる一文の兆候)。
4. 書かれている内容が、本当に言いたいことからずれていないか。借り物の意見に見える箇所はないか。

気づいた点は台帳に起こして 6. に戻り、なくなったら完了とする。

## 8. 手動チェックリスト(スクリプト不可環境)

`uv` が使えない環境では、lint の各検出器を次の目視手順で代替する。まず 1〜3 を流し読みで確認し、気になる文章なら 4〜10 に進む。進め方(台帳・収束)はスクリプトを使う場合と同じ。

1. 禁止語・LLM 常套句: `sentence.md` 7. の表現を探す。1 文書に 3 個以上で要注意。
2. 翻訳調: 「〜することができる」「〜という点で」等を探し、`sentence.md` 8. で言い換えを試す。
3. 否定 → 肯定の対比: 「〜ではなく、〜」の回数を数える。3 回以上なら最重要の 1 箇所以外を変える。
4. 文の長さのリズム: 短い文(20 字前後)と長い文(60 字以上)が両方あるか。全部が 30〜40 字なら単調の疑い。
5. 体言止め: 地の文で文末が名詞の文を数える(開発ドキュメントでは原則使わない)。
6. 段落頭の接続詞: 全段落の 3 割以上が「しかし」「また」「そして」等で始まっていたら要注意。
7. 段落の均質さ: ほぼすべての段落が同じ文数ならテンプレートの疑い。
8. 文頭・構文の使い回し: 同じ書き出し・同じ骨格が 3 回以上ないか。
9. 語彙の使い回し: 同じ内容語の繰り返し、「重要」「様々」など便利な抽象語への依存がないか。
10. 英語統語: 無生物主語 + 他動詞、名詞修飾の 3 連鎖、「それは〜である。なぜなら〜だ」の 2 文構成がないか。

`outline.py` が使えない環境では、見出しと段落先頭文を手で拾ってスケルトン通読を行う。

## 9. 診断モード(score)

- 「この文章は AI っぽいか」「AI 臭さを採点して」という書き換えを伴わない依頼には、文書を一切書き換えず、スコアと根拠と「直すなら何からか」の 3 点だけを返す。リライトを求められたら通常の工程に切り替える。
- 深さは 2 段階とする。quick(既定)は lint 1 回(ジャンルが分かれば `--genre`)とスケルトンの一瞥で約 30 秒。full は `outline.py`・`terms.py` を加え、構造レビュー・読みやすさレビューを判断に織り込む。診断では収束ループは回さない(1 周の評価で完結する)。
- スコアは 0〜100 の自然度で、高いほど自然(AI 臭が薄い)。二層で作り、内訳を必ず開示する。
  - 機械ベース(決定的): `減点 = (critical×8 + warn×4 + info×0.5) × (1000 / max(文書の文字数, 1000))`、`機械ベース = max(100 − 減点, 20)`。短い文書ほど 1 件の重みが大きい。本文が実質 100 字未満なら、スコアを出さず「診断対象として短すぎる」と返す。
  - 判断調整(±15 点): full では、lint が拾えない構造の機械臭(全節同型、フラット列挙、確信度の平坦化、So What の空洞)を減点し、誤検知気味でも文脈上自然な検出は減点を戻す。quick では調整せず、精度が粗い旨を明記して機械ベースをそのまま使う。最終スコアは 0〜100 に切り詰める。
- スコアは判断を含む目安であり、同じ文書でも数点は揺れる。CI のゲートに使う数値ではない。この注意を結果に一言添える。

| スコア | バンド | 伝え方の例 |
| :-- | :-- | :-- |
| 90〜100 | 自然 | AI 臭はほぼ見当たらない。指摘があっても好みの範囲 |
| 70〜89 | 軽微 | 数カ所に癖が残るが、読者が「AIっぽい」と感じる可能性は低い |
| 50〜69 | 要修正 | 表層か構造のどちらかに明確な機械臭がある。直す価値がある |
| 0〜49 | 濃厚 | 複数のカテゴリで強く検出。リライト推奨 |

- 出力は、スコアとバンド(内訳つき)、理由トップ 3〜5(カテゴリ名でなく中身で、代表箇所の行番号つき)、直すなら何から(効果の大きい順に 2〜3 個)の順で返す。理由は lint の detail の転記でなく、文書の文脈に即して言い直す。

## 10. 作業ファイルの扱い

- 判断台帳・lint の JSON・下書きのバックアップ等の中間ファイルは、対象文書と同じディレクトリに置かない。スクラッチパッドか `mktemp -d` の一時ディレクトリに置く。
- 完了したら中間ファイルをすべて削除する。最終的に残すのは完成した文書本体だけとする。
