# 仕様書・規約・アーキテクチャ指針の型

## 1. この型が答える問い

仕様書・規約が答える問いは「実装・運用・判断を、読み手によらず同じ結果にするには何に従えばよいか」である。読み物ではなく参照される文書であり、解釈が読み手ごとに割れた時点で機能していない。網羅性と一意性を、読み手の負荷より優先する数少ない文書タイプにあたる。

## 2. 必須要素

- 目的と適用範囲(何に適用され、何に適用されないか)。
- 用語の定義(初出定義に加え、必要なら一覧)。
- 要請レベルの規定。規約では RFC2119 対応語句を使い、対応表を文書の最初で明示する(`format.md` 3.)。
- 本文(仕様・規則・指針)。
- 規約どうしが競合したときの優先順位。
- アーキテクチャ指針では、決定の理由と見送った選択肢(採らなかった理由つき)。理由のない規則は、状況が変わったときに変更してよいかを後任が判断できない。

## 3. 構成の型

- 見出しは付番し(`format.md` 2.)、節は参照される単位で切る。文中参照は節番号で行う。
- 並べる軸は読者の探索目的に合わせる(`composition.md` 3.4)。設定リファレンスはカテゴリー、手続き規定は時間、判断基準は階層が合いやすい。
- 例示するコードには要請レベルに応じたラベルを付ける(`format.md` 5.)。
- 分類は MECE を厳密に点検する(`composition.md` 3.2)。規約の抜けは「書かれていないから自由」と解釈され、重複は矛盾の温床になる。

## 4. 品質基準

- 同じ文を二人が読んで、同じ判断に至る(一意性)。
- 曖昧語(「など」「あたり」「基本的に」「適宜」)を使わない。断定できることは断定し、例外があるなら例外の条件を明示的に書く。
- 条件・保証は正確に書く(`paragraph.md` 2.)。「必ず〜される」と書けるのは機構がそれを保証する場合に限る。
- 要請レベルの語句(する・しなければならない・推奨される・してもよい)が、意図した強さと一致している。
- 表記が統一されている(`format.md` 7.)。仕様書での表記ゆれは「別のものを指しているのか」という誤読に直結する。

## 5. やりがちな失敗

- 規則だけ書いて理由を書かない。後任が変更の可否を判断できず、規則が形骸化するか盲従される。
- 「原則として〜する」で例外条件を書かない。原則の語が例外の存在だけを匂わせ、いつ逸脱してよいかは誰にも分からない。
- 読み物向けの演出(結論見出し、修辞的な導入)を持ち込む。参照される文書では、見出しは対象を指す句が最も速い。

## 6. 共通規範への例外と重み付け

- 例外: 見出しに結論を埋め込まない。`format.md` 2. の「内容を特定できる具体的な句(セリフにしない)」をそのまま適用し、`composition.md` 4.5 の結論見出しは使わない。
- 例外: リファレンス型の節は、地の文でなく表・定義リスト中心で書いてよい。
- 重み付け: 一意性・網羅性(MECE)・要請レベルの正確さ・表記統一を、文の簡潔さより優先する。事実と意見の峻別(`sentence.md` 6.)は最も厳格に適用し、仕様(保証)と設計意図(意見)を混ぜない。
