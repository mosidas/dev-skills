# 移行・廃止(Migration & Deprecation)

既存の仕組みを**置換・廃止・移行**する変更のための知識 port。新規構築と異なり、「壊さずに移し、使われなくなってから消す」規律が要る。置換・廃止・移行を含む作業で、仕様(dev-spec)と実装(dev-implement)に注入する。

前提: 観測可能な挙動はすべて事実上の契約になる(**Hyrum's Law**)。「誰も使っていないはず」を理由に消さない。**使用ゼロを観測で確認してから**消す。

## 1. いつ使うか

- 既存モジュール/API/データモデルの置換・統合・分割。
- レガシーの段階的リプレース。非推奨化(deprecation)と削除。
- 既存機能の拡張が、実質は既存挙動の置換・廃止を含む場合。

## 2. 移行パターン(置換の進め方)

- **Strangler Fig(段階的絞め殺し)**: 新実装を脇に立て、機能単位で旧→新へトラフィック・責務を少しずつ移す。全移行が済むまで旧と新が共存する。大規模置換の既定。
- **Adapter(アダプタ)**: 旧インターフェースを保ったまま、内部を新実装へ委譲する。呼び出し側を変えずに実体を差し替えられる。
- **Feature-flag(フラグ切替)**: 新旧をフラグで切替可能にし、段階的に新へ寄せる。問題時は即座に旧へ戻せる。

いずれも「新旧並行 → 段階移行 → 旧の使用ゼロを確認 → 削除」の順を踏む。

## 3. 削除の前提(Verify-Zero-Usage)

- 削除対象が**実際に使われていない**ことを、メトリクス・ログ・参照解析で確認する(呼び出し回数・参照箇所がゼロ)。
- 後方互換を壊す削除は、非推奨化期間と移行ガイドを経てから行う。データの移行は可逆性(ロールバック可能性)を担保する。

## 4. 廃止判断(コードは資産でなく負債)

コードは維持コストを生む負債である。残すより消す方が良いことが多い。廃止を判断する問い:

1. その機能に**一意の価値**があるか(代替で置き換わるか)。
2. 依存している consumer はどれだけあるか。
3. 代替手段は存在するか。
4. consumer ごとの移行コストはどれだけか。
5. 廃止しない場合の維持コストはどれだけか。

- **advisory(推奨的廃止)を既定**とする。compulsory(強制・遮断)は維持コストがそれを正当化するときのみ。
- **Churn Rule**: 共有基盤を変更する側が、その移行の責任とコストを負う(consumer に丸投げしない)。
- **Zombie code の兆候**: owner が居らず、しかし consumer は存在するコード。放置せず owner を定めるか、計画的に移行・廃止する。

## 5. 各工程での適用

- 仕様(dev-spec): 要求が置換・廃止・移行を含むなら、移行方針(パターン選択・削除条件)をスコープ・前提に明示する。
- 計画(dev-decompose の File Structure Plan): **削除対象**を明示し、移行パターンと「使用ゼロ確認」の手順を計画に含める。後方互換を壊す変更は SemVer 方針と整合させる。
- 実装(dev-implement): 削除タスクでは DB レコードだけでなく紐づく関連リソース(ストレージ・キャッシュ・外部データ)のクリーンアップまで行う。
