# 用語集 — 良いスキルの設計

スキルは確率的なシステムから決定性を引き出すために存在する。根本の徳は **predictability(予測可能性)** であり、以下の用語はすべてそれを動かすためのレバーである。本ファイルは `SKILL.md` の disclosed reference(必要時に読む定義集)である。

用語は軸ごとにまとめる。**Invocation**(スキルがどう呼び出されるか)、**Information hierarchy**(内容がどう並ぶか)、**Steering**(実行時の挙動をどう形づくるか)、**Pruning**(どう無駄をそぎ落とすか)。**失敗モード** は、それを治すレバーの隣に `失敗モード` と付けて置く。

定義文中の **太字語** はこの用語集の見出し語である。見出しから引く。

## 目次

- Predictability(予測可能性)
- Invocation(呼び出し)
- Information hierarchy(情報の階層)
- Steering(操縦)
- Pruning(剪定)

## Predictability(予測可能性)

スキルが、毎回のrunでエージェントに同じ「やり方」をとらせる度合い。同じ出力ではなく同じプロセスである(ブレインストーミングのスキルは予測可能に発散すべきで、トークンは変わるが挙動は変わらない)。他のすべての用語が奉仕する根本の徳。コストと保守性はこれの症状であって、対立する目標ではない。

_避ける語_: 一貫性、信頼性、頑健性、出力の決定性

## Invocation(呼び出し)

スキルがどう到達されるか。そして選択に伴って払う 2 つの負荷。

### Model-invoked(モデル呼び出し)

**description** を持ち、エージェントがそれを見て自律的に発火できるスキル。人間が名前を打って呼ぶこともできるため、model-invoked は常に user 到達を「含む」。モデル専用の状態は存在しない。description はエージェントの発見可能性を「足す」だけで、人間の到達を「奪う」ことはない。その発見可能性と引き換えに、毎ターン恒常的な **context load** を払う。他のスキルからも到達できる。description が到達可能性を与えるからである。内容がすべて **reference** の model-invoked スキルは、共有 reference の置き場にもなる。複数のスキルが必要とする reference を 1 か所に置ける。エージェント自身がそのスキルへ到達する必要があるときだけ model-invocation を選ぶ。手動でしか発火しないなら description を落とし、context load を払わない。

_避ける語_: 能力、ツール、機能

### User-invoked(ユーザー呼び出し)

**description** を外したスキル。エージェントからは見えず、人間が名前を打ったときだけ到達できる(model-invoked が user かつ agent であるのに対し、user のみ)。エージェントの発見可能性を、ゼロの **context load** と引き換えにする。description を持たないため、人間以外は到達できない。他のどのスキルからも発火できない。

_避ける語_: 手続き、ワークフロー、コマンド

### Description

スキルの機械可読なトリガーであり、**model-invoked** スキルが常時読み込みを強いられる唯一の **context pointer**。その存在自体が invocation の軸を決める。残せば model-invoked(かつ他スキルから到達可能)、消せば **user-invoked**(人間のみ到達可能)になる。model-invoked スキルの **context load** の源。

_避ける語_: frontmatter、要約

### Context pointer(文脈ポインタ)

エージェントの文脈内に保持され、文脈外の素材を名指しし、それへ到達する条件を符号化する参照。**description** は最上位の context pointer(文脈ウィンドウ → スキル)であり、disclosed ファイルへのポインタは 1 段下の同じ対象である。到達の「タイミング」と「確実さ」を決めるのは、ポインタの向き先ではなく文言である。必須の素材が弱い文言のポインタの陰にあるのは variance(ばらつき)のバグである。まず文言を鋭くし、それでも駄目なときだけ素材をインライン化する。

_避ける語_: リンク、参照、import

### Context load(文脈負荷)

**model-invoked** スキルがエージェントの文脈ウィンドウに課すコスト。常時読み込まれる **description** が、トークンと注意の両方を消費する。**user-invoked** スキルが description を持たないことで免れるもの。model-invoked スキルを増やす分割へのブレーキ。

_避ける語_: トークンコスト、文脈の肥大

### Cognitive load(認知負荷)

**user-invoked** スキルが人間に課すコスト。どのスキルが存在し、いつどれへ手を伸ばすかを人間が覚えておく必要がある(人間が索引になる)。**model-invocation** がエージェント発見可能になることで取り除くもの。user-invoked スキルを増やす分割へのブレーキ。最小化すべきコストではない。人間の主体性の対価であり、一部のスキルを user-invoked に留める理由である。人間の判断が要る場所で払い、要らない場所で取り除く。

_避ける語_: 人間の索引、負担、オーバーヘッド

### Router skill(ルータースキル)

他の user-invoked スキルを指すことを役割とする **user-invoked** スキル。各スキルとその使いどころを名指しし、人間が覚えるスキルを多数から 1 つに減らす。ヒントを出せるだけで発火はできない。user-invoked スキルは **description** を持たず、人間以外は到達できないからである。user-invoked スキルが増えたときの **cognitive load** への処方箋。

_避ける語_: ディスパッチャ、メニュー、レジストリ、索引

### Granularity(粒度)

スキルをどれだけ細かく分けるか。細かく分けるほど 2 つの負荷のどちらかを払う。model-invoked スキルを増やせば **context load**(description が文脈を混雑させ注意を奪い合う)、user-invoked スキルを増やせば **cognitive load**(人間が覚えて手を伸ばす対象が増える)。分割を導く 2 つの切り口がある。**invocation** による切り口では、それを発火させる固有の **leading word**(プロンプトで実際に使うトリガー語)があるとき model-invoked スキルを切り出す。**sequence** による切り口では、ある step の **post-completion steps** を隠す必要があるとき steps の連なりを切る。逆に、連なりをまとめると各 step の post-completion steps が後続にさらされ、premature completion を招く。

_避ける語_: チャンク化、モジュール化

## Information hierarchy(情報の階層)

スキルの内容がどう並ぶか。各要素が階段のどこまで下がるか。

### Information hierarchy(情報の階層)

エージェントがどれだけ即座に必要とするかで順位づけたスキル内容の階段。2 つの切り口(ファイル内かポインタの陰か、step か reference か)で作られる 1 本の階段。段は次のとおり。

- **Steps** — ファイル内、一次
- **Reference**(ファイル内) — 二次
- **Reference**(disclosed) — **context pointer** の陰

**steps** を持たないスキルは下 2 段だけを使う。多くは正当にフラットな並列集合(例: レビューの全ルールが 1 段に並ぶ)であり、匂いではなく妥当な配置である。階層は invocation とは独立で、スキルは all steps でも all reference でも両方でも、model / user のどちらでもよい。steps を持つスキルで、disclosed にすべき in-file reference は steps を埋もれさせ、それらに注意を向けるかどうかをコイン投げにする。可読性だけでなく variance のレバーである。階段の上を読みやすく保ち、下げられるものは下げる。

_避ける語_: 構造、組織、レイアウト

### Steps

エージェントが実行する順序づけられた動作。スキルがそれを持つとき内容の一次の段であり、`SKILL.md` に載る価値を得る部分。すべてのスキルが steps を持つわけではない。all steps でも、all **reference** でも、両方でもよく、invocation とは独立である。各 step は **completion criterion** で終わる(明確または曖昧)。

_避ける語_: ワークフロー、指示、振り付け

### Reference

エージェントが必要時に参照する素材。定義、事実、パラメータ、例、条件つき指示。スキルが **steps** を持つときはそれに次ぐ二次であり、持たないときは内容そのものである。あるいはスキルの外に存在する(**external reference** を見よ)。**context pointer** 経由で到達し、**progressive disclosure** の第一候補。

_避ける語_: 補足資料、ドキュメント、背景

### External reference(外部リファレンス)

スキルシステムの外に存在する **reference**。description も steps も持たず、呼び出せない素のファイルで、どのスキルからも指せる。単独で発火する必要のない共有 reference の置き場であり、2 つの **user-invoked** スキルが使える唯一の共有の置き場でもある(どちらも description を持たず、互いを発火できないため)。

_避ける語_: ドキュメント、リソース、ナレッジベース

### Progressive disclosure(段階的開示)

**reference** を階段の下へ動かすこと。`SKILL.md` の外へ、**context pointer** の陰へ出し、上を読みやすく保つ。主にトークン最適化ではない。**information hierarchy** を守る手段である。**branch** によって正当化される。一部の branch だけが必要とするものを disclose し、すべての経路が必要とするものをインラインにする。必須の素材でポインタの発火が不確実なら文言を鋭くし、それでも駄目なときだけインラインに戻す。

_避ける語_: 遅延読み込み、チャンク化

### Co-location(共置)

エージェントが同時に必要とする素材を 1 か所に置くこと。概念の定義・ルール・注意点を 1 つの見出しの下にまとめ、ファイル中に散らさない。1 か所を読めば隣も一緒に入るようにする。**information hierarchy** のファイル内の相棒。階層は要素が「どこまで下がるか」を順位づけ、co-location は下がった先で「隣に何が来るか」を決める。reference の正しい書式に公式はない。テストは、スキルがエージェント向けに書かれたドキュメントのように読めることであり、まとまった素材はそう読め、散った素材はそう読めない。**Duplication** とは異なる。あちらは 1 つの意味を 2 か所で繰り返すが、散逸は 1 つの意味を多数に断片化する。

_避ける語_: グルーピング、クラスタリング、凝集

### Sprawl(冗長化)

_失敗モード。_ 単に長すぎるスキル。`SKILL.md` の行が多すぎる状態で、それらが古いか重複かとは独立である。全行が生きていて一意でも sprawl は起こる。可読性(行動に移る前にエージェントがより多くを読み、注意が余分に薄まる)、保守性(余分な 1 行は **relevance** を保つ対象が 1 つ増える)、トークンのコストを払う。処方箋は **information hierarchy**。**reference** を **context pointer** の陰へ下げ、**branch** か sequence で分割して各経路が必要な分だけを運ぶようにする。**sediment**(古い蓄積による長さ)や **duplication**(意味の重複による長さ)とは異なり、sprawl は原因を問わず長さそのものである。

_避ける語_: 肥大、長さ、サイズ、冗長

## Steering(操縦)

エージェントの実行時の挙動を **predictability** へ向けて形づくるレバー。

### Branch(分岐)

スキルが呼び出されうる別々のあり方。スキルが扱うケースで、runごとに別の経路を通る。steps の多いスキルは多数の branch を持ちうる。直線的なスキルは持たない。

_避ける語_: 経路、ケース、フォーク

### Leading word(先導語)

モデルの事前学習にすでに宿るコンパクトな概念(_Leitwort_ とも呼ぶ)で、スキル実行中にエージェントがそれで考える。モデルがすでに持つ prior を呼び起こすことで、行動原則を最小のトークンで符号化する(例: _lesson_、_proximal zone of development_、_fog of war_、_tracer bullets_)。文ではなくトークンとして繰り返され、スキル全体に分散した定義を蓄積し、行動の一領域を固定する。自分で語を作ることも、明確に定義すれば機能するが、造語は prior を呼び起こさない。事前学習語が無料で与えるものを定義トークンで払うことになる。まず既存の語へ手を伸ばす。

leading word は **predictability** に 2 度奉仕する。本文では **実行** を固定する。概念が現れるたびエージェントは同じ挙動へ手を伸ばし、フラットな reference の中では見るべき対象のクラスに注意を集め、run ごとに正しいチェックを呼び起こす。**description** では **呼び出し** を固定する。しかもスキル内に留まらない。同じ語がプロンプト・ドキュメント・コードベースに宿るとき、エージェントはその共有言語をスキルに結びつけ、より確実に発火する。description は、スキルを呼びたいとき実際に使う leading word で書く。

_避ける語_: キーワード、用語、モチーフ

### Completion criterion(完了基準)

作業の単位が終わったとエージェントに告げる条件。判定の対象となる目標。これをレバーたらしめる 2 つの性質がある。**明確さ**(done と not-done を区別できるか)は **premature completion** に抗する。曖昧な境界(「理解に達した」)はエージェントに done を宣言させ次の step へ滑らせる。この軸は step があって初めて効く。premature completion は step 間の失敗だからである。**要求量**(どれだけ求めるか)は **legwork** を定める。「変更したモデルをすべて計上」は「変更リストを作る」より徹底した作業を強いる。この軸は step に縛られない。フラットな reference も縛れる。これが steps を持たないスキルでも網羅性の基準(「全ルールを適用」)を持てる理由である。最強の基準はチェック可能かつ網羅的である。

_避ける語_: 完了条件、終了条件、停止規則

### Legwork(地道な作業)

エージェントが 1 つの step の中で裏で行う作業。ファイルを読み、コードベースを探索し、変更を加え、ユーザーに丸投げせず必要なものを掘り出す。step 構造の下に住み、それ自体を step として書かず、文言に潜み、スキルではなくエージェントが制御する。**post-completion steps** の step 間の引きに対する、step 内の相棒。**leading word**(_comprehensive_、_thorough_)や、作業を網羅的にせよと求める **completion criterion**(フラットな reference に適用した要求量を含む)によって高まる。要求が欠けるか、**premature completion** が step を短く切るときに薄くなる。

_避ける語_: スコープ、労力、勤勉さ、網羅

### Post-completion steps(後続 step)

現在の step に続く **steps**。見えていると、エージェントを前へ引き **premature completion** へ誘う。見える数が多いほど引きは強い。防御は、steps の連なりを 2 つに分けて隠すこと。

_避ける語_: 地平、fog of war、先読み

### Premature completion(早すぎる完了)

_失敗モード。_ 現在の step を本当に終わる前に終えること。エージェントの注意が、作業ではなく done であることへ滑るために起こる。step 間の失敗で、起こるには **steps** が要る。steps を持たないスキルが早く止めるのは premature completion ではなく、要求が満たされない下での薄い **legwork** である。2 つの力の綱引き。見えている **post-completion steps**(前への引き)と、**completion criterion** の明確さ(抵抗。鋭くチェック可能な境界は持ちこたえ、曖昧な境界は屈する)。曖昧さが必要条件である。鋭い境界は、後続の step がいくつ見えていても引きに抗するため、決して急がない step は防御を要さない。急ぐ step を持ちこたえさせるレバーは 2 つあるが、順に手を伸ばす。**まず境界を鋭くする**。局所的で安価である。基準が本質的に曖昧で、かつ実際に急ぎを観測したときだけ、**後続の step を隠す**。隠蔽は本物の文脈境界(user-invoked の受け渡しか subagent への発送)でのみ効く。インラインの model-invoked 呼び出しは後続の step を文脈に残し、何も消さない。薄い legwork の一因だが、それとは異なる。legwork は step が完走しても薄くなりうる。

_避ける語_: 早すぎるクロージャ、急ぎ、近道

### Negation(否定)

_失敗モード。_ 禁止による操縦。エージェントに「するな」と告げることで、禁じた挙動を文脈に引き込み、かえって「利用しやすく」する。_象を思い浮かべるな_ と言えば象しか残らない。_冗長なコメントを決して書くな_ と言えば、冗長さがエージェントが今読んだパターンになる。否定は弱い修飾で、強く活性化した概念に飲まれ、禁止が半ばその行為への指示として読まれる。その **leading word** が _象_ である。禁止が枠に名指しするものが何であれ。処方箋は **肯定** でプロンプトすること。目標の挙動を述べ(「1 行コメントを書く」)、禁じた側を口に出さない。禁止が場所を得るのは、肯定で言い換えられない挙動へのハードなガードレールとしてだけで、それでも肯定の目標と対にし、注意がすべきことに落ちるようにする。

_避ける語_: 皮肉な反動、ダメ出しプロンプト、ピンクの象

## Pruning(剪定)

スキルを無駄なく保つ。各処方箋を、それが治す失敗と対にする。

### Single source of truth(単一の真実の源)

各意味がちょうど 1 つの権威ある場所に住む望ましい状態。スキルの挙動の変更が 1 か所の変更で済む。**Duplication** はその違反である。

_避ける語_: home、正典の場所

### Duplication(重複)

_失敗モード。_ 同じ意味に 2 つ以上の **single source of truth** を与えること。保守(1 か所を変えれば他も変えねばならない)、トークン、目立ちの過大化(意味の繰り返しが階段上の実際の順位を超えて重みを与える)のコストを払う。**leading word** の偶発的な逆。leading word はトークンを繰り返して意図的に注意を上げるが、意味は繰り返さない。

_避ける語_: 反復、冗長

### Relevance(関連性)

ある行がスキルの働きにまだ関わるか。何を残すかのレンズ。行は 2 通りで関連性を失う。作業に一度も関わらない(単なる説明か、disclose すべき **branch**)か、古びる(記述する挙動や世界が変わってずれる)。短いスキルほど関連性を保ちやすい。各行のチェックが安いからである。**no-op** とは異なる。relevance は行が作業に関わるかを問い、挙動を変えるかは問わない。

_避ける語_: load-bearing、陳腐化、新鮮さ

### Sediment(堆積)

_失敗モード。_ スキルに沈着して決して除かれない古い内容の層。足すのは安全に感じ、除くのは危険に感じるため、古く無関係な行が積もり、まだ生きているものを見つけるのに掘り下げねばならなくなる。剪定の規律を持たないスキルの既定の運命。**duplication** の意味の繰り返しに対し、こちらは **relevance** の緩慢な浸食。

_避ける語_: 付着、肥大、垢、腐敗

### No-op(無効行)

_失敗モード。_ 何も変えない指示。モデルが既定で既に行うことを言い、何も言わないために負荷を払う。テスト: その行は既定に対して挙動を変えるか。行は完全に **relevant** でありながら no-op でありうる。**leading word** を無料にする同じ prior が、no-op を無価値にする。

leading word は _技法_、no-op は行への _評決_ で、両者は交差する。既定に勝てないほど弱い leading word は no-op であり(_be thorough_ をエージェントが既にそこそこ徹底しているとき)、直し方は評決を通す強い語(_relentless_)であって別の技法ではない。だから no-op のテスト(既定に対し挙動を変えるか)は、leading word が繰り返しに値するかの採点でもある。これはモデル相対であって読者相対ではない。ある行が no-op かで 2 人が割れるのは既定について割れているのであり、議論ではなくスキルを実行して決める。

_避ける語_: 冗長な指示、当たり前の再述、くどさ
