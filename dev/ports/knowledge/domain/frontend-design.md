# 視覚設計の正本準拠と方向づけ(frontend-design)

GUI を持つ作業で dev-implement・dev-spec に注入する知識 port。視覚設計の正本(事前指定のデザイントークン・共通レイアウト)への準拠を最優先とし、正本が無い場合にテンプレート的な既定デザインへの後退を避けて対象に固有の視覚的な選択を行うための規範。由来: Anthropic の frontend-design スキル(要点を日本語に再構成)、[addyosmani/agent-skills](https://github.com/addyosmani/agent-skills) frontend-ui-engineering(Design System Adherence)。

## 1. 正本への準拠(最優先)

プロジェクトに視覚設計の正本(デザイントークン定義・共通レイアウト仕様・デザインシステム・UI モック)が指定されている場合、以降の節の規範(方向づけ・トークン系の新規作成)より正本への準拠が優先する。

- トークン系を再発明しない。色・書体・余白・角丸は正本のトークンから導き、生の値(hex 直書き・スケール外の任意 px)を書かない。スケール外の値が必要になったら、その場しのぎで書かず正本側の更新として扱う。
- 共通レイアウト(ヘッダ・ナビゲーション・フッタ等)は共通コンポーネントとして 1 箇所に実装し、全ルート(認証後の画面を含む)に配線する。画面ごとに再実装・省略しない。新規画面の完了条件に「共通レイアウトへの配線」を含める。
- トークン・共通レイアウトは「定義した」だけでは完了でない。実ルートに配線され、起動した画面の観察(実行時検証)で適用を確認できて完了とする。

## 2. 主題に根ざす

- 何のプロダクトか・誰が使うか・そのページの唯一の仕事は何かを、設計前に 1 つに定めて明言する。
- 特徴的な選択は主題の世界(その領域の素材・道具・語彙)から導く。どの依頼にも通用する汎用の見た目を、その依頼への答えにしない。

## 3. 設計原則

- **ヒーローはテーゼ**: 冒頭には主題の世界で最も特徴的なもの(見出し・画像・動くデモ・インタラクション)を置く。「大きな数字 + 小さなラベル + グラデーション」はテンプレートの答えであり、本当に最適なときだけ使う。
- **タイポグラフィが人格を担う**: 見出しと本文の書体は意図して組み合わせ、太さ・字間・スケールを設計する。書体を中立な運搬手段にしない。
- **構造は情報**: 番号・ラベル・罫線などの構造装置は、内容について真であることを符号化する場合のみ使う(順序が意味を持たないのに 01/02/03 と番号を振らない)。
- **モーションは意図的に**: 散発的な効果より、練られた 1 つの見せ場が効く。動きを足すほど AI 生成らしさが出る場合は減らす。
- **複雑さはビジョンに一致させる**: マキシマルな方向には作り込みを、ミニマルな方向には余白・字間・細部の精度を。

## 4. 既定デザインの回避(自己校正)

AI 生成デザインは次の 3 つの見た目に集中しやすい。依頼が明示的に求めない限り、自由に使える軸をこれらに費やさない。

1. 温かいクリーム背景(#F4F1EA 付近)+ 高コントラストのセリフ見出し + テラコッタのアクセント
2. ほぼ黒の背景 + 蛍光グリーンまたは朱色 1 色のアクセント
3. 新聞風レイアウト(ヘアライン罫・角丸ゼロ・高密度カラム)

## 5. 進め方(2 パス)

1. **計画**: 正本が無い場合に限り、依頼からコンパクトなトークン系を作る — 色(名前付き 4〜6 色)・書体(役割 2 つ以上: 個性的な見出し用 + 補完する本文用)・レイアウト概念(1 文 + 必要なら ASCII ワイヤーフレーム)・**シグネチャ**(このページが記憶される唯一の要素)。正本がある場合は 1 節(正本への準拠)に従い、正本のトークン系を計画の入力にする。
2. **批評してから実装**: 計画を依頼と突き合わせ、「似た依頼でも同じ答えになる部分」があれば汎用の既定と見なして修正し、何をなぜ変えたかを述べる。実装は修正済みの計画に従い、全ての色・書体の決定をトークン系から導く。

- CSS ではセレクタ詳細度の衝突(型ベースと要素ベースの相殺、セクション間の padding/margin)に注意する。

## 6. 抑制と品質床

- 大胆さは 1 箇所(シグネチャ)に集中させ、周囲は静かに規律を保つ。仕上げ前に「装飾を 1 つ外す」。
- 品質床(宣言せずに満たす): モバイルまでのレスポンシブ・キーボードフォーカスの可視化(`:focus-visible`)・`prefers-reduced-motion` の尊重。

## 7. UI の文言

- 文言は装飾ではなく設計材料。ユーザー側の語彙で命名し(システムの実装語彙で書かない)、能動態で、操作の結果をそのまま言う(「保存する」であって「送信」ではない)。同じ操作は全フローで同じ名前を保つ。
- エラーは謝らず、何が起きたか・どう直すかを具体的に言う。空状態は行動への招待にする。
