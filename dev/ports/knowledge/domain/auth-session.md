# 認証・セッション管理(auth-session)

認証を含む作業で dev-spec・dev-implement に注入する知識 port。「認証が破られない」(セキュリティ観点の守備範囲)とは別軸の、「認証が動き、維持される」(機能の成立)を守るための知見。出典: [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills) security-and-hardening(セッション管理・認証チェックリスト)。

## 1. セッションの保存と復元(リロード耐性)

- セッションの既定は httpOnly・secure・sameSite を設定した Cookie とする。認証トークンを localStorage・sessionStorage に保存しない(XSS で窃取可能)。
- SPA でトークンをメモリにだけ保持する構成は、リロードで認証状態が消える。設計時にリロード復元の経路(Cookie セッション・silent refresh・サーバ側セッション)を明示し、「ログイン → リロード → 認証維持」を受け入れ基準とテストに必ず含める。
- アプリ起動時のセッション復元処理(初期化時に認証状態をサーバへ問い合わせる等)を実装する。フロントの認証状態ストアを初期値(未認証)のまま画面遷移の判定に使うと、リロード直後に誤ってログイン画面へ遷移する。

## 2. ログイン正常系の落とし穴

いずれも単体テストのグリーンに現れず、実行時にのみ露見する。

- 初期ユーザー不在: seed が無く、初期状態でログインできるユーザーが存在しない。seed の作成方法と初期状態を環境定義に含める。
- Cookie 属性と環境の不一致: `secure` Cookie は http のローカル環境で送信されない。`sameSite` とクロスオリジン構成の不整合でセッション Cookie が付かない。環境(ローカル・本番)ごとの属性の切り替えを設計で明示する。
- CORS: 資格情報付きリクエストは `credentials: true` と特定オリジンの許可の両方が必要(ワイルドカード不可)。
- トークンの往復不一致: フロントが送る場所(ヘッダ・Cookie)とバックエンドが検証する場所の不一致。送信側と検証側を同じ設計節で定義する。
- 認証エンドポイントにはレート制限を設ける(正常系の設計と同時に決める)。

## 3. セッションのライフサイクル

- 有効期限・アイドルタイムアウト・同時ログインの扱い・ログアウト時のクリーンアップ(サーバ側セッションの破棄と Cookie の失効)を定義する。
- セッション失効時の挙動(API が 401 を返したときの画面遷移・再ログイン導線)を異常系の受け入れ基準として定義する。未定義のままフレームワーク既定に委ねない。

## 4. 検証

- 認証・セッション境界の検証をモックで代替しない。実バックエンド + 実ブラウザ、または HTTP レベル(Set-Cookie の属性確認と Cookie 付き再リクエスト)で確認する。jsdom・偽 Cookie で緑にしたテストを認証成立の根拠にしない。
- 最低限のスモーク: ログイン 1 往復 → リロードでセッション維持 → ログアウト。実行時検証の規範は dev-core の runtime-verification リファレンスに従う。
